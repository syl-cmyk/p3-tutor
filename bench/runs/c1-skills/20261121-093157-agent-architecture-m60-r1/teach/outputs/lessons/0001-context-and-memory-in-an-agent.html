Lesson 1 · 60 minutes

Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what gets saved between visits, and how it finds the right page in a long manual.

Objective O3: context, memory, retrieval and notes About 60 minutes Builds on the agent loop (quiz 0001)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both jobs come down to the same question: what does the model see right now, and who put it there?

It also decides your bill, because you pay for what the model reads on every single step.

The numbers in the examples are made up to keep the arithmetic easy. Real token counts depend on the model and your text, so measure yours once you start calling a model.

Warm-up: recall (2 min)

Without scrolling up: a student asks, "Is the laser cutter free tomorrow at 3 pm?" The model asks for a calendar check. Who actually runs the calendar check, and what happens to the result?

Check your answer

The program around the model runs the tool. The result is sent back to the model in its next input, and the model is called again. Today's question is what that "next input" is made of, and how big it gets.

The context window: all the model sees 12 min

The model has no view of your program, your files or your database. It only sees the text you hand it on each call, and that text has a size limit.

Start with one real call

Here's roughly what the program sends to the model for the very first step of a student's question. Everything the model will ever know about this request is on this page.

[system prompt]  You are the makerspace assistant. Answer from the manuals.
                 Check the calendar before promising a time. Be brief.   (~300 tokens)
[tool list]      check_calendar(machine, date)   - Lists bookings for one machine on one day.
                 search_manuals(query)           - Finds manual pages that match a question.
                 book_slot(machine, date, time)  - Books a slot for the student.
                 ...descriptions and parameters...                        (~1,700 tokens)
[student]        Is the laser cutter free tomorrow at 3 pm?               (~40 tokens)

That whole bundle is the context: the text the model reads for one call. The context window is the maximum amount of text a model can take in, counted in tokens, which are the small chunks of text the model reads and writes (a token is roughly three quarters of an English word).

Anthropic's guidance on this treats the context as a limited resource to curate, and aims for the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).

Why the size matters twice

First, there's a hard limit: if the text doesn't fit the window, the call can't be made. Second, and sooner than you'd think, there's cost and quality.

You pay for the tokens you send, so a bloated context makes every request expensive. And more text doesn't mean better answers: a well-known study found that models answer best when the key fact is at the start or end of a long input, and do worse when it's buried in the middle (Lost in the Middle, TACL 2024).

A common mix-up (M7)

"A bigger context window means I can stop worrying about what goes in." It's tempting because a big window sounds like a big brain.

But the window is only how much fits. If you paste five manuals in, you pay for all of them every call, and the one sentence that matters may sit in the middle where the model is weakest.

Check yourself

Your assistant answers a question about the 3D printer. Which context is the best bet for a correct, cheap answer?

Show the answer

The third option. You want the smallest context that still contains what the model needs.

Spot what is in the context

Notice that the tool list in the example above took 1,700 tokens, much more than the question. Tools count against the window and your bill on every call, even when the model doesn't use them.

That's one reason to keep your tool list lean and the descriptions clear. A teammate who adds a tenth tool "just in case" is adding tokens to every future call.

Your turn

The program sends a call with: the system prompt (300 tokens), a tool list of three tools (1,700), the student's question (40), and yesterday's chat with this student (800). Which of these tokens was the model going to read anyway, and which did your program choose to add? Say what you'd do about the yesterday's chat.

Show a solution

The program chose all of it. The model reads whatever you send, and nothing else, so there's no "anyway". Yesterday's chat is the only item the student didn't write today; if most of it isn't needed, replace it with one or two lines of notes, which is cheaper and easier to read. Sending 800 tokens on every call of every request adds up fast.

Between steps: the context keeps growing 13 min

The model doesn't remember the previous step. So at every step of the loop, your program builds the whole context again, with everything that has happened so far added on the end.

Trace one request, step by step

This is the question from the warm-up, with a second part added: "Is the laser cutter free tomorrow at 3 pm, and what can't I cut on it?" Watch how many tokens the model reads at each call.

  1. Call 1. The model reads the system prompt, the tool list and the question: 2,040 tokens. It writes a request for check_calendar (60 tokens).
  2. The program runs the calendar check. It returns the bookings for tomorrow (300 tokens).
  3. Call 2. The model reads everything from call 1, plus its own request and the calendar result: 2,040 + 60 + 300 = 2,400 tokens. It requests search_manuals (70 tokens).
  4. The program runs the search and returns three manual pages (3,000 tokens).
  5. Call 3. The model reads 2,400 + 70 + 3,000 = 5,470 tokens and writes the final answer (80 tokens).

Add up what the model read: 2,040 + 2,400 + 5,470 = 9,910 input tokens for one student question, even though only about 5,500 tokens of text were ever written or returned. Everything old gets re-read on every call.

Check yourself

Same trace, but the manual search returns 9,000 tokens instead of 3,000. By about how much does the total input read across all three calls go up?

Show the answer

6,000 more. The extra arrives before call 3 and the loop ends there, so it is read once. Add two more steps after it and you'd pay for it three times. That is why big tool results are expensive in long loops.

Worked example: what clearing saves

A longer request takes five model calls. The system prompt and tool list are 2,000 tokens, the question is 40, and every step adds 500 tokens (the model's request plus the tool result). Compare no clearing with clearing.

  1. No clearing. Call 1 reads 2,040. Each later call reads 500 more than the one before: 2,540, 3,040, 3,540, 4,040.
  2. Total: 2,040 + 2,540 + 3,040 + 3,540 + 4,040 = 15,200 tokens read.
  3. With clearing. Say each older tool result shrinks to a placeholder, so an older step costs only 100 tokens, and only the newest step keeps its full 500. Call 1 reads 2,040. Call 2 reads 2,040 + 500 = 2,540. Call 3 reads 2,040 + 100 + 500 = 2,640. Call 4 reads 2,740 and call 5 reads 2,840.
  4. Total: 2,040 + 2,540 + 2,640 + 2,740 + 2,840 = 12,800 tokens read.
  5. That is 2,400 fewer tokens, about 16% less, and the gap widens with every extra step. The cost is that the model can no longer see the old raw results.
Your turn

A loop takes four model calls. Call 1 reads 2,040 tokens, and every step adds 800 tokens, with no clearing. Step 1 is done for you: call 2 reads 2,040 + 800 = 2,840. Work out calls 3 and 4 and the total across all four calls.

Show a solution

Call 3 reads 2,840 + 800 = 3,640. Call 4 reads 3,640 + 800 = 4,440. Total: 2,040 + 2,840 + 3,640 + 4,440 = 12,960 tokens read. Notice that the total is about 6.4 times the 2,040 of the first call, even though only four calls were made.

What to do when it grows

Long loops can blow past the window or past your budget. There are three moves, and they trade information for space (context management).

  • Clear old tool results. After the model has used a manual page, replace it with a short placeholder. The API's context editing does this automatically for the oldest tool results (context editing docs).
  • Summarize. When the conversation nears the limit, have the model write a short summary and start a fresh context from it. Anthropic calls this compaction.
  • Return less in the first place. Make search_manuals return two short passages, not whole chapters.

Here's what summarizing looks like in a long chat, where a student plans a whole project over many messages.

  1. Messages 1 to 30: the student plans a laser-cut box. The context has grown to about 20,000 tokens.
  2. Program: notices it's close to the limit it set for itself and asks the model: "Summarize this conversation, keeping decisions and open questions."
  3. Model: writes 300 tokens: "Box is 20 x 10 cm, 3 mm plywood, laser cutter booked Saturday 10 am, still need to choose the joint style."
  4. Program: starts a new context with the system prompt, the tool list and that summary. The next call reads about 2,300 tokens, not 20,000.

The price is that any detail the summary left out is gone from this context. That's why the prompt says what to keep, and why long-lived facts also belong in the notes file.

Providers may charge less for a context prefix that repeats from call to call, which helps loops like this. Check your provider's pricing page before counting on it.
A common mix-up

"Clearing a tool result means the model forgot the answer." Not quite. If the model already wrote down what mattered in its reply (say, "laser cutter free at 3 pm"), that stays in the context; only the bulky raw result is swapped for a placeholder.

The risk is the opposite: clear too early, before the model has used the page, and it has to run the search again.

Between sessions: notes as memory 14 min

When a conversation ends, the context is gone. The model never keeps anything on its own, so any memory across visits is something your program writes down and loads back in.

A common mix-up (M3)

"The assistant will remember Riley from last week." It feels natural because chatbots in apps seem to remember you.

But a fresh call starts with an empty context. Unless your program loads last week's information into it, the model has no idea Riley exists.

An example across two visits

The simplest memory is a file of notes that the assistant can read and write through tools. Anthropic's memory tool works this way: the model asks to view, create or edit files in a memory folder, and your application carries out those file operations (memory tool docs).

Here's how it would go for training status. This is the first visit.

  1. Student, Oct 3: "I just finished the laser cutter safety training."
  2. Model: asks to create /memories/students/riley.md with the line "Laser cutter training: passed 2026-10-03."
  3. Program: writes the file and reports success. The model replies: "Great, I've noted it."
  4. Session ends. The context is thrown away. The file stays on disk.

Now the second visit, three weeks later, a brand-new conversation.

  1. Program: starts with an empty context and checks the memory folder for this student, then lets the model view it.
  2. Student: "Can I book the laser cutter Saturday morning?"
  3. Model: views riley.md and sees the training line. It calls check_calendar, then book_slot.
  4. Model: "Booked for 10 am. Your laser cutter training is on file."

Notes can go stale

A note is a snapshot from the day it was written. The world can move on without the note knowing.

Say riley.md still says "Laser cutter training: passed 2026-10-03", but staff revoked the training in November after a safety incident. If the assistant trusts the note blindly, it books a dangerous machine for someone who shouldn't have it.

  1. Student: "Book the laser cutter Saturday."
  2. Model: views the note and sees "passed". It calls check_training_record("riley") as well, because the system prompt says to confirm safety-critical facts against the official record.
  3. Tool: returns "laser cutter: revoked 2026-11-12".
  4. Model: refuses to book, explains why, and updates the note.

So treat notes as hints that save time, and send anything where a mistake could hurt someone back to the real source. Put a date on every line, so a reader can tell how old it is.

Your turn

Write the one-line note you'd save after this chat: the student says "I prefer evening slots, and I did the 3D printer training today, 14 November." Include a date and keep it short. Then say which of the two facts you'd double-check against an official source before acting on it.

Show a solution

For example: "2026-11-14: prefers evening slots (said by student). 3D printer training: reported done 2026-11-14, not yet confirmed by staff." The training claim is the one to verify, because it unlocks a machine; a preference for evening slots is harmless if it turns out to be wrong.

Deciding what to save

Notes are small, on purpose. Save facts that will be needed later and that the assistant can't easily look up again: a student's training status, a preference, a decision, a "tried this, it failed" note.

Don't save what a tool can fetch fresh. The calendar changes constantly, so a saved copy goes stale; call check_calendar instead. Anthropic describes this note-taking pattern, where an agent writes notes outside the context and pulls them back in later, in its context engineering post (source).

Training records decide who may use dangerous machines. Whether the notes file or an official database is the source of truth is a design decision for your team and the makerspace staff, not for the model.
Check yourself

Which of these belongs in the assistant's notes file between sessions?

Show the answer

The training note. It's small, it stays true, and it can't be fetched from anywhere else. Live data goes through tools, long documents go through retrieval.

Retrieval: finding the right page 13 min

The manuals are far too long to load every time. So instead of carrying them in the context, the assistant searches them and loads only the pages that match the question.

Retrieval is just another tool

Retrieval means fetching only the relevant pieces of a large body of text into the context when they're needed. Anthropic's term for the pattern is "just in time": keep light pointers such as file paths or search queries, and load the real content on demand (source).

In your assistant that's search_manuals(query). Before it works, someone has to cut each manual into small chunks, such as a section or a page, so a search can return a few of them and not a whole book.

A trace: a safety question

  1. Student: "Can I cut vinyl stickers on the laser cutter?"
  2. Model: requests search_manuals("laser cutter vinyl materials allowed").
  3. Program: searches the chunks and returns the top two (about 600 tokens), each with its source: 
    [laser-cutter-manual, p.14] Never cut PVC or vinyl. It releases
chlorine gas, which harms people and corrodes the machine.
[laser-cutter-manual, p.13] Approved materials: plywood, acrylic,
cardboard, ...
  4. Model: "No, vinyl isn't allowed: it gives off chlorine gas when cut (manual, p.14). Acrylic or plywood stickers work."

The context grew by about 600 tokens, not by a 120-page manual. And because each chunk carries its source, the student can check the answer, which matters for safety rules.

How big should a chunk be?

This is the choice that most affects whether the right text comes back. Take the same laser cutter manual and look at three ways to cut it.

Chunk sizeWhat the search returnsProblem
One sentence"Never cut PVC or vinyl."Loses the reason and the neighbouring rules
One section (about 500 tokens)The whole "Materials" sectionUsually the sweet spot, with the rule and its context
One chapter (about 6,000 tokens)Everything about materials, settings and cleaningMostly irrelevant text, and it costs ten times more

There's no perfect size, and the sweet spot depends on how your manuals are written. Try a size, ask ten real student questions, and look at what comes back. Keep each chunk's source and page, so every answer can be checked.

What retrieval saves you

Say the laser cutter manual is 120 pages at about 500 tokens a page, so 60,000 tokens. Paste it in and every call in a three-call loop reads it: 3 × 60,000 = 180,000 tokens, before anything else is counted.

With retrieval, the manual is read once, by the search, outside the model. The model reads only the 600 tokens that come back, and re-reads them in at most the calls after. That is the difference between a request that fits a small budget and one that doesn't.

Where retrieval goes wrong

Retrieval returns the best matches it finds, not necessarily the right ones. If the student says "burn marks" and the manual says "scorching", a keyword search may miss it, and the model will answer from nothing or from a wrong page.

So two choices matter for your design review: how you cut the chunks, and how many you return. Too small and a rule loses its context ("never cut it" without saying what); too many and you're back to a bloated context.

The model also sees the query it wrote, so a tool description that tells it to search with the machine name and the material gets better matches than a vague one.

A common mix-up (M8)

"Retrieval means the model reads the whole manual and finds the page itself." It's tempting because it sounds like how a person would do it.

But the model only reads what the tool returns. If the search misses the right page, the model never sees it, however good the model is.

Check yourself

A student asks about "burn marks" and the manual only says "scorching". The search returns nothing useful. Which fix is the most direct?

Show the answer

Retry with other wording. The failure is in what retrieval returned, and the loop gives the model a chance to try again. Matching by meaning is another fix you can look into later.

Put it together: design the assistant's memory 13 min

You now have three places information can live: the context for this call, a notes file for later visits, and the manuals behind a search. Your job at the design review is to say which piece goes where.

Worked example

Decide where each piece of information lives for the request: "Book me the 3D printer Friday afternoon, and remind me what filament to use."

  1. The assistant's rules (be brief, check the calendar first): they apply to every call, and they are small. They go in the system prompt, always in the context.
  2. Friday's printer bookings: they change by the hour. They come from check_calendar at the moment they're needed, and aren't saved.
  3. Whether this student passed the 3D printer training: small, stable, and not available from anywhere else on this call. It goes in the notes file, loaded at the start of the session.
  4. Which filament to use: it's in the printer manual, which is long. It stays on disk and comes in through search_manuals, as one or two chunks.
  5. Old tool results after the answer: once the filament chunk has been used, it can be cleared if the conversation goes on for many more steps.

  1. Done for you: "which tools did I use last time" is about this student's history, so it comes from the notes file.
  2. Monday's vinyl cutter bookings: where do they live?
  3. The right blade for the vinyl cutter: where does it live?
  4. What stays in the context for the whole request, and what could be cleared if the conversation ran long?
Show a solution
  1. Last time's tools: notes file, viewed at the start of the session.
  2. Monday's bookings: check_calendar("vinyl cutter", Monday), fetched live and never saved, because it can change before the student arrives.
  3. The blade: search_manuals("vinyl cutter blade"), which returns one or two chunks from the manual with their page numbers.
  4. Always in context: the system prompt, the tool list and the student's questions. Clearable later: the raw calendar result and the manual chunks, once the answers have been written into the model's replies.

The three calls: view the notes file, check the calendar, search the manuals. The book action comes after the student agrees.

Worked example: one request, all three kinds of memory

Riley comes back in December: "Is the laser cutter free Saturday morning? And can I cut my vinyl stickers there?" Here is the whole trace.

  1. Program: starts a new context with the system prompt and tool list (2,000 tokens), loads riley.md (60 tokens), and adds the question (40 tokens). Memory between sessions, done.
  2. Call 1: the model sees the training note, and requests check_calendar("laser cutter", Saturday).
  3. Call 2: the calendar result (300 tokens) is in the context. The model requests search_manuals("laser cutter vinyl"). Live data, then retrieval.
  4. Call 3: two manual chunks (600 tokens) are in the context. The model writes: "Saturday 10 am is free. But no vinyl: it releases chlorine gas (manual, p.14). Want me to book 10 am for acrylic?"
  5. Riley: "Yes, acrylic." The model calls book_slot, then writes a note: "2026-12-05: booked laser cutter Sat 10 am. Asked about vinyl; told not allowed." The session ends and the context is discarded.

Count what the assistant kept: the notes file kept two things, one old and one new; everything else was fetched, used and dropped.

Your turn, a harder one

A student writes: "Last month you told me the vinyl cutter was out of blades. Is it fixed? And is the bandsaw free Tuesday?" Say where each fact comes from and what the assistant would do first. One of the facts is a trap.

Show a solution

"Last month you told me" is a claim about an old conversation. The model doesn't have that conversation, so it can't confirm it from memory; it can only look in the notes file, and if nothing is there, say so honestly and check the current state. "Is it fixed?" is a live fact: the answer isn't in the notes or the manuals, so it needs a tool such as an equipment status check, if you build one. The bandsaw question is a calendar lookup: check_calendar("bandsaw", Tuesday).

The trap is trusting the student's version of last month. The assistant should never pretend to remember; it should read its notes, then check the live state.

Say it with your budget in mind

For your design review, prepare one sentence for each choice. For instance: "We search the manuals instead of loading them, because every step re-reads the whole context and we pay per token."

Then add the matching trade-off: "The risk is a missed page, so the search tool lets the model retry and always returns the page number."

Before you leave: a design-review checklist 6 min

You can turn everything above into six questions to ask about any agent design, yours included. Try answering each one for the makerspace assistant out loud before you open the answer.

Question 1

What exactly is in the context on the first call, and roughly how many tokens is it?

A good answer

The system prompt, the tool list, any loaded notes and the student's message. For your assistant, count the tool descriptions first; they're usually the biggest part, and they're paid for on every call.

Question 2

What is the biggest thing that gets added during a request, and what happens to it afterwards?

A good answer

Usually a tool result, such as manual chunks or a long calendar listing. Decide whether it stays, is cleared after use, or is shortened at the source by returning less.

Question 3

What happens when the conversation gets long, and who decides?

A good answer

Your program decides, not the model. Pick a limit, and decide whether to clear old results, summarize, or stop and ask the student to start again.

Question 4

What does the assistant know about a student who has never used it before, and about one who has?

A good answer

For a new student, nothing beyond what they say. For a returning one, only what your program loads from the notes file or database at the start. If a fact isn't loaded, the model doesn't have it.

Question 5

Which notes could be wrong, and how would the assistant find out?

A good answer

Anything that can change after it was written, such as training status. Dates on every line help, and safety-critical facts should be checked against the official record with a tool.

Question 6

How does the assistant find the right manual page, and what does it do when the search misses?

A good answer

It calls a search tool that returns a few chunks with their page numbers. When nothing useful comes back, it retries with other words, and if that fails it says it couldn't find the answer and points the student to staff, so it never guesses at a safety rule.

Summary and where to go next 4 min

  • The model only sees its context: the system prompt, the tool list, the conversation and the tool results, on every call.
  • Between steps, the program rebuilds that context with everything so far, so each call re-reads and re-bills the old text. Clear, summarize or return less.
  • Between sessions, nothing persists unless your program saves it. Notes in a file are the simple memory: small, stable facts only.
  • Long documents stay outside the context and come in by retrieval: a search tool that returns a few chunks with their sources.

Say it in your own words: in two or three sentences, explain to a teammate why the assistant doesn't just paste all the manuals into every request, and what it does instead.
