Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it sits in the context, goes into saved notes, or gets looked up from the manuals only when needed.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are context-and-memory decisions, and they are also your biggest cost lever, because you pay for what goes into the model every single step.

The context window and what it keeps between steps 9 min

The model only sees what's in its window, and nothing else. So at every step, someone has to decide what goes in.

Let's watch a real request. A student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Here's what the program sends to the model on each call. The token counts are made-up round numbers, just to show the shape.

Trace: what the model sees at each call
  1. Call 1. Input: instructions + tool descriptions (2,000 tokens) + the student's question (100). Total 2,100. The model replies with a request for check_calendar("laser cutter", "tomorrow 15:00").
  2. Call 2. Input: everything from call 1, plus the model's request, plus the calendar result (400). Total 2,700 or so. The model asks for search_manuals("laser cutter training").
  3. Call 3. Input: everything from call 2, plus a manual page (1,500). Total about 4,300. The model writes the final answer.

Notice what happened. The model has no memory of call 1 when call 2 starts. The program just re-sends the whole list again, with new stuff added at the end.

That list is the context window: all the text the model reads for one call, including instructions, tool descriptions, the conversation so far and every tool result. It has a maximum size, counted in tokens (small chunks of text, roughly three-quarters of a word each on average). Anthropic's engineering team calls it a finite resource with diminishing returns ("Effective context engineering for AI agents").

So here's the cost point for your sponsor's budget: you pay for the input on every call. The trace above reads 2,100 + 2,700 + 4,300 = 9,100 input tokens, even though the actual new information is only about 2,000. Long runs get expensive fast because the early steps get re-read again and again.

There's also a quality problem. Anthropic describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it goes down, and this happens across models (source). It's a gradual slide, not a cliff, so a huge window doesn't mean you should fill it.

A common mix-up

"The model remembers the conversation, so the program doesn't need to send it each time." It's tempting because chat apps feel like talking to someone who remembers. In fact, each call starts blank, and the "memory" within a conversation is just the program re-sending the earlier text. If it isn't in the window on this call, the model doesn't know it.

What are your options when the window fills up? Two cheap ones from Anthropic's write-up: compaction, which summarizes the conversation so far and starts a fresh window with that summary, and clearing old tool results, which they call one of the safest, lightest forms of compaction (source). For your assistant, a raw calendar dump from call 2 is a good thing to clear once the model has used it.

Between sessions: notes as memory 7 min

When a conversation ends, the window is thrown away. So anything that must survive until the student's next visit has to be written somewhere outside the window and loaded back in later.

Here's what that looks like for you. Sam finishes laser-cutter training on Monday and tells the assistant. On Thursday Sam opens a brand-new chat and asks to book the laser cutter.

Trace: a note that survives the session
  1. Monday. Sam: "I just passed the laser safety quiz." The model asks for save_note("sam", "laser cutter: trained 2026-11-16").
  2. The program writes that line to a file or database row for Sam. It lives outside any context window.
  3. The chat ends. The Monday window is gone.
  4. Thursday. New chat. The program starts the context with the instructions plus Sam's saved notes (about 30 tokens).
  5. Sam: "Book the laser cutter Friday at 2." The model sees the note, skips the training question and goes straight to check_calendar.

That's memory in an agent: notes the program saves outside the window and puts back into a later window. Anthropic's memory tool works this way. Claude reads and writes files in a memory folder through ordinary tool calls, and you run the storage yourself (source). Anthropic also describes agents that write notes to memory as they go and pull them back in later (source).

The hard part isn't saving, it's deciding what to save. Notes loaded at the start of every session cost tokens on every call, so keep them short and useful. Claude Code, for example, loads only the first 200 lines or 25 KB of its memory file at session start (Claude Code docs). The lesson there is general: a notes file that grows without limit becomes its own cost.

Two design questions come up right away. First, who decides what to save: the model (through a save tool, as above) or your program (for example, always recording a passed training)? For something as important as training status, a fixed rule in your program is safer than hoping the model remembers to save it.

Second, what happens when notes get stale? If Sam's training expires after a year, an old note will confidently say "trained". Store a date with each fact, and let the model or program check it. This is the same problem you noticed with chatbots stating outdated facts.

A common mix-up

"A bigger context window means the assistant remembers students." It's tempting because both sound like memory. But a window only lasts for one conversation, however big it is. Remembering Sam on Thursday needs something saved outside it.

Retrieval: finding the right page 7 min

Manuals are too long to keep in the window, so the assistant looks things up only when a question needs them. This is retrieval: searching outside storage and putting only the best matches into the window.

The usual setup first splits each manual into chunks (say, a few paragraphs each) ahead of time. At question time, a search tool returns the chunks that best match the question. Chunks must be small enough to fit, but big enough to keep their meaning, and there's no golden rule for the size, so you'll tune it by testing on real questions (see the RAG survey).

Trace: one lookup
  1. Student: "What's the thickest acrylic I can cut?"
  2. The model asks for search_manuals("laser cutter maximum acrylic thickness").
  3. The program searches the chunks and returns the top 3 (about 300 tokens each, 900 total): "Laser cutter: material limits", "Laser cutter: focus height", "Acrylic safety notes".
  4. These 900 tokens join the window. The model reads "Acrylic: up to 10 mm" in the first chunk.
  5. The model answers: "Up to 10 mm. Thicker sheets won't cut cleanly." The other 59,000-odd tokens of the manual were never loaded.

The saving is big: if the whole manual was 60,000 tokens, loading it would cost 60,000 every call, against about 900 for the lookup. Anthropic calls this "just in time" loading: keep a light pointer (like a file path or a stored query) and load the content only when it's needed (source).

How does the search find the right chunk? One common way turns each chunk and the question into lists of numbers called embeddings, so that text with similar meaning gets similar numbers, and then picks the closest chunks (RAG survey). Plain keyword search also works, and often is a fine first version.

A common mix-up

"Retrieval always finds the right page." It's tempting because search feels reliable. But if the top 3 chunks are about the wrong machine, the model sees only those and will either answer from them or from guesswork. Log what was retrieved, so you can tell a bad search from a bad answer.

Retrieval is also just a tool, which connects back to the loop you already know. The model decides when to search, reads the returned chunks, and can search again with different words if the first results look wrong. That second try costs another call, so a good tool description and a step limit matter here too.

One more design choice is how many chunks to return. Too few and the answer might not be in them; too many and you're back to paying for pages the model doesn't need, and the useful line gets buried. Start with three to five and test on real student questions.

Worked example and practice 3 min

Now put the three places together on one list. Sorting each item is the exact decision you'll defend at the design review.

Worked example: where does each item go?

Item: "The booking tool takes machine, date and start_time."

  1. Is it needed on almost every call? Yes, the model must know the tools to call them.
  2. Is it short and fixed? Yes, a few dozen tokens.
  3. So it lives in the context from the start, with the instructions.

Sorting is half the job. The other half is checking what your choice costs, so let's do that with numbers for one full request.

Worked example: the cost of one request

A student asks a manual question that needs one search. The setup (instructions and tool descriptions) is 2,000 tokens, Sam's notes are 50, the question is 100, and the search returns 900 tokens of chunks. The model's search request and its final answer are about 100 tokens each.

  1. Call 1 input: 2,000 + 50 + 100 = 2,150 tokens. The model replies with the search request.
  2. Call 2 input: call 1's input, plus the 100-token request, plus 900 of chunks = 2,150 + 100 + 900 = 3,150 tokens. The model writes the answer.
  3. Total input read: 2,150 + 3,150 = 5,300 tokens.
  4. Compare: if the 60,000-token manual sat in the window instead, each call would read about 62,000, so the two calls would read about 124,000. That's roughly 23 times more input for the same answer.

Summary and go further 2 min

  • The model sees only the window; each call re-sends the history, so input cost grows with every step.
  • A longer window doesn't mean better recall: context rot is real, so keep it lean.
  • Between sessions, nothing survives unless the program saved it: short notes, loaded back at the start.
  • For long manuals, retrieve a few matching chunks instead of loading everything.
