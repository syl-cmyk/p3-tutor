Context and memory: what your agent sees, keeps and looks up

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each step, what gets saved between visits, and how it finds the right page in a long manual.

Why this matters for you

Your design review will ask three things: what does the assistant keep in context, what does it remember about a student next week, and how does it find a page in a 300-page manual? Your sponsor's budget makes the first one a money question, not just a design question.

Warm-up: recall (3 min)

From last time: in the agent loop, after the program runs a tool, what happens to the result? Say it in a sentence before you look.

Check your answer

The program hands the result back to the model as part of its next input, and calls the model again, so the model can decide the next step or write the final answer. Today's question is hiding inside that sentence: what exactly is "its next input", and how big does it get?

The context window 12 min

The model only knows what's in front of it on each call. That "in front of it" has a name, a size limit and a price, so we start by looking at one real call.

Here's the very first call the makerspace assistant makes. The student typed one short line. Look at what actually gets sent:

SYSTEM PROMPT        (800 tokens)  "You are the makerspace assistant. Rules: ..."
TOOL DESCRIPTIONS    (600 tokens)  check_calendar, search_manuals, book_slot ...
USER MESSAGE          (30 tokens)  "Is the laser cutter free Friday at 3 pm?"
                     -----------
                     1,430 tokens sent to the model

The student wrote 30 tokens. The model was sent 1,430. Everything the model reads in one call is the context, and the maximum it can read at once is the context window. Anthropic's docs describe it as all the text a model can look at and reference when generating a response, which they compare to the model's working memory ([context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)).

A token is a chunk of text, roughly three quarters of a word in English. Models read and write in tokens, and providers bill by them. The numbers in this lesson are made up to be easy to add, but the shape is real.

Now see the same chat one turn later, to watch the list grow. Dana answers the assistant's reply with "Okay, book it". What does your program send on that second turn?

  1. The system prompt and tool descriptions again: 1,400 tokens, unchanged.
  2. Dana's first question, 30 tokens, exactly as before.
  3. Every step the assistant took on the first turn: the calendar request, the calendar result, the search request, the manual excerpts, and the final answer. In the example below that's about 1,500 tokens.
  4. Dana's new message: "Okay, book it", 5 tokens.

Total: about 2,935 tokens to say five tokens' worth of words. The student typed a few words; your program sent a small book. That's why a chat that feels short to the student can be expensive for you, and why the next section is about the cost of keeping history.

The window is a budget, not a bucket

It's tempting to think a bigger window means you can stuff in everything. Anthropic's engineers say the opposite: context is a limited resource with diminishing returns, and the goal is the smallest set of high-signal tokens that gets the job done ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Two reasons. First, you pay for every token you send. Second, a stuffed window can make the model worse: they call this context rot, where the model's ability to accurately recall information from the context goes down as the number of tokens in it goes up (same source).

A common mix-up

"The model remembers what I told it earlier, like a person would." It doesn't. Each call starts blank, and the only reason the model "remembers" your earlier message is that your program pasted it into this call. If it's not in the context, the model doesn't have it.

The third option. The model is stateless between calls; the conversation exists in a list your program keeps and re-sends.

What survives between steps 13 min

Inside one request, the agent loop keeps adding to the context. So the cost of a request isn't one call's size; it's the sum of a growing series of calls.

Here is the full trace for "Is the laser cutter free Friday at 3 pm, and do I need training?". Watch the input column, the tokens sent to the model on each call.

Trace: one request, three model calls
  1. Call 1. Sent: system 800 + tools 600 + question 30 = 1,430. The model replies with a request: check_calendar("laser cutter", "Friday") (about 40 tokens).
  2. The program runs the tool. Result: "Friday 3 pm is free" plus the day's slots, about 200 tokens.
  3. Call 2. Sent: everything from call 1 (1,430) + the model's tool request (40) + the result (200) = 1,670. The model asks for search_manuals("laser cutter training") (40 tokens).
  4. The program runs the search and returns three manual excerpts, about 1,200 tokens.
  5. Call 3. Sent: 1,670 + 40 + 1,200 = 2,910. The model writes the final answer (about 100 tokens): "Yes, it's free. You need the Level 1 laser training first."

Input tokens billed in total: 1,430 + 1,670 + 2,910 = 6,010.

That's what the loop "keeps between steps": everything. Each step's request and result gets appended to the same list, and the whole list goes back in. Nothing is forgotten, nothing is compressed, unless you write the code that does it.

Why the manual should not live in the prompt

Say you skipped the search tool and pasted a 30,000-token manual into the system prompt, so the model always has it. Now every call starts at about 31,430 tokens, and three calls cost more than 94,000 input tokens. At a made-up price of $3 per million input tokens, that's about 28 cents against about 1.8 cents for the search version, for the same answer. (Real prices differ, and caching can discount a repeated prefix, but the 15x gap in tokens is the point.)

Output tokens are usually priced higher than input tokens, but in an agent the input side tends to dominate, because the whole history is re-sent on every step.

When the list gets too long

A long task can run for dozens of steps and fill the window. When that happens you have a few moves, and Anthropic's guidance names them: clear out old tool results that no longer matter, summarize the history and start a fresh window with the summary, or keep notes outside the window and read them back ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [context management announcement](https://www.anthropic.com/news/context-management)).

The cheapest one is the first. A calendar lookup from step 2 is useless by step 20, so your program can delete it from the list. Anthropic calls this context editing, and reports that it improved an agent's performance by 29% over baseline in their internal test on its own ([source](https://www.anthropic.com/news/context-management)).

Here's what trimming looks like on a longer run. A student is booking three machines in one chat, and the assistant has already made six tool calls. The trace shows one decision your program makes before the next call:

  1. The history holds six tool results: two calendar lookups (200 tokens each), two manual searches (1,200 each) and two training-record checks (100 each). That's 3,000 tokens of results.
  2. The student has now picked the laser cutter, so the 3D printer and vinyl cutter results are no longer needed.
  3. The program deletes the four results about those machines and leaves a one-line stub, [results for 3D printer and vinyl cutter removed], so the model knows something was there.
  4. What stays: the laser calendar (200), the laser manual excerpts (1,200) and the laser training check (100), which is 1,500 tokens. The next call is 1,500 tokens lighter on results, and so is every call after it.

The stub matters. If the history just changes silently, the model may be confused about why an earlier message refers to something that isn't there. A short placeholder keeps the story straight.

A common mix-up

"If a model's window is huge, I don't need to manage context." A huge window is a bigger limit, not a free pass. You still pay per token on every call, and by the context rot finding the model may recall the useful part less accurately when the window is crowded. Managing context is a cost and quality habit, not just a way to avoid hitting a limit.

What survives between sessions: notes 12 min

Once the request ends and the list is thrown away, the model remembers nothing. If the assistant should know next week that Dana already passed laser training, something outside the context has to hold that fact.

The simplest answer is a file. Look at what the assistant does when Dana comes back a week later:

Trace: a returning student
  1. Dana: "Can I book the laser cutter for tomorrow?"
  2. The model, with a memory tool in its tool list, first asks to view the memory folder: view /memory.
  3. The program lists the folder and sends it back: students/dana.md.
  4. The model asks to read students/dana.md. The program returns: "Passed laser Level 1 on Oct 14. Prefers afternoon slots. Banned from 3D printer until fines are paid."
  5. The model calls check_calendar, finds a free afternoon slot, and replies: "You're cleared for the laser. Tomorrow at 2 pm is open. Want it?"
  6. Dana says yes; after booking, the model asks to append "Booked laser Nov 22, 2 pm" to the file. The program writes it.

That is Anthropic's memory tool in a nutshell: a directory of files, outside the context window, that Claude can read and write to recall things across conversations. It's client-side, which means Claude only requests memory operations, and your application executes them against storage you control ([memory tool docs](https://platform.claude.com/en/docs/agents-and-tools/tool-use/memory-tool)).

Notice what that means for you as the designer. The "memory" is just a file your program owns. You decide where it lives, who can read it, and what gets deleted, which matters when it holds students' training records.

Now the first visit, because that's where the file gets made. Nobody wrote Dana's file by hand; the assistant did, in the moment, and you can trace it:

  1. Dana, first visit: "I just finished the laser safety class. Can you remember that?"
  2. The model views the memory folder. It's empty, so it asks to create students/dana.md with the text "Passed laser Level 1, Oct 14 (self-reported)".
  3. The program writes the file and returns "File created". The model replies: "Got it, I've noted that."
  4. Notice the words "self-reported". A good note records where a fact came from, because a student's word is weaker than the staff's training sheet. When the staff system is connected later, a tool call should win over the note.

That last step is a real design decision for your team, and it points at the main risk of notes: they go stale. A note that says "banned from 3D printer" is wrong the day the fines are paid. Good notes carry a date, and the assistant treats an old note as a hint to check, not as the truth.

Try it: write the note (faded)

A different student, Sam, says: "I'm Sam, I'm in mechanical engineering, I did the CNC router training last spring, and please don't book me before 10 am because of my classes." Write the lines you'd save to students/sam.md. The first line is given: Name: Sam (ME major). Decide what else is worth keeping, what you'd mark as self-reported, and what you'd leave out.

Show a solution

A good note: CNC router: trained, last spring (self-reported, check staff record) and Scheduling: nothing before 10 am (stated Nov 21). Leave out anything that isn't needed to serve him next time, such as the details of how he said it. The major could be debatable; it's fine to keep because it's short, but it's the least useful line, and notes full of trivia are what bloat the context when they get read back each visit.

Three kinds of memory, one rule for choosing

KindLives inLastsMakerspace example
ContextThe list sent each callOne request (or one chat)This morning's calendar result
NotesFiles or a database your program ownsAcross sessions, until deletedDana's training status
RetrievalA searchable index of documentsPermanent, updated by youThe laser cutter manual

The rule: put it in context if you need it right now, in notes if it's a fact about someone or something that changes through use, and in an index if it's reference material the assistant should look up but never change.

A common mix-up

"The assistant will automatically remember each student." It won't, and nothing happens by default. A fresh session starts with an empty context, so you have to build the save and the read-back yourself, as in the trace above.

Anthropic's reports say that pairing the memory tool with context editing improved performance by 39% over baseline in their test, against 29% for editing alone ([source](https://www.anthropic.com/news/context-management)). Those are one internal evaluation, not a promise for your assistant.

Finding the right page: retrieval 13 min

The manuals are too big to paste in and too important to guess at. So the assistant looks up only the few passages that matter for this question, and puts those in context.

Here's the idea first, with real text. The student asks: "Can I cut acrylic on the laser?" The manual has a page that says "Do not cut PVC. Cast PMMA up to 6 mm is approved. Use the red exhaust setting."

Trace: retrieval step by step
  1. Before any student asks (once): split the manual into chunks, short passages of a few hundred tokens each. Say there are 600 chunks.
  2. Turn each chunk into a list of numbers called an embedding, built so that chunks with similar meanings get similar numbers. Store them in an index.
  3. The student asks: "Can I cut acrylic on the laser?" The program embeds the question the same way.
  4. The program finds the chunks whose numbers are closest to the question's. The "PMMA up to 6 mm" chunk scores high, even though it never uses the word "acrylic", because PMMA is acrylic.
  5. It returns the top few chunks (say 3, about 1,200 tokens) as the result of search_manuals.
  6. The model reads just those and answers: "Yes, cast acrylic (PMMA) up to 6 mm is approved. Not PVC. Use the red exhaust setting."

This pattern is called retrieval-augmented generation, or RAG: look up relevant text, then let the model write from it. Retrieval is why the 30,000-token manual cost you 1,200 tokens in the last section. For your assistant it's also a tool the model calls, so it fits the agent loop you already know.

How many chunks to bring back

The number of chunks you return is a dial, and it trades quality against cost. Let's put numbers on it with the same assistant, where each chunk is about 400 tokens.

Worked example: top 3 versus top 10
  1. With 3 chunks, the search result is 3 × 400 = 1,200 tokens. If the right page is among the top 3, the model answers from it and nothing else is needed.
  2. With 10 chunks, the result is 4,000 tokens. The right page is more likely to be in there, but seven other passages come with it.
  3. That result is now part of the history, so it's re-sent on every later call. If three more calls follow, the extra 2,800 tokens are billed again three times: 2,800 × 3 = 8,400 extra input tokens, on top of the first 2,800.
  4. So top 10 costs about 11,200 extra tokens in this request for a better chance of finding the page. If the manuals are well chunked, top 3 is often enough, and you can test it on real student questions.

You don't have to guess the dial. Collect twenty questions students really ask, find the page that answers each, and see how often the right page lands in the top 3, the top 5 and the top 10. That's the same kind of check Anthropic ran, and it takes an afternoon.

Where retrieval goes wrong

Chunking can strip the meaning off a passage. Imagine a chunk that reads only "Replace the filter every 40 hours." Which machine? Anthropic's example is the same problem: a chunk saying revenue grew 3% never says which company or quarter ([Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)).

Their fix is to have a model write a short note for each chunk, such as "From the laser cutter manual, maintenance section", and put it in front of the chunk before indexing. They also pair embeddings with plain keyword search (BM25), which catches exact terms like a part number that embeddings can blur. In their tests, contextual embeddings alone cut failed retrievals in the top 20 results by 35% (5.7% down to 3.7%), and with keyword search added, by 49% (to 2.9%) ([source](https://www.anthropic.com/news/contextual-retrieval)). Those numbers come from their own test sets, so measure on your manuals.

A common mix-up

"Retrieval means keyword search." Keyword search misses "acrylic" when the page says "PMMA"; embeddings match meaning. But embeddings can miss exact codes, like "Model ULS-60". That's why the good setups use both.

The third option: exact strings are what keyword search is good at.

Fetch it when you need it

One last move: don't pre-load. Let the agent keep light pointers, such as file names or page ids, and load the full text through a tool only when it needs it. Anthropic calls this just-in-time retrieval, and notes the trade-off: it's slower than having data ready up front, and the agent needs good tool descriptions to know where to look ([source](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Putting it together 6 min

Now you design the whole memory plan for one request, using all three kinds. We'll do one with every step shown, then you do one with the first step given.

Worked example: Dana wants to cut acrylic tomorrow

Goal: say what goes where, and total the input tokens. Fixed prompt and tools: 1,400. Question: 50. Each tool request: 50 tokens.

  1. Call 1. Input 1,450. The model requests the memory file. The note comes back at 300 tokens.
  2. Call 2. Input 1,450 + 50 + 300 = 1,800. The model requests search_manuals. Three chunks come back at 900 tokens.
  3. Call 3. Input 1,800 + 50 + 900 = 2,750. The model requests check_calendar. The result is 200 tokens.
  4. Call 4. Input 2,750 + 50 + 200 = 3,000. The model writes the final answer.
  5. Total input: 1,450 + 1,800 + 2,750 + 3,000 = 9,000 tokens.
  6. Placement: the note was a notes read, the chunks were a retrieval, and the calendar result is context that can be dropped after this request.

Design-review practice

Your reviewer asks: "For each of these, where does it live: context only, a note file, or the retrieval index? Why?" Decide for all four before opening the answers.

  1. The band-saw blade-change procedure.
  2. "The student wants Friday, and the laser is booked until 2 pm."
  3. That Priya always asks for the large-bed 3D printer.
  4. The list of which chemicals are banned in the makerspace.
Show a solution

1: index, since it's reference text everyone shares. 2: context only, because it's true for this request and will be wrong tomorrow, so don't save it. 3: a note, since it's a fact about one person that helps next time. 4: index, because it's shared reference text, and if it's short enough you could even keep it in the system prompt, at the cost of its tokens on every call. The tie-break is how often it's needed: always needed goes in the prompt; sometimes needed goes in the index.

Summary
  • The model sees only the context: the text your program sends on each call. Anything not in it is not known.
  • Within a request, the loop re-sends everything each step, so cost grows with each call; trim stale results.
  • Between sessions, nothing survives unless your program saves it, for example in note files the model reads through a memory tool.
  • For long manuals, retrieve a few relevant chunks instead of pasting the lot, and use keyword plus embedding search.

Say it in your own words: without looking, explain to a teammate why the assistant "forgets" Dana overnight, and give one fix.

How to say it at the review

When a teammate asks "why not just give the model everything?", you now have three answers that each fit in a sentence. It costs money on every step, because the whole history is re-sent. It can hurt accuracy, because a crowded window makes recall worse. And it still wouldn't remember a student next week, because the context disappears when the request ends.

When they ask "so how does it know Dana?", the answer is a file your program reads at the start and updates at the end. When they ask "how does it find the right page?", the answer is a search tool that returns a few chunks. Three questions, three mechanisms, and none of them is "the model just remembers".

Last, a rule of thumb for your sketch: draw the context as a box, draw the notes and the index as boxes outside it, and draw arrows only where a tool call moves information in or out. If an arrow has no tool call behind it, you have invented a memory the model doesn't have.
