Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in your makerspace assistant, whether it lives in the context window, in a saved note, or in a manual you search.

Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both come down to what the model sees on each call, and every token it sees costs you budget. Today you learn the three places information can live, so you can defend your choice at the design review.

Warm-up recall

From the agent loop: after the program runs a tool the model asked for, what does it do with the result?

Check your answer

It puts the result into the model's next input and calls the model again. That is the whole point of today: "the model's next input" is the context, and it grows with every step.

What the model sees 6 min

The model has no view of anything except the text you hand it on each call. So everything you want it to know has to be in that text, and that text has a size limit.

Here's a real-looking call from your assistant, written out. A student types a question, and this is everything the model receives:

[system prompt]   You are the makerspace assistant. Be brief. Only book
                  a machine if the student's training is current.
[tool list]       check_calendar(machine, date)
                  search_manuals(query)
                  check_training_record(student_id)
                  book_machine(machine, date, time, student_id)
[user message]    Is the laser cutter free tomorrow at 3 pm, and do I
                  need training to use it?

That's roughly 2,000 tokens in your real assistant once the tool descriptions are fully written out (the number is my estimate, for the examples below). A token is a chunk of text, usually a bit under one word.

The context window is all the text a model can look at when it writes a response, including the response itself. Anthropic calls it the model's "working memory" (Claude docs, Context windows).

Everything in the request counts toward it: the system prompt, every message, the tool results, and the tool definitions (same page). Current Claude models have windows from 200,000 to 1,000,000 tokens, depending on the model.

A big window doesn't mean you should fill it. Accuracy and recall get worse as the token count grows, a problem the docs call context rot (Claude docs). Anthropic's engineers describe context as a finite resource with diminishing returns, and the aim is "the smallest possible set of high-signal tokens" for the job (Anthropic, Effective context engineering).

What survives between steps 7 min

Inside one request, the agent loop keeps everything. That's good for correctness and bad for cost, because the window grows with every step.

The reason is simple: the model is stateless, so the program re-sends the whole conversation on each call. The docs put it plainly: previous turns are "preserved completely" (Claude docs). An agent in a loop "generates more and more data that could be relevant for the next turn" (Anthropic).

Here's the laser-cutter question traced step by step. The token counts are made-up but realistic, so you can see the shape.

  1. Call 1. Input: system prompt, tools and question, about 2,000 tokens. The model asks for check_calendar("laser cutter", "tomorrow").
  2. The program runs it. The result, "free 2 pm to 5 pm", is about 300 tokens.
  3. Call 2. Input: everything from call 1, plus the model's request (about 100), plus the result (300): about 2,400 tokens. The model asks for search_manuals("laser cutter training").
  4. The program runs it. The three best manual passages come back, about 1,200 tokens.
  5. Call 3. Input: about 2,400 + 100 + 1,200 = 3,700 tokens. The model writes the final answer.

You're billed for input tokens on every call, so this request costs about 2,000 + 2,400 + 3,700 = 8,100 input tokens, not 3,700.

A common mix-up

It feels like the model "remembers" the earlier steps, the way you remember what you just read. It doesn't: it re-reads the whole transcript every call. That's why a big tool result is expensive twice, once when it arrives and again on every later call.

So what do you do when the window fills up? Two main moves. Tool result clearing drops old tool results you don't need again, which Anthropic calls "one of the safest lightest touch forms of compaction". Compaction summarizes the conversation near the limit and starts a new window with that summary (Anthropic).

The manual passage was useful for call 3, but if the student then asks a long run of follow-ups, you can clear it. Keep the conclusion ("laser cutter needs the safety course") and drop the 1,200 tokens of passage.

What survives between sessions 6 min

When a session ends, the context window is gone. Anything the assistant should know next week has to be saved somewhere outside it, and loaded back in.

By default, nothing carries over. Here's what a student sees if you don't build memory:

  1. Monday. Sam asks about the 3D printer. The assistant checks the training record: Sam passed the printer safety course. It answers.
  2. The session ends. The window, with everything in it, is thrown away.
  3. Thursday. Sam writes, "Can I book the printer for Saturday?" The model gets a fresh window containing only the system prompt, tools and this question. It knows nothing about Monday.
A common mix-up

Many people assume a chatbot "learns" from each conversation, so it'll remember Sam next time. The model's weights don't change when you chat with it. Any memory is something you build around the model: you save text, and you put it back into the next window.

The simplest build is note-taking: the agent writes notes to storage outside the window, and those notes are pulled back into the window later (Anthropic). Anthropic's examples are a to-do list or a NOTES.md file.

For your assistant, the note can be tiny. A trace of the same Thursday, with memory built:

  1. Sam: "Can I book the printer for Saturday?"
  2. The program, before calling the model, loads Sam's record from a file or database and adds it to the context: sam: printer-safety passed 2026-10-12; laser-cutter not trained (about 30 tokens).
  3. The model calls check_calendar("3D printer", "Saturday"), gets "free", and calls book_machine(...).
  4. It replies that the printer is booked, and the program saves a line: sam booked printer Sat.
Notice what you did not save: the whole Monday transcript. Saving every word and reloading it just brings the full-window cost back. Save facts that will matter, in a few lines.

Which facts? A good test: would the assistant be worse off next time without it? Training status, active bookings and a stated preference ("I only use the printer after 5 pm") pass. The text of last week's small talk doesn't.

Training status is a fact where being wrong has a cost (a student on a laser cutter untrained). So keep the record in a database your program reads as the source of truth, rather than a note the model wrote and could mistype. Notes the model writes itself are good for its own working state, like "still need to confirm the time with the student".

Finding the right page in a manual 7 min

Notes work for small facts about one student. A manual is the opposite: too big to carry in every window, so you search it and bring in only the part you need.

Start with the simplest option, because it might be enough. If your whole knowledge base is under about 200,000 tokens (roughly 500 pages), Anthropic says you can put it all in the prompt, and prompt caching can cut cost by up to 90% and latency by more than half (Anthropic, Contextual Retrieval). Check your manuals' size before building anything fancier.

If it won't fit, or the cost is too high, use retrieval: search the manuals and put just the best few passages in the window. The classic setup is called RAG, retrieval-augmented generation, where you retrieve information from a knowledge base and append it to the user's prompt (Anthropic, Contextual Retrieval).

A trace of how it works for the question "How do I change the laser cutter's focus lens?":

  1. Before any question (one-time setup). Split each manual into chunks, passages of usually no more than a few hundred tokens, and index them.
  2. At question time. The model calls search_manuals("change focus lens laser cutter").
  3. The search scores every chunk against the query and returns the top few, say 3 chunks of 400 tokens: 1,200 tokens.
  4. Those chunks come back as the tool result and join the window. The model writes the answer from them.

There are two ways to score chunks, and they fail in opposite places. Embedding search matches meaning, so "swap the lens" finds a chunk that says "replace the focusing optic". But embeddings "can miss crucial exact matches" (Anthropic).

BM25 matches the exact words. A query like "Error code TS-999" finds the chunk with that code, which meaning-based search may blur with other errors. Anthropic's pipeline runs both and merges the results, so each covers the other's blind spot (Anthropic).

A common mix-up

It's tempting to think a chunk carries its own context. It doesn't. A chunk reading "Press the red button twice" doesn't say which machine, so it can match the wrong machine's question. Anthropic's fix is to prepend a short note (50 to 100 tokens) saying where the chunk came from before indexing it, which cut retrieval failures by 35% with embeddings, and by 49% when combined with BM25 (5.7% to 2.9%) (Anthropic).

One more option sits beside this: don't search at all, but give the agent a pointer and let it fetch. Anthropic calls this just-in-time retrieval: keep lightweight identifiers such as file paths and load data through tools only when needed (Anthropic). It's slower than precomputed search, but needs no index. For a manual folder with one file per machine, a tool like read_manual(machine, section) could be enough.

Worked example and practice 3 min

Now put the three places together: for each piece of information, pick where it lives.

Worked example

Decide where each item for the makerspace assistant belongs: in the window every call, saved between sessions, or retrieved from a manual.

  1. "Be brief; only book if training is current." Needed on every call, tiny. It goes in the system prompt, always in the window.
  2. The laser cutter's maintenance chapter (40 pages). Large, and needed only for some questions. It's retrieved: chunks come in when searched, and only a few.
  3. Sam's training status. Needed across visits, small, and costly if wrong. It's saved in a database and loaded into the window at the start of a session.
  4. The calendar result from five steps ago. Needed once. Once its conclusion is used, clear it from the window.
Your turn

Place these three yourself. (a) The student's request, "book the vinyl cutter Friday at 2". (b) A 6-page PDF of the vinyl cutter's blade-change steps. (c) "Priya prefers afternoon slots." Start with (a): it's the live question, so it's in the window. Now do (b) and (c).

Show a solution

(a) In the window: it's what the model is working on right now. (b) Retrieved: or, if the manuals total under about 200,000 tokens, simply placed in the window with caching, but don't paste all of it into every call. (c) Saved between sessions: a small stated preference that should shape future bookings, loaded at the start of Priya's next session.

Summary and where next 3 min

  • The context window is everything the model sees on a call: instructions, tool definitions, messages and tool results, and its own reply.
  • Between steps the whole transcript is re-sent each call, so it grows; clear old results or compact to keep it small.
  • Between sessions nothing survives unless you save it: keep short notes or records, and load them back into the next window.
  • For a manual too big for the window, retrieve a few chunks, using meaning-based and exact-word search together.

Say it in your own words: without looking, explain to a teammate why Sam's training status goes in a saved record and the laser cutter chapter goes in a searchable index.

Why this matters in the real world: these choices decide your assistant's cost per request and how often it answers from the wrong page. Next in the mission is workflows versus agents: which parts of this should be fixed steps instead.
