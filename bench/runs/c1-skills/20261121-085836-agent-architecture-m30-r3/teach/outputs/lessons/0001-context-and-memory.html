Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a manual that gets searched.

Why this matters for you

The window: all the model ever sees 7 min

The model has no memory of its own. Every time you call it, it only knows what is in the text you send right now, so your program is deciding what it knows.

Warm-up recall

From the agent loop: after the model asks for check_calendar, the program runs it. Is the model still "running" while it waits, and does the next step continue the same model call?

Check your answer

No. Each step is a brand-new model call. The program runs the tool, then makes a fresh call that includes the result. That detail matters today: a fresh call knows only what you put in it.

Here is one real call from the makerspace assistant, written out as the text the model receives. This is everything it has.

[system]  You are the makerspace assistant. Answer from the manuals.
          Never book without checking the calendar. (about 800 tokens
          with the rules and tool descriptions)
[user]    Is the laser cutter free tomorrow at 3 pm?
[answer]  (the model writes here, and its reply also needs room)

That whole block is the context window: the fixed amount of text, counted in tokens (small chunks of text, roughly three-quarters of a word each), that the model can read and write in one call. Your input and the model's reply must both fit inside it, and the docs say that if they don't, newer models return an error rather than quietly cutting text (Claude docs: context windows).

Bigger windows exist, but size isn't the only cost. You pay for every token you send, and a model with a lot of text in front of it has more to sift through. Anthropic's advice is to aim for the smallest set of high-signal tokens that gets the job done (Anthropic: effective context engineering).

A common mix-up

"The assistant remembers my last chat, because chatbots seem to." They seem to because the app re-sends the earlier messages every time. Start a fresh call with only a new question, and the model has no idea who you are.

Check yourself

At step 3 of a loop, the model's answer depends on what the calendar tool returned at step 1. How does the model know that result?

Show the answer

The third option. The program re-sends the earlier result inside the new call, because the model keeps nothing between calls.

Between steps: the window grows 7 min

Inside one request, the loop keeps what happened by appending it to the window. That keeps the model on track, but each step makes every later call bigger and more expensive.

Take the request from the agent-loop lesson: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" The numbers below are made up but realistic, and each call re-sends everything before it.

  1. Call 1. The model sees the system prompt (800 tokens) and the question (30). That is 830 tokens in. It asks for check_calendar (40 tokens out).
  2. Call 2. The program sends 830 plus the request (40) plus the calendar result (150). That is 1,020 tokens in. The model asks for search_manuals.
  3. Call 3. The program sends 1,020 plus the request (40) plus three manual passages (1,200). That is 2,260 tokens in. The model asks for check_training_record.
  4. Call 4. The program sends 2,260 plus the request (40) plus the training record (100). That is 2,400 tokens in. The model writes the final answer.

Add the four inputs: 830 + 1,020 + 2,260 + 2,400 = 6,510 input tokens, for one student question.

See what dominates? The manual passages are 1,200 tokens, and you pay for them in calls 3 and 4. Anything big that lands in the window gets paid for again on every later step.

A common mix-up

"I'll just paste the whole laser cutter manual into the first message, so the model has it." Say it's 30,000 tokens. Then every call carries it, and the same request costs 830 + 1,020 + 31,060 + 31,200 = about 64,000 input tokens instead of 6,510. Roughly ten times the cost, for the same answer.

So long loops need housekeeping. Anthropic's context editing, for instance, clears old tool results once they've been used, while keeping the conversation flow (Anthropic: managing context). The simple version you can build yourself is to drop or shorten old tool results the model no longer needs.

Check yourself

Same four-call request, but search_manuals returns 2,000 tokens instead of 1,200 (everything else unchanged). How many input tokens in total across the four calls?

Show the answer

Call 1 is 830 and call 2 is 1,020, as before. Call 3 is 1,020 + 40 + 2,000 = 3,060. Call 4 is 3,060 + 40 + 100 = 3,200. Total: 830 + 1,020 + 3,060 + 3,200 = 8,110. The extra 800 tokens cost you twice, once in call 3 and once in call 4, so about 1,600 more than before (6,510).

Between sessions: notes as memory 6 min

When a session ends, the window is gone, and nothing carries over by itself. If the assistant should know something next week, your program has to save it somewhere and load it again.

The simplest working version is notes in a file. Here is a trace for Sam, who visits twice.

  1. Visit 1. Sam says: "I need the large bed on the 3D printer, my parts are wide." The model calls a save_note tool: "Sam prefers the large-bed printer."
  2. The program writes that line to Sam's notes file. The session ends and the window is thrown away.
  3. Visit 2, a week later. Sam says: "Book me the printer Thursday." Before the model is called, the program reads Sam's notes and puts them into the system prompt.
  4. The model now sees the note. It books the large-bed printer without asking again.

That is what "memory" means for an agent: information saved outside the window and loaded back in when it's needed. Anthropic's memory tool works this way. Claude reads and writes files in a /memories directory, and your own code does the storing, so you decide what persists (Claude docs: memory tool).

Where it livesLastsMakerspace example
The context windowOne requestTomorrow's calendar entries for the laser cutter
Saved notesAcross sessions"Sam prefers the large bed"
A database toolPermanently, exactSam's training status

The last row is my design advice, not a rule from a source: facts that must be exactly right, like who has passed laser training, shouldn't live in notes the model wrote in its own words. Keep them in a real record and let the assistant look them up with a tool, as check_training_record already does. Notes are best for soft facts, like preferences.

A common mix-up

"A bigger window means the assistant remembers more across visits." A bigger window only holds more within one request. When the session ends it's empty again, however big it was.

Show the answer

The third option. A wrong note about training could let someone onto a machine they aren't cleared for, so look it up.

Finding the right page: retrieval 6 min

Manuals are far too big to carry in the window every call, as the last section showed. So you keep them outside and fetch only the few passages that match the question.

This is retrieval, and it's another kind of memory, one the assistant reads but never writes. You prepare the manuals once, ahead of time:

  1. Split each manual into chunks, short passages of a few hundred tokens each.
  2. Index them so a search can find the right ones.

Then, at question time, search_manuals turns the question into a search, takes the best few chunks, and returns only those. Those 1,200 tokens in the last section were three chunks.

There are two ways to search the index, and they fail differently. Keyword search matches the exact words. Embedding search turns text into numbers so that passages with similar meaning land close together, even with no shared words. Anthropic's tests found that using both, and re-ranking the results, cut missed passages the most (Anthropic: contextual retrieval).

The student typesBetter searchWhy
"What does error E-204 mean?"KeywordThe exact code appears in the manual
"The edges of my acrylic look burnt"EmbeddingThe manual says "scorching", not "burnt"

One more trick fixes a chunk that makes no sense alone. A chunk saying "Set the speed to 2 mm/s" doesn't say which machine. Prepend a short line like "From the laser cutter manual, section on cutting acrylic" to each chunk before indexing, and the right one is found more often (same Anthropic source, which reports failed retrievals dropping from 5.7% to 2.9% when combining this with keyword search).

Check yourself

A student asks: "Why does my print keep lifting off the bed?" The 3D printer manual only says "first-layer adhesion failures". Which search finds that chunk?

Show the answer

The second option. The words differ but the meaning matches, which is what embeddings are for.

Worked example and practice 3 min

Now put the three kinds of memory together on one request. First I do one, then you do the next.

Worked example

Sam, in a later session: "How do I clean the laser lens? And book the cutter Friday at 2."

  1. Session start. The program loads Sam's notes into the system prompt: "Sam prefers short answers." That is saved memory.
  2. Call 1. The model asks for search_manuals("clean laser lens"). The manuals are not in the window; this is retrieval.
  3. Call 2. The window now holds the notes, the question and the top 3 chunks. The model asks for check_calendar(laser cutter, Friday).
  4. Call 3. The model asks for check_training_record(Sam), because training must be exact, so it comes from a database.
  5. Call 4. The model replies briefly, because the notes say so, and books Friday at 2 pm.
  6. Session end. The window is discarded. If Sam said something new about their preferences, the model saves one line to the notes.
Your turn

A new student, Priya, asks: "What's the maximum material thickness for the bandsaw? I always work with plywood, remember that for next time." Start with the first step done: the program loads Priya's notes, which are empty. For each remaining step, name where the information comes from: the window, saved notes, a database tool, or retrieval from the manuals.

Show a solution
  1. The thickness limit is in the bandsaw manual, so it's retrieval via search_manuals.
  2. The three returned chunks go into the window, and are re-sent on each later call.
  3. "Always works with plywood" is a soft preference, so the model calls save_note and it goes into saved notes.
  4. The session ends, the window is gone, and the next visit loads that note back.

Summary and go further 1 min

  • The model only knows what's in the window for this call; your program decides what goes in.
  • Within a request, the window grows each step, and you pay for everything again on every call.
  • Between sessions, nothing survives unless saved: notes for soft facts, a database for exact ones.
  • Long manuals stay outside and are searched; only the top few chunks enter the window.
