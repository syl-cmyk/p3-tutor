Context and memory: what your assistant sees, keeps and looks up

By the end of this lesson you can decide, for the makerspace assistant, what stays in its context, what gets saved between sessions, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 60 minutes Builds on your trace of the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both come down to this lesson's question: what does the model see right now, and where does everything else live? That is also where most of your model budget goes, so you'll defend this design at your review.

Warm-up 3 min

First, a quick pull from memory. It's what you built last time, and everything today sits on top of it.

Recall

A student asks, "Is the laser cutter free tomorrow?" Write out, in four or five steps, what happens from the question to the final answer. Say who does each step: the model, or the program around it.

Check your answer
  1. The program sends the question and the tool list to the model.
  2. The model replies with a request: check_calendar("laser cutter", "tomorrow"). That's only text.
  3. The program runs the tool and gets the bookings.
  4. The program sends the model the bookings as a new message, and calls the model again.
  5. The model writes the final answer.

Notice step 4: every step is a fresh model call. Today's whole question is what goes into each of those calls.

The context window, and what it costs 12 min

The model can only use text that's in front of it, and what's in front of it is rebuilt on every call. So the first job is to see exactly what that text is, and how it grows.

Here's one request through the makerspace assistant. I'm using rough, made-up token counts so you can add them up. A token is the small chunk of text a model reads and writes, usually a bit shorter than a word.

Example: one request, call by call

Student: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Fixed parts: system prompt 800 tokens, tool descriptions 600, the question 30. Each tool request is about 60 tokens.

  1. Call 1. The model sees system prompt + tools + question = 1,430 tokens. It asks for check_calendar.
  2. Call 2. The program sends everything from call 1, plus the request (60) and the calendar result (400) = 1,890. The model asks for search_manuals.
  3. Call 3. Everything again, plus the request (60) and a manual excerpt (1,500) = 3,450. It asks for check_training_record.
  4. Call 4. Everything again, plus 60 and the record (150) = 3,660. The model writes the answer.

Add up what was sent: 1,430 + 1,890 + 3,450 + 3,660 = 10,430 input tokens, for a request whose new information totals about 2,100.

Why's it re-sent? Because the model remembers nothing between calls. Each call is a fresh read of the whole transcript so far. The context window is that transcript: all the text the model can see in one call, including your instructions, the tool descriptions, earlier results and its own earlier output. It has a size limit, and Anthropic's docs describe it as the model's "working memory" (Claude docs: context windows).

Window sizes differ by model and change often, so look up the current limit for whichever model your team picks instead of memorizing a number.

That's why cost matters for you: you pay for input tokens on every call, and calls pile up. Fixed text like the system prompt and tool list is the cheap thing to trim, since it's repeated every time.

So what's actually in the window? Four kinds of text, and you control each one differently:

PartExampleWho controls it
Instructions"You are the makerspace assistant. Never book without checking the calendar."You, once, in the system prompt
Tool descriptionsWhat check_calendar does and what it needsYou, once, in the tool definitions
ConversationThe student's messages and the model's repliesThe user, and the model
Tool resultsCalendar rows, manual excerptsYour tools, so your design

The last row is the one that grows fastest, and it's the one you design. A tool that returns a whole manual, or fifty calendar rows when one would do, quietly inflates every later call. Returning less is one of the cheapest savings you have.

A common mix-up

"The model remembers the conversation, so I only pay for the new message." It's tempting, because chat apps feel like a continuing conversation. But the model is stateless: the program re-sends the transcript each call. Look at the example: call 4 re-sent the calendar result, though the model no longer needed it.

One more thing, and it's a surprise: a bigger window doesn't mean everything in it gets used equally well. In tests where the answer sat in the middle of a long input, models did noticeably worse than when it sat at the start or end, and accuracy fell as the input got longer (Liu et al., "Lost in the Middle"). Anthropic describes this as a limited "attention budget": every extra token competes with the others for it (Effective context engineering for AI agents).

Keeping the window lean as the loop runs 11 min

If everything stays in the window and gets re-sent, long tasks get slow, expensive and worse. So the agent needs a policy for what stays in context between steps. The short version: keep what the next step needs, and drop or shrink the rest.

Anthropic's guidance for this is to find the smallest set of high-signal tokens that gets the job done (source). Three habits follow from it:

  1. Keep pointers, not payloads. Hold a file name or page id, and load the content only when a step needs it. Anthropic calls this "just in time" loading.
  2. Clear old tool results. Once the model has used a result, the raw text is mostly dead weight. The Claude platform can do this automatically, removing the oldest tool results and leaving a placeholder (context editing docs).
  3. Summarize when it fills up. Replace a long history with a short summary of the decisions so far, then continue (same article).
Example: the same request, with the 1,500-token excerpt cleared
  1. Call 3 is unchanged: 3,450 tokens. The model reads the excerpt and asks for check_training_record.
  2. Before call 4, the program replaces the excerpt with one line: [manual excerpt cleared: laser cutter needs training level 2, booking limit 2 h], about 30 tokens.
  3. Call 4 is 3,660 − 1,500 + 30 = 2,190 tokens, instead of 3,660.

That one line is the useful part of the excerpt. Choosing what goes in it is the design work.

Summarizing deserves its own look, because it's the one you'd use on a long chat with a student who keeps changing plans. Here's how it plays out:

  1. Twenty messages in, the window holds 9,000 tokens of back-and-forth about booking, rebooking and a machine fault.
  2. The program asks the model for a summary: "Student wants the laser cutter Friday 2 pm. Booked. Trained. Reported the exhaust fan is noisy; told to email staff."
  3. The program starts a fresh window with the system prompt, tools and that 40-word summary, then carries on.
  4. The window is now about 1,500 tokens, but anything the summary left out is gone. If the student's exact wording of the fan fault matters later, it needs to be in the summary.

That last step is the trade. Summaries save tokens and lose detail, so write the instruction for the summary with care: say what must survive (decisions, bookings, open problems) and what can go (small talk, retries).

A common mix-up

"Just buy a bigger window and keep everything." It sounds simpler, but you'd pay to re-send everything on every call, and as the previous part showed, a long window can bury the one fact you need. A bigger window is room, not a plan.

One catch: clearing is lossy. If the model needed the excerpt again, it has to fetch it again, so clear things the loop is done with, not things it's still using. Which brings up the next problem: what survives when the whole session ends?

Check yourself

Notes: memory between sessions 12 min

When a session ends, the window is gone. So anything the assistant should know next time has to be written down somewhere outside the window, and loaded back in. That's all "memory" means for an agent: the model doesn't remember, the program does.

Here's what that looks like for your students. A session is one conversation, from the first message to when it ends.

Example: Priya's two visits
  1. Session 1, Oct 3. Priya: "I just finished the laser cutter safety class." The model calls save_note(student="priya", note="Laser cutter training done Oct 3"). The program writes it to a file or database row.
  2. The session ends. The window is discarded. The model keeps nothing.
  3. Session 2, Nov 14. Priya: "Can I book the laser cutter Friday?" Before the first call, the program looks up Priya's notes and puts them in the system prompt: Notes on this student: Laser cutter training done Oct 3.
  4. The model sees the note, calls check_calendar, and answers: "Yes, you're trained, and 2 pm Friday is free. Want me to book it?"

Notice the two parts: something writes the note (here, the model, through a tool) and something loads it at the start (here, the program). Anthropic's memory tool works this way: Claude makes tool calls to create, read and update files in a memory directory, and your application executes them, so you choose where the memory lives (memory tool docs).

What should go in a note? Facts that stay true and that the next session will need: training completed, preferred machine, a standing booking limit. Don't save the whole transcript. It's big, it's mostly noise, and you'd pay to re-load it every visit.

The same trick works inside one long session. The agent writes progress notes to a file, and Anthropic reports this lets it pick up after its window is cleared (context engineering article). They also report that combining context editing with the memory tool beat editing alone on their own agentic test (announcement).
A common mix-up

"The assistant will just remember Priya." Tempting, because a chatbot that greets you by name feels like it remembers. But nothing carries over unless your code saves it and loads it. If you forget the loading step, session 2 starts blank, however well session 1 went.

Notes can go stale

A note is a claim from the past. "Training done Oct 3" stays true, but "Laser cutter booked Friday" stops being true on Saturday, and a model that trusts it will give a confident wrong answer.

Two habits help. Put the date on every note, so the model can judge how old it is. And for anything the booking system already knows, call the tool instead of trusting a note.

Example: a stale note causes a wrong answer
  1. Notes loaded at the start: Priya: booked laser cutter Fri 2 pm (no date).
  2. Priya, three weeks later: "Do I have anything booked?"
  3. The model reads the note and says: "Yes, Friday at 2 pm." That booking was weeks ago.
  4. Fix: save only lasting facts as notes, and answer "what's booked?" from check_calendar, which is always current.

Also keep the notes store small. If every session appends five lines, the notes become a second long transcript that you load into the window every visit, and you've rebuilt the problem from the first part. Periodically merge or delete old notes, the way you'd tidy a lab notebook.

Check yourself

Which of these is the best thing for the assistant to save as a note about a student after a visit?

Show the answer

The training fact. Save small, lasting facts; leave out bulky transcripts and things a tool can look up fresh.

Retrieval: finding the right page 12 min

Notes are memory you wrote yourself. A manual is memory someone else wrote, and it's too long to put in the window. So the assistant needs a way to find just the right pages, and that's retrieval.

Retrieval means searching a collection outside the window and putting only the best matches into it. The standard recipe, often called retrieval-augmented generation, is: split the manuals into chunks ahead of time, then at question time find the chunks closest in meaning to the question and hand those to the model (Lewis et al., the original RAG paper). "Closest in meaning" usually means comparing embeddings: lists of numbers that a separate embedding model produces for a piece of text, so that similar meanings get similar numbers.

Example: one question, three chunks

The manuals were split into chunks beforehand. Student: "What speed do I use to cut 3 mm acrylic?" The scores below are invented, to show the idea; higher means closer in meaning.

  1. The program embeds the question and compares it to every stored chunk.
  2. Chunk A, "Laser cutter settings. 3 mm acrylic: speed 20 mm/s, power 60%": score 0.82.
  3. Chunk B, "Laser cutter safety: never leave a running job unattended": score 0.55.
  4. Chunk C, "3D printer: PLA nozzle temperature 200 °C": score 0.31.
  5. Taking the top 2 (called top-k, with k = 2) gives A and B, about 600 tokens. The 40,000-token manual stays outside.
  6. The model answers "20 mm/s at 60% power" from chunk A, and could add the safety reminder from B.

In an agent, retrieval is just another tool, like check_calendar. The model decides when to call search_manuals(query), reads what comes back, and can search again with a better query if the first try missed. That's the loop you already know, doing the lookup.

Two knobs decide how well this works. Chunk size: too small and a chunk loses its surroundings (a setting with no machine name); too large and you're back to paying for filler. And k: too low and you miss the answer, too high and you drag in noise. In the "lost in the middle" tests, going from 20 to 50 retrieved documents helped only a little, so more isn't a fix (Liu et al.).

When the search misses

Retrieval can fail quietly. The right page exists, but the question used different words than the chunk ("kerf" in the manual, "how wide is the cut" from the student), so the right chunk scores low and a wrong one wins.

Because the search is a tool inside the loop, the model gets a second chance. Here's a trace of what that looks like:

  1. Student: "How wide a slot does the laser leave?"
  2. The model calls search_manuals("slot width laser"). Back come chunks about slot-cut joinery and enclosure vents. None has the number.
  3. The model reads the results, sees they don't answer the question, and calls search_manuals("laser kerf width") instead.
  4. Back comes "Kerf for 3 mm acrylic: about 0.2 mm". The model answers.

This only works if the tool's description tells the model it can search again, and if results come back with enough text for the model to judge them. When no chunk answers the question, the assistant should say "I couldn't find that in the manuals" instead of guessing. That behavior goes in the system prompt, and it's worth testing on purpose.

A common mix-up

"Retrieval means the model looks things up in what it learned in training." It's tempting because both feel like the model "knowing" things. But training is frozen and can be outdated, which you've seen yourself. Retrieval pulls from your current documents, and puts the text into the window, so you can show the source.

Worked example and practice 10 min

Now you put the three tools together. For each thing your assistant needs to know, the question is where it should live: in the window now, in the notes store, or behind a search.

WhereGood forCost
In the windowWhat the very next step needsPaid for on every call

Worked example

Place these four items: (1) the system prompt telling the assistant its role; (2) "Sam completed laser training"; (3) the 80-page band saw manual; (4) the calendar result just fetched for this question.

  1. System prompt: needed on every call, and short, so it stays in the window. Keep it lean, because it's re-paid each call.
  2. Sam's training: small, lasting, about one student: notes. Load it at the start of Sam's next session.
  3. Band saw manual: large, and any question needs only a page or two: behind search.
  4. Calendar result: needed now, stale soon: in the window for this step, then cleared or shrunk to a note.

Worked example: a budget comparison

Assume 5 calls per request, and a fixed start of 1,400 tokens (prompt, tools, question). Each call adds about 400 tokens of new tool output that stays. Compare pasting a 40,000-token manual into the start with searching for a 600-token excerpt.

  1. Search design. Call sizes: 1,400; 1,800; 2,200; 2,600; 3,000. Sum: 11,000 input tokens. Add 600 once the excerpt arrives, and it's re-sent on the calls after it. Suppose that's calls 3, 4 and 5: 1,800 more. Total about 12,800.
  2. Pasted design. Every call carries the manual: 41,400; 41,800; 42,200; 42,600; 43,000. Sum: 211,000 input tokens.
  3. Compare. 211,000 ÷ 12,800 is about 16, so pasting costs roughly 16 times as many input tokens per request, before counting the accuracy loss.

These are illustrative numbers. The point is the shape: a big block in the fixed start gets multiplied by the number of calls.

Your turn: redo it with clearing

Use the search design above. Suppose the 600-token excerpt is cleared just before call 5, and replaced by a 30-token note. First step, done for you: calls 1 to 4 are unchanged at 1,400; 1,800; 2,800; 3,200 (the excerpt arrives with call 3, so call 3 is 2,200 plus 600). Now work out call 5 and the new total.

Show a solution
  1. Without clearing, call 5 would be 3,200 + 400 = 3,600 (the 400 is the new tool output).
  2. Clearing swaps the 600-token excerpt for 30 tokens: 3,600 − 600 + 30 = 3,030.
  3. Total: 1,400 + 1,800 + 2,800 + 3,200 + 3,030 = 12,230 input tokens, versus 12,800 before.

That saves only about 4%, because the excerpt was cleared late and the run is short. Clear earlier, or on longer runs, and the saving grows.

Argue it at your design review

A teammate says, "Let's skip retrieval and notes. We'll use a model with a huge window, paste in all the manuals, and keep each student's full chat history in there." Write three sentences of reply using cost, accuracy and what happens between sessions.

Show a sample reply

Cost: everything in the window is re-sent on every call of every request, so pasting all manuals multiplies our bill by the number of calls. Accuracy: long inputs bury facts, especially in the middle, so more text can make answers worse. Sessions: the window disappears when a session ends, so Priya's training status still needs a saved note either way.

Summary and go further 5 min

You started by seeing the window as a transcript re-sent each call, and ended by sorting what the assistant knows into three places. Here's the short version.

  • The model is stateless: each call re-reads the whole window, so context grows and you pay for it on every call.
  • Keep the window lean: pointers over payloads, clear or shrink used results, and summarize when it fills.
  • Memory across sessions is a store you write to and load from. The model doesn't remember; your program does.
  • Retrieval is a search tool that brings only the top-k relevant chunks of a long document into the window.

Say it in your own words: without looking up, explain to a teammate where Priya's training status lives, where the laser cutter manual lives, and why neither sits in the window all the time.
