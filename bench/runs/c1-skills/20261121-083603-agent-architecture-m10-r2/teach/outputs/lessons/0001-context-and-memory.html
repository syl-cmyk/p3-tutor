Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can say what goes in your assistant's context, what it saves between visits, and how it finds one page in a long manual.

Objective O3: context and memory in an agent About 10 minutes
Why this matters for you

Your assistant has to answer from long machine manuals, remember each student's training status, and stay inside a small budget. All three are context and memory decisions.

Warm-up 1 min

Recall

In the agent loop, who actually runs a tool: the model or the program around it?

Check your answer

The program. The model only writes a request for the tool; the program runs it and puts the result back in front of the model. That "putting back" is exactly what this lesson is about.

What the model sees 3 min

The model only knows what's in front of it on each call. So at every step, you're choosing what to put there.

Here's one request, with made-up but realistic sizes. A student asks: "Is the laser cutter free Friday, and how do I focus it?" The text sent to the model is called the context, and a token is a small chunk of text, roughly three-quarters of a word.

Trace: three model calls
  1. Call 1 sends the instructions (800 tokens), the tool descriptions (570) and the question (30): 1,400 tokens. The model asks for check_calendar.
  2. The program runs it and gets a 250-token calendar result. Call 2 sends everything from call 1, plus the request and the result: 1,650 tokens. The model asks for search_manuals.
  3. The manual page is 1,500 tokens. Call 3 sends all of it again, plus the page: 3,150 tokens. The model writes the answer.

Total the model read: 1,400 + 1,650 + 3,150 = 6,200 tokens, though the conversation only holds 3,150.

The model remembers nothing between calls; the program re-sends the whole history each time. The limit on how much fits in one call is the context window, and you pay for every token you send, every call ([context window docs](https://platform.claude.com/docs/en/build-with-claude/context-windows)).

A bigger window doesn't mean fill it. A long context costs more and is harder for the model to use well, so the aim is the smallest set of useful tokens ([Anthropic on context engineering](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

A common mix-up

"The model remembers what I told it earlier." It feels that way in a chat, but only because the program re-sends the earlier text. If it isn't in the context, the model can't see it.

Check yourself

Call 4 would add a 100-token model reply to the trace above. About how many tokens does call 4 send?

Show the answer

About 3,250: the whole 3,150-token history plus the new 100.

What survives between sessions 2 min

When a session ends, the context is gone. Anything the assistant should know next time has to be written down outside the model, then loaded back in.

Say Sam finishes the laser cutter training on Monday. A few days later Sam comes back and asks to book it. Here's what happens with notes, which means facts the program saves to a file or database:

Trace: saving and reloading a note
  1. Monday: the model calls save_note with {"student": "Sam", "laser": "trained 2026-11-17"}. The program writes it to a file.
  2. Monday: the session ends. The context is thrown away; the file stays.
  3. Friday: Sam says "book the laser cutter". The program loads Sam's 60-token note into the new context.
  4. The model sees "trained", skips the training question and calls the booking tool.

Anthropic's memory tool works this way: the model reads and writes files in a memory folder, and your own code does the storing ([context management announcement](https://www.anthropic.com/news/context-management)). Replaying ten old chats of 2,000 tokens would cost 20,000 tokens every visit; the note costs 60.

A common mix-up

"A bigger window is memory." A big window only holds one session's text. Once the session ends, it's empty again, so only saved notes carry over.

Finding the right page 3 min

Your manuals are far too long to put in the context every time. So the assistant looks up only the part it needs, when it needs it.

That's retrieval: a search tool (like search_manuals) returns a few small chunks, and only those enter the context. The manuals are stored outside, the same way notes are ([Anthropic on context engineering](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Worked example

The laser cutter manual is about 100,000 tokens. A student asks, "What's the focus distance for 3 mm acrylic?"

  1. Paste-everything: 100,000 tokens in the context, on every call of the loop.
  2. Retrieval: the model calls search_manuals("laser focus distance acrylic"). The program returns the 3 best chunks of 500 tokens each: 1,500 tokens.
  3. The model reads the chunks, finds "focus 6 mm above the surface", and answers.
  4. Saving: 100,000 / 1,500 is about 67 times fewer tokens on that call.

The catch: if the search returns the wrong chunks, the model answers from them anyway. So the quality of your search is part of your design.

Your turn

The 3D printer manual is 60,000 tokens. Retrieval returns 4 chunks of 400 tokens. Step 1 is done for you: retrieval costs 4 × 400 = 1,600 tokens. How many times fewer tokens is that than pasting the manual? And what could go wrong?

Show a solution

60,000 / 1,600 = 37.5, so about 37 times fewer. The risk: the search returns the wrong chunks, and the model confidently answers from them.

Summary 1 min

  • The model sees only the context, and the program re-sends all of it every call.
  • The context window caps one call's size; you pay for every token, every call.
  • Notes carry facts between sessions; the window does not.
  • Retrieval pulls small chunks of a long manual in only when needed.

Say it in your own words: for Sam's return visit, what do you load into the context, and what do you leave outside?
