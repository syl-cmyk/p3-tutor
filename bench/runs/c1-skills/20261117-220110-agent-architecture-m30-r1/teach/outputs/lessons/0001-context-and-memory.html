Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a manual it looks up on demand.

Objective O3: context and memory in an agent About 30 minutes Builds on your agent-loop work (quiz 0001)
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training between visits. Those are two different memory problems, and each choice changes the cost of every request, which is what your sponsor's budget pays for.

Warm-up (2 min): recall

Without scrolling up: in the agent loop, who actually runs a tool, the model or the program around it? And what happens to the result next?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then puts the result in front of the model and calls it again. That "puts the result in front of the model" step is exactly what today is about: where does that result live, and for how long?

The context window, and what it keeps between steps 9 min

The model has no memory of its own between calls. Whatever it knows at a step is whatever the program sent it in that one call.

Here's what that looks like for one request. A student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The agent makes four model calls. Here is what the program sends each time (the token counts are made-up but realistic round numbers):

Call 1 sends: system prompt + tool definitions (1,500) + question (30)
              = 1,530 tokens
              model replies: "call check_calendar(laser, tomorrow)"

Call 2 sends: everything from call 1 + the request (50) + calendar result (400)
              = 1,980 tokens
              model replies: "call search_manuals('laser cutter training')"

Call 3 sends: everything from call 2 + the request (50) + 3 manual pages (2,400)
              = 4,430 tokens
              model replies: "call check_training_record(student)"

Call 4 sends: everything from call 3 + the request (50) + training record (150)
              = 4,630 tokens
              model replies: the final answer to the student

Now the idea. The context window is everything the model can see in one call: your system prompt, the tool definitions, every message so far, every tool result, and the reply it's writing. The Claude docs list exactly this, and note it works like the model's "working memory" (Claude docs: context windows). Tokens are the chunks of text it's measured in, and the window has a maximum size in tokens.

Add up what was actually sent: 1,530 + 1,980 + 4,430 + 4,630 = 12,570 input tokens for one question. The final context was only 4,630. You pay for every call, so cost grows faster than the context does.

A common mix-up

"Each step only sends the new result, so a long task costs about as much as its final context." It's tempting because the loop feels like a conversation where you only say the new thing. But the model only sees what's in the call, so the program must resend everything. In the trace, the calls sum to 12,570 tokens, nearly three times the final 4,630.

There's a second cost, and it isn't money. As the window fills, the model gets worse at using it: recall and accuracy degrade, which is called context rot. The authors of Anthropic's context-engineering post say you want "the smallest set of high-signal tokens" that gets the job done (Anthropic: effective context engineering). So a bigger window doesn't mean you should fill it.

Prompt caching can make the repeated part cheaper, but cached tokens still sit in the window and still count toward its limit (docs). Cheaper is not the same as free or gone.

So what do you do when a task runs long? Two simple moves from the same post. First, clear old tool results you can re-fetch, like a calendar lookup from ten steps ago. Second, compaction: when the context nears its limit, summarize it and start a fresh window from the summary.

Check yourself

In the trace above, call 3 sends three manual pages (2,400 tokens). Which statement about call 4 is true?

Show the answer

The third option. The program resends the whole history every call, so the pages are billed again. Clearing them would be a choice you make.

What survives between sessions: notes 7 min

When a session ends, the context window is gone. A new chat starts with an empty window, so anything the assistant should remember next week has to be saved somewhere else and loaded back in.

Here's a student's two visits. Without any saved memory:

  1. Monday, student: "I just finished laser cutter training." The assistant answers, and the session ends. The window is discarded.
  2. Wednesday, new session, student: "Can I book the laser cutter for Friday?" The window holds your system prompt, the tools and this question. Nothing else.
  3. The assistant has no idea about Monday. It either asks again or calls the training tool, if you built one.

The fix is notes: information the program writes to storage outside the context window (a file or database row) and reads back later. Anthropic's post calls this structured note-taking: the agent keeps notes like a to-do list and pulls them back into the window when needed (source). Anthropic's memory tool works this way too: Claude asks to create, read or change files in a /memories folder, and your code does the actual reading and writing (memory tool docs).

Now the same two visits with notes. This is what the program and model do on Wednesday:

  1. Student: "Can I book the laser cutter for Friday?"
  2. The program starts a new window and loads the student's note: laser_cutter_training: done 2026-11-09.
  3. The model sees the note and the question, and requests check_calendar(laser, Friday).
  4. The result comes back: free at 2 pm. The model replies and offers to book it.
A common mix-up

"The assistant remembers earlier chats on its own." It's tempting because chat apps feel that way: they save and reload history for you. A model called from code remembers nothing; in the Wednesday trace without notes, it truly knew nothing about Monday.

Notes cost tokens too, so save less than you think. Keep the facts that change what the assistant does next (training status, a student's usual machine) and leave out the chat itself. A note you wrote in one line is cheaper to reload than a 3,000-token transcript.

Finding the right page: retrieval 8 min

Notes remember things about students, but manuals are too long to paste into every call. So the assistant keeps the manuals outside the window and fetches only the few pieces a question needs. That's retrieval.

Here's one question with numbers. Say the laser cutter manual is about 60,000 tokens. Someone has split it into chunks of about 300 tokens each, so there are 200 chunks. The student asks, "What's the maximum material thickness for the laser cutter?"

  1. The program searches the 200 chunks for the ones that best match the question.
  2. It picks the top 5 chunks: 5 × 300 = 1,500 tokens.
  3. Those 1,500 tokens go into the window, not the 60,000.
  4. The model reads them and answers: "Up to 12 mm for acrylic, per the specs table."

How does the search decide what matches? Two common ways, which Anthropic describes in its contextual retrieval post (source). Embeddings turn each chunk into a list of numbers that captures its meaning, and the search finds chunks closest in meaning to the question. BM25 matches exact words and phrases, so it's good at things like an error code.

Each one misses things the other catches. Say the laser cutter shows "Error E-47" and a student searches that. Meaning-based search can return pages about errors in general, while BM25 finds the exact page that contains "E-47". The same post says to run both and merge the results, and that this hybrid cut the share of relevant chunks missed from 5.7% to 2.9% in their tests (with extra context added to each chunk, which is the post's own technique).

The same post says that if your whole knowledge base is under about 200,000 tokens (roughly 500 pages), you may be able to just put it all in the prompt and cache it. A single manual might be small enough; all your machines together might not be. Check the numbers before you build retrieval.
A common mix-up

"A bigger context window means retrieval isn't needed." It's tempting because 1M tokens sounds like it fits everything. But context rot means answers can get worse as it fills, and you pay for every token on every call: 60,000 tokens resent over 4 calls is 240,000 tokens, against 1,500 per call when you retrieve.

Retrieval can also be a tool the model calls, like search_manuals in your loop. That makes it just-in-time: the agent keeps lightweight pointers (file names, queries) and loads the content only when it needs it, instead of loading everything up front (source).

Worked example and practice 5 min

Time to use all three together: decide where each piece of information lives. Here's one worked decision, then you do the rest.

Worked example

Information: "The 3D printer's nozzle-cleaning steps, 4 pages." Where does it live?

  1. Is it about this student and needed next visit? No, it's about the machine. So not notes.
  2. Is it needed on every call? No, only when someone asks about nozzles. So not always in the window.
  3. Is it long and looked up by topic? Yes. So it goes in the manual store, retrieved on demand.
  4. Result: retrieval. It enters the window only when a student asks about nozzles, as a few chunks.

  2. "This student prefers morning slots and always books the vinyl cutter."
  3. The result of check_calendar from ten steps ago in a very long session.
Show a solution

1: context, always, as the system prompt, because the model needs it on every call. 2: notes, since it's about this student and useful next visit. 3: clear it from the context, because it can be re-fetched if needed and it's just taking space.

Now put numbers on your budget. Your design review will ask what each design costs per request, so here's one comparison using the same four-call request as before.

Worked example: two designs, same question

Design A pastes the whole 60,000-token laser cutter manual into the system prompt. Design B retrieves the best 5 chunks (1,500 tokens) only when a manual question comes up, which is at call 3 of the trace.

  1. Start from the earlier trace: 1,530 + 1,980 + 4,430 + 4,630 = 12,570 input tokens. That already includes the 2,400 tokens of manual pages added at call 3.
  2. Design A adds 60,000 tokens to every one of the 4 calls: 4 × 60,000 = 240,000 extra, and drops the retrieved pages (2,400 × 2 calls that carried them = 4,800 saved). Total: 12,570 + 240,000 − 4,800 = 247,770 input tokens.
  3. Design B keeps the 12,570 as is. Real numbers will differ, but the shape holds: B is about 20 times cheaper on input.
  4. Design A also puts 60,000 tokens of mostly irrelevant text in front of the model on every call, which is exactly the setup for context rot.
  5. So for your budget: retrieve, and keep the system prompt short.
Your turn

Design C keeps no notes: at the start of every session it asks the training tool for the student's record, a 150-token result, and the model's request to call it adds 50 tokens. Design D stores that record as a one-line note of 30 tokens, loaded at the start of every session. The first step is the same arithmetic as above: how many tokens does each design add to the window, and does the saving matter for the budget?

Show a solution

C adds 50 + 150 = 200 tokens; D adds 30. The difference is 170 tokens per session, tiny next to the 1,500-token manual chunks. So here, notes don't save much money. The real reason to keep a note is that it can hold things no tool returns (a student's usual slot, say). Save money by retrieving, not by trimming notes.

One more design choice: what happens in a session that runs very long? Say the context reaches 90% of the window. The program summarizes it (compaction), starts a new window with the summary, and keeps going. Facts that must survive that summary, such as a booking the student just confirmed, belong in notes too, so the summary can't lose them. The memory tool docs suggest using both together for long-running agents (memory tool docs).

Summary 1 min

  • The model sees only what's in the context window for one call, and the program resends the whole history every step.
  • Cost grows with every step, and a fuller window can also make answers worse. Keep it small.
  • Between sessions only what you save survives. Notes hold small facts about students, loaded when needed.
  • Retrieval keeps long manuals outside the window and brings in only the best-matching chunks; combine meaning search with keyword search.

Say it in your own words: a student asks about the laser cutter's thickness limit. Out loud, say what is in the window, what comes from notes, and what comes from retrieval.
