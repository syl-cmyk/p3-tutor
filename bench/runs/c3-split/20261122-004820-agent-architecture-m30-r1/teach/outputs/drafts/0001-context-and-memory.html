Context window and agent memory: what the model sees now, what it keeps, and how it finds the rest

By the end of this lesson you can decide, for an agent, what belongs in the context window on each call, what should be saved as notes between sessions, and what should be fetched from a large document only when needed.

Why this matters for you

Your makerspace assistant has to answer from long machine manuals and remember each student's training between visits. Your sponsor's budget is spent per token, so these choices decide what each request costs, and you will have to defend them at your design review.

Warm-up

Context is the text the model is handed on one call. Memory is whatever the program saves outside that text so a later call or session can use it.

Information can live in three places: the window the model reads on each call, notes saved between sessions, and a long document you search. We take them one at a time, and in Part 6 you sort real items into them.

Recall

In the agent loop, who runs the tool, and is each step a separate model call?

Check your answer

Your program runs the tool; the model only asks for it. And yes, every step is a separate model call. That second fact is today's starting point: if every call is separate, what the model sees on each call is something you design.

Part 1. Context window: everything the model can see on one call

The model only knows what is written in the text it is handed on this call, so the first design question is what that text contains. Once you see what fills it, you can see why it costs money and why it has a limit.

Text is measured in tokens. A token is a chunk of text the model reads or writes, often a short word or a piece of a longer one. You pay per token going in and per token coming out.

The context window is all the text the model can reference while it answers, including the reply it is writing, and it is different from what the model learned in training (Claude docs: context windows). Its size is capped: the window can hold at most a set number of tokens in one call, input plus output.

Current Claude models have windows of up to 1M tokens, depending on the model (same page). So the limit is rarely your first problem. Cost and quality are, and Part 3 shows why.

Worked example: one call from the makerspace assistant

The token counts here are invented round numbers for teaching, not measurements. The student writes: "Is the laser cutter free Friday?"

  1. System prompt (the assistant's instructions): say 400 tokens.
  2. Tool definitions (calendar lookup and booking): say 600 tokens.
  3. The student's message: say 20 tokens.
  4. Input total: 400 + 600 + 20 = 1,020 tokens.
  5. The model writes a reply of, say, 60 tokens: a request to call the calendar tool.
  6. The reply counts toward the window too, so this call uses 1,020 + 60 = 1,080 tokens.
  7. Cost: you pay for tokens in and out, so what you put in is what you pay for.

Everything in the request counts: the system prompt, every message including tool results, and the tool definitions (docs).

A common mix-up

"The context window is the model's whole knowledge." It is tempting because the model seems to know so much. But it can state Friday's laser cutter slot only if the calendar result is in the window. With no result there, it can only guess, like the confident outdated fact you have seen from a chatbot. What it learned in training is separate from the window.

Part 2. Message history: what is kept between steps of one task

The model keeps nothing from one call to the next, so the program has to send the whole story again on every step. That is why a long task costs more than its length suggests.

The message history is the list of everything said and returned so far in this task. Your program holds it in a list and re-sends it each call. Previous turns are preserved completely, and each output becomes part of the input for the next turn (docs).

Worked example: three calls for one booking

The student says: "Book the laser cutter Friday at 2." Same invented numbers as Part 1.

  1. Call 1 input: 1,020 tokens (instructions, tools, question). The model asks for the calendar lookup: 60 tokens out.
  2. The program runs the calendar lookup. A 300-token result comes back.
  3. Call 2 input: 1,020 + 60 + 300 = 1,380. The model asks to book: 70 tokens out.
  4. The program runs the booking. The result is 40 tokens.
  5. Call 3 input: 1,380 + 70 + 40 = 1,490. The model writes the final reply, 90 tokens: "Booked, Friday 2 pm."
  6. Input tokens billed across the three calls: 1,020 + 1,380 + 1,490 = 3,890. Yet beyond the 1,000 tokens of instructions and tools, only 490 tokens of new input appeared: 20 + 60 + 300 + 70 + 40 (580 if you count the final 90-token reply).
A common mix-up

"The model remembers the earlier step on its own." It feels that way in a chat. But if the program sent call 3 with only the 40-token booking result, the model would not know which machine or time was asked. It needs the 1,380 tokens before it, because each call is a separate model call and the program holds the history.

A common mix-up

"A longer task costs a bit more, in a straight line." Look at the inputs: 1,020, 1,380, 1,490. Say a ten-step task starts at 1,020 and grows 300 tokens a step: the inputs run 1,020, 1,320 and so on up to 3,720, which add to 23,700. A straight-line guess of ten calls at 1,020 would say 10,200. Every step re-pays for all the steps before it.

Part 3. Context rot and clearing: keep the window small and useful

A bigger window is not a reason to fill it (a small manual can still be worth pasting in whole; Part 5 weighs that), because the model gets worse at using a crowded context and every token costs. So the agent should drop what it no longer needs.

As token count grows, accuracy and recall degrade, a problem called context rot (docs). It is a gradual decline rather than a hard cliff (Anthropic Engineering). The aim is the smallest set of high-signal tokens that makes the result likely (same post).

Worked example: clearing old tool results

The assistant has done many steps, and its history is, say, 40,000 tokens. Six old calendar results of, say, 2,000 tokens each (12,000 in total) are not needed for the current question.

  1. Spot the old tool results the model has already acted on.
  2. Replace each with a 20-token placeholder such as "calendar result for Tuesday, cleared". Six placeholders are 120 tokens, so 12,000 becomes 120.
  3. History drops from 40,000 to 40,000 - 12,000 + 120 = 28,120.
  4. The next call is cheaper, and the model has less clutter to wade through.
  5. If the history is still near the limit, use compaction: the model writes a summary of the conversation, and a new window starts from that summary (Anthropic Engineering).

That trace used two of three tools. Here they are side by side; the third is set up for Part 5.

Both are options for agents (docs). Compaction built into the API is still in beta and only on newer models, so check before the team relies on it.

A common mix-up

"A 1M-token window means I can paste everything in." It is tempting because it fits. But say you paste a 90,000-token manual on every call of the three-call task: that bills about 3 x 90,000 = 270,000 input tokens. A 900-token excerpt does the same job, and the model has to find one line among 90,000 tokens.

A common mix-up

"Summarizing loses nothing." A summary that drops "student is not trained on the laser cutter" makes the assistant book them anyway. Compaction should keep decisions and unresolved items and drop repeated tool output. Anything that must survive should also be saved as a note, which is Part 4.

Part 4. Memory: notes the agent saves for the next session

When a session ends, the window is gone, so anything that must last has to be written somewhere outside it. The simplest approach is a notes file the agent reads at the start and updates as it goes.

This is called structured note-taking: the agent regularly writes notes that persist outside the context window (Anthropic Engineering). Claude's memory tool does it with files under /memories (memory tool docs).

Worked example: remembering a student's training
  1. Session 1, student Sam says: "I finished the laser cutter safety training today." The assistant has a memory tool that works on files under /memories.
  2. The model asks to view /memories. The program, not the model, runs it and returns an empty listing.
  3. The model asks to create /memories/students/sam.md with "Laser cutter: trained 2026-11-21. 3D printer: not trained." The program writes the file and returns "File created successfully at: /memories/students/sam.md".
  4. The session ends. The window, history and all, is thrown away. The file stays on the program's disk.
  5. Session 2, a week later, the student says: "Book the laser cutter Friday." It is a new window with an empty history.
  6. The model views /memories, then views sam.md. The file, say 15 tokens, comes back as a tool result and is now in the window.
  7. The model sees the training is recorded, calls the calendar tool, books, and replies.
  8. Cost: 15 tokens of notes, instead of re-asking the student or re-reading a whole old conversation.

Memory here is not magic inside the model. It is a file the program stores and the model reads through a tool call, so it travels into the window as ordinary text.

The model only asks for file operations, and your application runs them against storage you control (docs). So your team decides where notes live and how long they are kept. The model is also told to view its memory first and to assume its window might be reset at any moment, so it records progress as it goes (same page).

A common mix-up

"The assistant will remember Sam next week because it talked to Sam." It feels natural, as with a person. But with no notes file, session 2 starts with an empty window, and the assistant must ask whether Sam is trained, or wrongly book.

A common mix-up

"Save everything the student says." Saving a 3,000-token transcript means session 2 loads 3,000 tokens to learn one fact, when a 15-token line holds it. Keep notes small, organized and updated. The docs suggest capping file sizes and deleting files nobody has opened in a long time. For stronger guarantees about sensitive data, add validation, and check paths so a note cannot be written outside /memories (docs).

Part 5. Retrieval: finding the right page in a long manual

Some knowledge is too long to carry in the window every call, so the agent keeps the manual outside and pulls in only the few pieces that answer the question. This is the third place information can live, next to the window and the notes.

Worked example: the laser cutter manual

The numbers are invented for teaching. Say the manual is 120 pages, about 90,000 tokens.

  1. Prepare once: split the manual into chunks of about 300 tokens, which gives 300 chunks, and build a search index over them. Chunks are usually no more than a few hundred tokens (Anthropic: contextual retrieval).
  2. The student asks: "Can I cut PVC on the laser cutter?"
  3. The model calls a search-manual tool with the query "laser cutter PVC".
  4. The program searches the index and returns the top 3 chunks, 900 tokens in total, including the chunk that says PVC releases toxic fumes and must never be cut.
  5. The model answers with a warning and cites the page.
  6. Compare: 900 tokens in the window instead of 90,000, so the input for that call is a hundred times smaller.
  7. Second case: the student asks about "error E-42". A search by meaning can miss an exact code, while a keyword search (BM25) finds the exact string. Combining both kinds of search covers both cases (source).
  8. Just-in-time version: keep only a lightweight pointer in the window, such as a page index with titles, and let the model load the page it picks (Anthropic Engineering). The trade-off is that it is slower than pre-computed data, and the agent needs good guidance or it wastes context on dead ends (same post).

One more idea from the same post: before indexing, add a short, chunk-specific note (about 50 to 100 tokens) explaining where the chunk sits in the document. Combined with keyword search, that cut the top-20-chunk retrieval failure rate from 5.7% to 2.9% in their tests (source).

And an honest rule: if your knowledge base is under about 200,000 tokens (roughly 500 pages), the post says you can put it all in the prompt, and prompt caching, which changes what you pay per token, makes that cheaper (source). Beyond that, retrieve. Our 90,000-token manual is under that line, so for it both options are valid and a cost comparison decides. Part 6 retrieves it to show the skill, since your full set of manuals will likely be bigger.

A common mix-up

"Retrieval always finds the right page." The student types "E-42", a meaning-based search returns general error-handling chunks, and the one chunk with E-42 is missed. In the post's tests, plain embedding search missed the right chunk in its top 20 results 5.7% of the time, so retrieval can miss. Your assistant should say plainly when nothing relevant came back.

A common mix-up

"If the window is big enough, retrieval is pointless." Our 90,000-token manual fits in a 1M window, and it is also under the 200,000-token line, so putting it all in is a real option to price. But sent on each of Part 2's three calls it is 270,000 input tokens against 2,700 with retrieval. And the model reads a crowded context (Part 3).

Part 6. Choosing what goes where: window, notes or retrieval

Now you have three places for information, and each fact belongs in one of them depending on how often it is needed and how long it must last. Deciding this is the design skill your mission asks for.

Worked example: "Book the laser cutter Friday at 2"
  1. The assistant's instructions and tool descriptions: always in the window, since they are needed on every call.
  2. This student's training status: a note, loaded at the start of the session. It is needed every visit, it is tiny, and it must outlast the session.
  3. The laser cutter manual: retrieval, because it is large and only a little is needed.
  4. Friday's calendar: a tool result, kept in history until used, then cleared. It is needed now and stale soon.
  5. Final check: on the last call, say about 1,500 tokens of instructions, tools and history, plus about 900 tokens of retrieved manual chunks, so roughly 2,400 in the window instead of about 91,500 with the manual pasted in.

A common mix-up

"Memory and retrieval are the same thing." Compare: Sam's 15-token note is written and updated by the assistant, while the 300 manual chunks were written by the manufacturer and the assistant never edits them. This is the lesson's own distinction: memory is written by the agent, retrieval reads a fixed collection.

Summary

  • The model sees only the window: instructions, tools, history, results and its own reply.
  • Between steps, the program re-sends the whole history, so cost and clutter grow; clear or summarize what is no longer needed.
  • Between sessions, only what was written to notes survives; the model reads it back as ordinary text.
  • For long documents, retrieve a few relevant pieces instead of loading everything, and plan for misses.
  • Place each fact by how often it is needed, how long it must last and how big it is.
