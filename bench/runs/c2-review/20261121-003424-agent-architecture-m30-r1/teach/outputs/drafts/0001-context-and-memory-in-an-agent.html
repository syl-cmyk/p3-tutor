Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a searchable manual.

Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training between visits, all on a small budget. Those are three separate memory jobs, and this lesson gives you a way to pick the right home for each one before your design review.

Warm-up, and what the model sees 8 min

The model only sees what's sent to it on each call, so memory in an agent is really about what you choose to send. First, a quick look back at the loop you already know.

Recall

The assistant gets the question "Is the laser cutter free tomorrow at 3 pm?". The model asks for check_calendar. Who actually runs that tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. It then puts the result back in front of the model and calls the model again. That second call is the part that matters today: the model has to be handed everything again.

Here's the surprising part: between two model calls, the model keeps nothing. It doesn't remember the last call, so the program sends the whole story again every time.

Let's watch one request. The numbers are made up but realistic in shape, and I'm counting in tokens, the small chunks of text a model reads and writes (a token is often a short word or a piece of one).

Example: one request, step by step

The student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" Here is what the program sends to the model on each call.

  1. Call 1. Sent: instructions (1,500 tokens) + tool descriptions (1,000) + the question (50) = 2,550 tokens. The model replies with a request for check_calendar (60 tokens).
  2. Call 2. Sent: everything from call 1, plus the model's request, plus the calendar result (400) = 3,010 tokens. The model asks for search_manuals (60).
  3. Call 3. Sent: everything so far, plus that request, plus a manual page (3,000) = 6,070 tokens. The model asks for check_training_record (60).
  4. Call 4. Sent: everything so far, plus the request, plus the training record (200) = 6,330 tokens. The model writes the final answer (150).

Add up what was sent: 2,550 + 3,010 + 6,070 + 6,330 = 17,960 tokens for one question, even though the new facts were only about 3,650 tokens (not counting the fixed instructions and tool descriptions). The manual page was sent twice, in calls 3 and 4, so it cost 6,000 of that total.

That pile of text the model reads on each call is its context. The most it can read in one call is its context window, measured in tokens, and it has to hold the instructions, the tool descriptions, the whole conversation so far, and the room for the answer.

The window works like the model's "working memory", and it grows turn by turn as inputs and outputs pile up (Claude docs: context windows).

How big is it? It depends on the model: the docs list some current models with a window of 1 million tokens (same page). Whatever the size, it's a hard ceiling. In our trace the context reached 6,330 tokens, so if your window were only 6,000 tokens, call 3 (6,070 tokens) couldn't even be made and you'd have to trim first.

Think of it like a desk. Everything the model can use has to be laid out on the desk for this one call, the desk has a fixed size, and the program clears it and lays it all out again before the next call.

Three things follow from this, and they drive the rest of the lesson. Cost grows with the size of what you send, the window is a hard ceiling, and quality can slip when the context gets long.

On that last one: the more tokens in the window, the worse the model gets at recalling any one fact in it, an effect called context rot (Anthropic: effective context engineering). Researchers also found that models use facts near the start or end of a long input better than facts in the middle (Liu et al., Lost in the Middle).

A common mix-up

"The model remembers our earlier chat, like a person would." It's tempting because chatbots feel like they do. But the model keeps nothing between calls: what feels like memory is the program re-sending the earlier text. Close the program and the "memory" is gone, unless something saved it.

Picture it: on Monday a student books the laser cutter. On Wednesday they open a new chat and ask "what did I book last time?" The new context holds only instructions, tools and that question, so the model has nothing to answer from.

What is kept between steps 6 min

Within one request, everything stays in the context, which is both the good news and the problem. Good, because the model can use any earlier result. Problem, because the pile only grows.

So you have a job as the designer: curate what stays. Aim for the smallest set of high-signal tokens that still gets the result you want (Anthropic: effective context engineering).

Let's see why with a longer request. A student asks for the table saw's safety rules, and the assistant searches the manuals three times before it finds them.

Example: a request that keeps searching
  1. Step 1. The model calls search_manuals("table saw safety"). Back come 3,000 tokens of the wrong chapter (about the saw's motor).
  2. Step 2. It searches again with different words. Another 3,000 tokens arrive, about blade changes.
  3. Step 3. A third search returns the right 3,000 tokens: the safety rules.
  4. Step 4. The model answers. By now the context holds 9,000 tokens of manual text, and 6,000 of them are useless.

Those two wrong chapters are sent again on every remaining call, and they also crowd the right page and add noise for the model to read through.

Here is the money side, with a pretend price so the arithmetic is easy: say every 1,000 tokens you send costs 0.3 cents. Your real price depends on the model you choose, so check it before you quote a number at the review.

  1. The first wrong chapter arrives at step 1 and is re-sent on calls 2, 3 and 4: 3,000 × 3 = 9,000 tokens. The second arrives at step 2 and is re-sent on calls 3 and 4: 3,000 × 2 = 6,000. That's 15,000 wasted tokens.
  2. 15,000 tokens is 15 thousands, and 15 × 0.3 cents = 4.5 cents.
  3. Per request that looks tiny. At 1,000 requests a term, though, it's 4,500 cents, which is 45 dollars spent on text nobody needed.

One more thing that changes the bill: the API can cache a repeated prefix, such as your instructions, and charge less for re-sent tokens (see the prompt caching docs). So your real numbers will be lower than the pretend ones, but the habit of sending less still pays.

That's the reason cost per request is a design choice and not an afterthought: every habit that adds tokens gets multiplied by every call and every request.

There are three simple ways to keep this under control. You can pick them separately or combine them.

  1. Keep tool results small. Return the best two paragraphs, not the whole chapter.
  2. Clear old tool results. Once the model has used a result, drop it and leave a note that the call happened. The Claude API has a feature for this, called context editing, which removes stale tool calls and results as the agent nears its limit (Anthropic: managing context). Clearing is safest for results you can fetch again, such as a manual page.
  3. Stop and start over with a summary. When a very long task fills the window, summarize it and continue in a fresh window. For example, a 40,000-token booking conversation becomes a 300-token summary: "Student wants the laser cutter in the afternoon; Monday is full; Tuesday 2 pm offered, awaiting yes or no." The new window starts with those 300 tokens.

Option 2 only works for results you can get again, such as a manual page. A calendar answer that was true at 2 pm might not be true at 4 pm, so decide on purpose before clearing anything.

A common mix-up

"A bigger window means I can stop worrying about this." It's tempting because bigger sounds safer. But a bigger window doesn't change the two costs above: you still pay for the 17,960 tokens in our trace however big the window is, and recall can still get worse as the context grows (see the context rot source earlier).

What is kept between sessions 6 min

When the student closes the chat, the context is gone. The next visit starts with an empty window, so anything the assistant should remember has to be saved outside the model, as a note, and read back in.

The Claude API's memory tool works this way: the model stores and reads information outside the context window through a file-based system, and your own program handles the storage (Anthropic: managing context). From the model's side it's just more tools, so you already know the pattern.

Example: remembering a student's training

Visit 1 is on October 2. Visit 2 is two weeks later, in a brand new session.

  1. Visit 1. A student, Priya, finishes the laser cutter training. The model calls write_note("students/priya.md", "Laser cutter: trained 2026-10-02. Table saw: not yet."). The program saves a file.
  2. Session ends. The context is thrown away. The file stays on disk.
  3. Visit 2. Priya asks: "Can I book the table saw?" The program starts a fresh context with just instructions, tools and her question.
  4. Reading the note. The model calls read_note("students/priya.md") and gets back the one-line note.
  5. Reply. "Not yet: you haven't done the table saw training. Want me to look up the next session?"

The note cost about 25 tokens to read. Carrying a whole old conversation instead would cost thousands.

The hard question is what deserves a note. A useful test: save it if it stays true for a long time and would be annoying to work out again.

Let's see the same table at work on a second student. Dev says: "Book the laser cutter for tomorrow at 3." Here's how each row plays out.

  1. The assistant reads students/dev.md. It says "Laser cutter: trained 2026-09-14", so Dev is allowed.
  2. It calls check_calendar for tomorrow. 3 pm is taken, but 4 pm is free.
  3. It replies with the 4 pm option. The student says yes, and the assistant calls the booking tool.
  4. Dev mentions "I always prefer afternoons". It writes one line to Dev's note: "Prefers afternoons (2026-11-20)." The chat itself is then discarded.

Notice what never went into a note: the calendar's contents, the booking itself and the manual text. Only a stable, small, dated fact was saved.

Notes can also go wrong, so build in two guards. First, store dates with the facts so the assistant can see how old a note is. Second, treat a note as a hint and check the real source for anything important, such as booking only after the training record confirms it.

Notes about named students are personal data. Save the minimum the assistant needs, and ask your makerspace staff what the university allows.

Retrieval: finding the right page 6 min

Some knowledge is too big to put in the context at all, like all your machine manuals. For that, the trick is to leave it outside and fetch only the few pieces that matter for this question.

Say the manuals together come to 70 pages of about 3,000 tokens each, so 210,000 tokens. That's far more than you want to send on every call, and you'd pay for it each time (and, as the lost-in-the-middle research suggests, the model uses buried facts less reliably).

Here's the shape of it, with real text. This is the whole exchange for one search:

model asks:   search_manuals("laser cutter maximum acrylic thickness")
program runs: compares the query with every stored piece of manual
tool returns: "Laser cutter. Acrylic up to 10 mm may be cut at power 80%."

That's retrieval. You split the manuals into chunks ahead of time, say a few paragraphs each, and search the chunks for the ones closest to the question. Your search_manuals tool is exactly this.

Example: one search over three chunks

The student asks: "What's the thickest acrylic I can cut on the laser cutter?" The model calls search_manuals("laser cutter maximum acrylic thickness"). The search compares the query with each chunk:

  1. Chunk 41: "Laser cutter. Acrylic up to 10 mm may be cut at power 80%." It shares the words laser, cutter, acrylic.
  2. Chunk 87: "Band saw. Acrylic is not permitted on this machine." It shares only the word acrylic.
  3. Chunk 12: "Lunch hours at the makerspace are 12 to 1." It shares nothing.
  4. The search returns the top result, chunk 41, about 40 tokens. The model answers: "Up to 10 mm, at 80% power."

Only 40 tokens went in, instead of 210,000. Real systems compare meaning as well as words, using embeddings, which turn a piece of text into a list of numbers so that texts about similar things land close together. The idea is the same: score every chunk, return the best few.

Three design choices shape how well this works for your manuals. Each one trades cost against the chance of finding the right page.

  1. Chunk size. Tiny chunks lose their surroundings, and huge ones bring back lots of text you don't need. A few paragraphs, about one section of a manual, is a sensible start to test.
  2. How many chunks to return. Each extra chunk costs tokens on every later call, so start with two or three and look at what the assistant actually needs.
  3. Words, meaning, or both. Word matching (a standard keyword-ranking method called BM25) is good for exact things like error codes such as "E-204". Embeddings are good for questions phrased differently from the manual. Anthropic's contextual retrieval post combines both for this reason.

Two quick cases show why both help. A student types "E-204" and the manual has a line "Error E-204: lens not detected." Word matching finds it at once, while a meaning-based search might not know what E-204 is. Another student types "my cut won't go all the way through" and the manual says "Insufficient power causes incomplete cuts." There are no shared words, so only the meaning-based search finds it.

One catch is that a chunk can lose where it came from. A chunk that says "the company's revenue grew by 3% over the previous quarter" names no company or date, so nothing links it to the question (Anthropic: contextual retrieval).

Your manuals have the same problem: a chunk that says "Maximum thickness is 10 mm" doesn't say which machine. The fix is to have a model write a short line of context for each chunk, such as "From the laser cutter manual, materials section", and attach it to the chunk before indexing. They report that this cut failed retrievals by 35% on its own, and by 49% when combined with BM25 keyword matching, measured on their test sets (same source).

A common mix-up

"Retrieval means the model looks things up in its own memory." It's tempting because the model does seem to know things. But retrieval is a tool call to a search program: the model asks, your program searches the chunks, and the text comes back into the context like any other tool result.

That also tells you how to tune retrieval for cost: return few chunks. Research found that going from 20 retrieved documents to 50 improved answers by only about 1 to 1.5 percentage points on the models tested (Liu et al.), while it more than doubled the tokens sent.

Put it together 4 min

You now have three homes for information: the current context, a saved note, and a searchable manual. Let's use them together on a fresh request and then on your own.

Quick recap, one fact each: "Priya's training date" is a saved note, "the manual's thickness limit" is retrieved, and "what the student just asked" is in the context.

Worked example: sorting four facts

A returning student, Marco, writes: "Book me the 3D printer on Friday for the thing I printed last time." For each fact the assistant needs, pick a home.

  1. "Marco finished 3D printer training." It's stable and personal, so it lives in a saved note and is read at the start of the visit.
  2. "Friday afternoon is free on the printer." It changes constantly, so it comes from check_calendar, fresh, into the current context.
  3. "This filament needs a 215 degree nozzle." It's in the manual, so it's retrieved on demand with search_manuals, and the result can be cleared afterwards.
  4. "Marco asked for Friday." It only matters now, so it stays in the current context and is dropped at the end.

Summary
  • The model keeps nothing between calls: the program re-sends the whole context every time, so cost and the window limit both grow with it.
  • Between steps, keep the context small by trimming tool results, clearing old ones that can be re-fetched, and summarizing very long tasks.
  • Between sessions, memory is a saved note that the model reads back with a tool, so save only stable facts, with dates.
  • For big documents, use retrieval: chunk them ahead of time, search per question, and give each chunk its source.

Say it in your own words: without looking up, explain to a teammate why the assistant needs three different places to keep information, and give one example fact for each.

Why this matters in the real world: each token you send is paid for again on every call, so these choices decide your model bill. At your design review, "what stays in context, what is saved, what is retrieved" is the question to have a reasoned answer for.
