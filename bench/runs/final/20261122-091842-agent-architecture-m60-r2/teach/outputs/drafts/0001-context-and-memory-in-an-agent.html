Lesson 1 · 60 minutes

Context engineering: what an agent sees, what it keeps, and what it looks up

By the end of this lesson you can take any agent, list what is in its context window on each model call, and decide what to keep there, what to clear, what to fetch only when needed, and what to save as notes for later sessions.

Objective O3: context and memory in an agent About 60 minutes Builds on your notes from the first two sessions: the language model, and the agent loop
Why this matters for you

Your makerspace assistant has to answer from long machine manuals, check a calendar and remember each student's training status between visits, all on a small budget. Each of those is a decision about what goes in front of the model.

This lesson ends with a table you can defend at the design review: for every thing the assistant needs, where it lives and what that costs per request.

1. Context window: what the model can see on one call 10 min

The model only knows what is in the text it is handed on this one call, so everything it could use has to fit in there. That limit, and what counts toward it, is where context and memory both start.

A heads-up on numbers: every token count and every dollar figure in this lesson is made up, but realistic, so the arithmetic is easy to follow. The real counts come from the token counting tool, and you should look up the real price before the design review. The examples use Anthropic's Claude documentation as one concrete case of ideas that hold for any model.

Warm-up

Two quick recall questions from your first two sessions. Answer in your head, then open the answer.

Recall 1

In the agent loop, who actually runs the tool: the model or your program?

Check your answer

Your program. The model only writes a request, like "run check_calendar for Friday", and your code runs it and sends the result back. That closes the loose end from the loop session.

Recall 2

Where does a chatbot's knowledge stop?

Check your answer

At what it learned in training, plus whatever text it is handed on this call. That is why your homework chatbot could state an outdated fact with confidence: nothing newer was in front of it. This lesson is about what you hand it.

Worked example: the first call

A student types: "Is the laser cutter free on Friday?" Your program does not send just that sentence to the model. It builds a request out of several blocks.

One round trip, where your program sends a request and the model sends text back, is what I'll call a call. I'll count the size of each block in tokens, which are small chunks of text, and I define them right after the trace.

Worked example: call 1 of the makerspace assistant
  1. System prompt, 800 tokens. The standing rules and tone you wrote, such as "You help students at the makerspace. Be short and friendly. Check the calendar before you answer about times."
  2. Tool definitions, 600 tokens. The written descriptions of check_calendar, search_manual and book_slot: each name, what it does and what inputs it takes. The model cannot use a tool it cannot read about.
  3. The student's question, 20 tokens. The only part the student typed.
  4. Total sent in: 800 + 600 + 20 = 1,420 tokens.
  5. The model's reply, 40 tokens. A request to run check_calendar for Friday.
  6. Everything in the window by the end of the call: 1,420 + 40 = 1,460 tokens.

Look at the proportions. The student typed 20 of those 1,460 tokens, and the other 1,440 are rules, tool descriptions and the model's own reply.

One more case of the same thing. Say you add a 200-token list of safety rules to the system prompt. The first call now sends 800 + 200 + 600 + 20 = 1,620 tokens, and every later call in every conversation carries those 200 extra tokens too.

Here is a quick yes-or-no test you can run on any agent. For each thing, ask: is this text sent to the model on this call?

  • The system prompt: yes, it is sent every call.
  • The tool definitions: yes, also every call.
  • The student's message: yes.
  • The model's own reply: yes, it counts toward the window too.
  • A manual sitting on disk that nobody loaded: no.

The idea: tokens and the context window

A token is a small chunk of text. It can be a short whole word, a piece of a longer word, or a punctuation mark, so a word is not one token. Roughly, short common words tend to be one token and long rare ones get split, which is why counts only estimate (and why you measure with a counting tool, not by counting words).

The context window is all the text the model can reference when it writes one reply, including the reply itself (context windows docs). Think of it as the model's working memory for this call: if something is in the window the model can use it, and if it is not, the model cannot.

Everything counts toward the window's size limit: the system prompt, every message, every tool result, the tool definitions and the output the model generates (context windows docs). That is why the bar in the figure below fills up before the student has said much.

Every model has a limit on window size, counted in tokens. Some current models allow up to 1M tokens and others 200,000 (context windows docs).

Against even the smaller limit, our first call is tiny: 1,460 / 200,000 is about 0.7 percent. A single call is nowhere near full, so the trouble comes from what piles up over many calls, which is the next part.

A common mix-up: "A token is a word"

It feels natural because we count words all the time. But a token is a chunk the model's tokenizer chooses, so the count depends on the model: the same text can count as roughly 30 percent more tokens on the newest models than on older ones, because the tokenizer changed, and the exact increase depends on the content (token counting docs).

As an illustration, a 1,000-token prompt on an older model could be about 1,300 on a newer one. Token counts are estimates, so count again on the model you pick; the counting tool is free to use. A cost estimate made on one model does not carry over to another.

A common mix-up: "Only my message counts toward the window"

It is tempting because your message is the only thing you see typed. But the 800 tokens of rules and the 600 tokens of tool descriptions are sent, and counted, on every call, before the student types a word.

A common mix-up: "The window is the model's training data"

The window is working memory for this call, and it is different from the large body of text the model was trained on (context windows docs). The chatbot with the outdated fact is the contrast: the old fact was baked in during training, and nothing in its window corrected it.

Check yourself

On the first call of the laser cutter question, which list is everything that counts toward the window?

Show the answer

The third option. Rules 800 + tool descriptions 600 + question 20 + the model's reply 40 = 1,460 tokens. Anything not sent, like a manual on disk, is not in the window.

In one line: before the student says a word, 1,400 tokens are already in the window, and you pay to send them every time. Keep that number in mind, because the next part adds up what happens when there is more than one call.

2. Conversation history: what is kept between steps 10 min

The model does not remember the last step; your program hands it the whole story again each time. So the window grows with every step, and so does the bill.

Let's follow the same question to the end, and then add a booking on top of it. I'll add up what each call sends in, because that is the part that keeps growing.

Model usage is billed per token, and input tokens (what you send) and output tokens (what the model writes) are priced separately; check your provider's price page. The price below, $3 per million input tokens, is made up so the sums are easy. A tool result is the text your program sends back after it runs a tool the model asked for.

Worked example: four calls, one conversation (all numbers made up)
  1. Call 1. Input: 1,420 tokens (rules 800, tools 600, question 20). Output: a request to run check_calendar for Friday, 40 tokens.
  2. Your program runs the tool. The result is Friday's laser cutter slots, 300 tokens. The program adds the model's request and the result to its list of messages.
  3. Call 2. Input is the whole thing again: 1,420 + 40 + 300 = 1,760 tokens. Output: the final answer "Free 2 to 4 pm", 60 tokens.
  4. Input billed so far: 1,420 + 1,760 = 3,180 tokens. Not 1,760, and not 300.
  5. The student replies "Book 2 pm", 10 tokens. The program adds the answer and this new message to the list.
  6. Call 3. Input: 1,760 + 60 + 10 = 1,830 tokens. Output: a request to run book_slot, 40 tokens.
  7. Your program runs the tool. The result is a booking confirmation, 50 tokens.
  8. Call 4. Input: 1,830 + 40 + 50 = 1,920 tokens. Output: a short message confirming the booking.
  9. Total input across the four calls: 1,420 + 1,760 + 1,830 + 1,920 = 6,930 tokens.
  10. Cost at the made-up price: 6,930 / 1,000,000 × $3 = about $0.021 for the whole conversation.

Notice step 4. Each new call re-sends everything from the calls before it, so the total is far bigger than the length of any single message.

To see where call 3's 1,830 comes from, here is exactly what your program holds just before it sends call 3, besides the 1,400 tokens of rules and tool descriptions:

  1. The student's first question, 20 tokens.
  2. The model's check_calendar request, 40 tokens.
  3. The calendar result, 300 tokens.
  4. The model's answer "Free 2 to 4 pm", 60 tokens.
  5. The student's "Book 2 pm", 10 tokens.

Those five add up to 430, and 1,400 + 430 = 1,830. Nothing is hidden: the input is the rules, the tools and the list, in order.

The idea: the message list is the memory

The model is stateless per call: it keeps nothing from one call to the next. The only memory inside a conversation is the list of messages your program keeps and sends again.

Each turn's input is all the previous conversation history plus the current user message, and earlier turns are kept in full (context windows docs). Here is that shape as a sketch, not a real library:

messages = [user("Is the laser cutter free on Friday?")]
while True:
    reply = call_model(RULES, TOOLS, messages)   # sends everything
    messages.append(reply)                       # keep what it said
    if reply.is_tool_request:
        messages.append(run_tool(reply))         # keep the result too
    else:
        break                                    # final answer

"Between steps" means that list. If something is not in messages, the next call cannot see it.

Now a second line of arithmetic. The 1,400 tokens of rules and tool descriptions are sent on all four calls: 4 × 1,400 = 5,600, which is about 81 percent of the 6,930. That is why a long system prompt is the first place to look when you want to cut cost.

And what if the conversation keeps going? Suppose each later call adds about 100 tokens. Calls 5 to 10 then send 2,020, 2,120, 2,220, 2,320, 2,420 and 2,520 tokens, which add up to 13,620.

Add the first four calls and the total is 6,930 + 13,620 = 20,550 input tokens, about $0.062 at the made-up price. A conversation two and a half times longer (10 calls against 4) cost almost three times the bill, even though each message stayed short.

A common mix-up: "The model remembers the earlier steps by itself"

It feels that way because the answers fit together. But suppose your program forgot to append the check_calendar result. Call 2 would hold only 1,420 + 40 = 1,460 tokens, with no calendar in it, and the model would either ask again or guess.

A common mix-up: "Cost is just the length of my latest message"

The newest message in the trace is 10 tokens, yet the conversation billed 6,930 input tokens. Cost follows the whole window on every call, not the last thing typed.

A common mix-up: "The window just stops when it is full"

It does not stop politely. If the input alone is over the limit, the API returns a 400 error, "prompt is too long". On current models, if the input fits but the reply runs into the limit, generation ends early with the stop reason model_context_window_exceeded; older models return a validation error instead (context windows docs).

Either way the agent fails in the middle of a job, so budget before it happens.

Recap in three lines. The model keeps nothing between calls. Your program keeps the list and re-sends it. So the list is what you control, and what you pay for.

3. Context rot and context editing: why a fuller window is not a better one 9 min

A bigger window does not mean the model uses all of it well, and old results you no longer need still cost money every call. So you choose what stays, and clear or summarise the rest.

Here is a longer question that makes the problem visible. The student asks: "How do I change the lens on the laser cutter, and is it free Friday?"

Worked example: one big tool result (all numbers made up)
  1. Call 1. Input: 1,420 tokens. Output: a request, search_manual("laser cutter lens change"), 40 tokens.
  2. The tool returns a whole manual chapter: 5,000 tokens. The model needs only a few lines of it.
  3. Call 2. Input: 1,420 + 40 + 5,000 = 6,460 tokens. Output, 60 tokens: the three short lens-change steps it pulled from the chapter, plus a request to run check_calendar.
  4. The calendar result is 300 tokens.
  5. Call 3. Input: 6,460 + 60 + 300 = 6,820 tokens. The chapter is 5,000 of them, and the model finished using it in call 2.
  6. Now clear the chapter and leave a 20-token stub saying a search ran. Call 3's input becomes 6,820 − 5,000 + 20 = 1,840 tokens, which saves 4,980 on that call and on every later call in the conversation.

Clearing old tool results like this is called tool result clearing. The safe moment is after the model has written down what it needs, as in step 3, where its own short reply carries the three steps forward.

A stub is just the short line that stays behind. If the model needed the chapter again later, your program could simply call search_manual again; leaving a stub and re-fetching is a habit worth adopting.

A second way to shrink a long history is to summarise it. When the history nears the limit, the program (or the platform) replaces old messages with a short summary and carries on. That is compaction. Clearing and compaction together are what the title calls context editing: changing what is in the window while the job runs. Clearing old tool results is one of the lightest forms of it (Effective context engineering).

Here is a small compaction trace, with made-up numbers:

  1. A long visit has reached 12,000 tokens of history, close to the budget you set.
  2. The program asks the model to write a summary of the visit, and it comes back at 300 tokens.
  3. The program replaces the old messages with that summary, so every later call carries 300 tokens instead of 12,000. That saves 11,700 tokens per call.
  4. Check what the summary kept. "Dana asked about the lens change and was given the steps. Booked laser Friday 2 pm" is safe; a summary that dropped the booking is not.

The idea: more room is not better

A fuller window can make the model worse. As the token count grows, accuracy and recall degrade, a phenomenon called context rot (context windows docs).

Think of finding one line on a ten-page printout instead of a one-page note. The line is there either way, but it takes more care to find it. In the same spirit, context is a finite resource with diminishing returns, and the aim is the smallest set of high-signal tokens that gets the job done (Effective context engineering).

That gives you three moves:

  1. Clear old tool results once they have been used. It is the lightest move.
  2. Summarise the old history (compaction) when the window gets close to full.
  3. Do not load it at all until it is needed. That is the next part.

Which one to pick? Clear when one big result is done with. Summarise when the whole history is long and still matters. Skip loading when you can look it up later.

A common mix-up: "A bigger window means I can stop thinking about what goes in"

Many current models offer windows of up to 1M tokens, and the same docs still warn that more context is not automatically better because of context rot (context windows docs). A huge window does not make the 5,000-token chapter free either: it is still re-sent and billed on every call.

A common mix-up: "Clearing a result means the agent forgets it did the search"

Only if you clear it carelessly. A short stub, or a one-line note, keeps the record that the search happened, so the agent does not repeat it by mistake.

A common mix-up: "Summarising loses nothing"

A summary that drops "booked for 2 pm on Friday" makes the agent offer the slot again. Anything that must survive a summary should be written to notes, which is Part 5.

Check yourself

New trace. Rules and tool descriptions are 1,500 tokens and the question is 25. Call 1's output is a 40-token search_manual request, and the chapter that comes back is 4,000 tokens. Call 2's input is 5,565 and its output is 50 tokens. The calendar result is 200 tokens, so call 3's input is 5,815. If you clear the chapter and leave a 20-token stub, what is call 3's input?

Show the answer

The second option: 5,815 − 4,000 + 20 = 1,835 tokens. Only the used-up chapter goes. Clearing the rules or the student's question would be wrong, because the model still needs both.

Recap: a bigger window is room, not a goal. Clear what is used up, summarise what is long, and keep only what the next call needs.

4. Retrieval-augmented generation (RAG): finding the right page in a long manual 11 min

A long manual cannot sit in the window on every call, so the assistant looks up only the few pieces that match the question. This is how it finds the right page without paying to read the whole manual each time.

Take the laser cutter manual: 120 pages, at an invented 500 tokens a page, so 60,000 tokens. First, some preparation that happens once, before any student asks anything.

Worked example: from a 60,000-token manual to 900 tokens (all numbers made up)

Prepared once, offline

  1. Split the manual into chunks of about 300 tokens each: 60,000 / 300 = 200 chunks.
  2. Turn each chunk into a list of numbers and store it. The list is called an embedding, and it is built so that chunks with a similar meaning get lists that are close to each other.

At question time

  1. The student asks: "What's the thickest acrylic I can cut?" Your program turns the question into numbers the same way, and finds the best matching chunk, "Materials and thickness limits", and adds the chunk before it and the chunk after it in the manual, so about 900 tokens in all.
  2. Only those 3 chunks go into the window as the tool result. The whole manual would be 60,000 tokens, or $0.18 per call at the made-up price, while 3 chunks are 900 tokens, or $0.0027 per call. That is about 67 times cheaper (60,000 / 900).
  3. A second question: "What does error E-42 mean?" (E-42 is an invented code, not from any source.) A search by meaning may return chunks about errors in general, while a plain word-match search finds the exact string "E-42". Real systems run both and keep the top few.

A real case is the error code TS-999, where a word-match ranking called BM25 catches the exact string that a meaning-based search can miss (Contextual Retrieval). Same lesson as E-42, different code.

What does "close" mean in step 2? Here is a toy version with only two numbers per chunk; real embeddings use far more numbers, but the idea is the same.

  1. The chunk "Materials and thickness limits" is stored as (0.9, 0.1).
  2. The chunk "Cleaning the lens" is stored as (0.1, 0.9).
  3. The question "thickest acrylic I can cut?" becomes (0.8, 0.2).
  4. The question differs from the first chunk by 0.1 and 0.1, and from the second by 0.7 and 0.7. So the first chunk is nearer, and it is the one retrieved.

And here is what a retrieved result might look like as it lands in the window, again invented:

  1. Chunk 41, the end of "Cutting speeds", about 300 tokens.
  2. Chunk 42, "Materials and thickness limits: acrylic up to 10 mm", about 300 tokens.
  3. Chunk 43, the start of "Settings by material", about 300 tokens.

That is 900 tokens in total, and the model answers from the middle one. The neighbours are there in case the answer spills across a cut.

The idea in four steps

Each of the pieces from the trace has a name. A chunk is one small piece of a document, cut so it is small enough to fetch alone. An embedding is the list of numbers that stands for a chunk's meaning.

Retrieval means looking up the few pieces that match a question and putting only those into the window. Retrieval-augmented generation, or RAG, is retrieval followed by the model writing its answer from the pieces (Contextual Retrieval).

  1. Chunk: split the document into pieces.
  2. Embed: store each piece as a list of numbers, in a search index.
  3. Search: turn the question into numbers, find the nearest pieces, and add a word-match search for exact terms.
  4. Top few: put only the best pieces in the window.

In the agent loop, retrieval is just another tool: search_manual. Its result lands in the window like any other tool result, so Parts 2 and 3 apply to it. The three chunks get re-sent on later calls, and you can clear them once they are used.

A related trick is just-in-time loading. Keep lightweight pointers such as a file path or a page number, and load the content only when you need it (Effective context engineering).

When not to use it

Retrieval is memory for knowledge that is large and mostly unchanging: look it up when needed, rather than carry it. But it is not always the answer.

If the whole knowledge base is under about 200,000 tokens (a few hundred pages), you can skip retrieval and put it all in the prompt. Prompt caching, where the provider stores a prompt start you reuse, makes that faster and cheaper (Contextual Retrieval). So for the design review this is a cost and accuracy trade-off, not a rule.

A common mix-up: "Retrieval makes the model know the manual"

The model reads the 3 chunks fresh on each call. If the answer sits in a chunk that was not retrieved, it answers from guesswork, like the chatbot with the confident wrong fact.

In Anthropic's tests, standard embeddings failed to bring up the right chunk in the top 20 results 5.7 percent of the time. The best combination there (context added to chunks, both search types, and reranking, a second pass that re-orders the results) still failed 1.9 percent of the time (Contextual Retrieval).

A common mix-up: "Meaning-based search is always enough"

It sounds smarter, so it is tempting to trust it alone. But the E-42 query shows an exact identifier needs word matching, which is why the source combines both.

A common mix-up: "RAG is always the right answer for documents"

A 30-page quick-start guide of 15,000 tokens may be cheaper and simpler to include whole, especially when cached. Building and tuning a search index is work you only want to do when the document is big enough to need it.

Check yourself: choose the design

Recap: a manual is too big to carry, so you cut it, index it, and pull the best few pieces per question. The pieces then behave like any other tool result.

5. Persistent memory: notes that survive between sessions 10 min

When a conversation ends, the window is gone, so anything the assistant should know next visit has to be written down somewhere outside it. Notes are how it remembers a student, and loading them is just another step in the loop.

Two terms first. A session is one visit: from the student's first message until the window is thrown away. A memory file is a small text file your program stores outside the window and can load into it later.

This is your mission's own case: a student's training status between visits. Meet Dana, who comes twice. Your program adds her name from the login to the first message, and the system prompt now says: "check your notes folder before anything else". The booking system also gets a fourth tool, check_training.

Worked example: Dana, two visits (all numbers and dates made up)

Visit 1

  1. Dana asks: "Can I use the laser cutter?" The model first asks to view the notes folder. Your program looks, and there is no file for Dana.
  2. The model calls check_training. The booking system says Dana finished the safety orientation only, on 2026-09-14.
  3. It tells Dana she needs the laser training. Before ending, it asks your program to create /memories/students/dana.md, about 40 tokens: 
    Dana: orientation done 2026-09-14.
Laser training not done.
Asked about laser.
  4. The visit ends and the window is thrown away. Every message from visit 1 is gone. Only the file remains.

Visit 2 (new session, empty window)

  1. Dana: "Ok I did the laser class, can I book Friday?" The window holds the rules, the tool descriptions, her name and this message, and nothing from visit 1.
  2. The model views the notes folder and reads dana.md. That puts 40 tokens into the window, and it sees laser training was pending.
  3. It calls check_training to confirm. The booking system is the system of record, the place that holds the true answer, and the note is not. It says laser training was done on 2026-11-18.
  4. It checks the calendar and books the slot. That is the same loop as Part 2.
  5. It updates the note: "Laser training done 2026-11-18. Booked laser Fri 2 pm."

The cost of remembering Dana is about 40 tokens per visit. Compare the alternative of replaying visit 1: if that visit had been the 6,930-token conversation from Part 2, loading it would cost 6,930 / 40, about 173 times more.

One more visit shows the habit. A week later Dana says "Book me Tuesday at 3". The model reads the note (now about 50 tokens), sees she is trained, books through the tools, and adds "Booked laser Tue 3 pm" to the file. Nobody had to ask Dana anything twice.

The idea: who does what

Between steps, memory is the message list. Between sessions, it is something stored outside the window, which your program fetches and loads.

In Anthropic's memory tool, the model asks for file operations (view, create, str_replace, insert, delete, rename) under a /memories folder, and your application carries them out against storage you control, such as a per-user directory or keys in a database (memory tool docs).

When the tool is on, the model is told to view its memory folder before anything else, and to assume its context window might be reset at any moment (memory tool docs). That second part is why you write notes as you go, not only at the very end.

The same pattern appears as structured note-taking: the agent regularly writes notes that are kept outside the context window (Effective context engineering). Notes do not have to be files. A database row keyed by student id works for the same job, as long as your program stores it and loads it.

A common mix-up: "The model learned about Dana, so it will remember her"

Nothing in the model changes between visits; it is the same text predictor as before. Visit 2's window starts empty, and the only reason the model knows Dana is the 40-token file it read.

A common mix-up: "The model's memory is stored by the vendor"

With the memory tool, the model only requests operations and your application stores the files. So what to keep, for how long and who can read it are your decisions, and your risk (memory tool docs).

The docs list these safeguards: reject a path like /memories/../../secrets.env, cap how large a file can grow, and delete memory files that have not been accessed in a long time.

A common mix-up: "A note is always true"

Dana's note says laser training not done, and she finished it a few days later. That is why step 7 re-checks with check_training. A note is a hint with a date, and the booking system stays the source of truth.

Design note. Student notes are personal data, so store the least you need, decide who can read the folder, and expire old files. Cap the size of each file so loading it stays cheap. Put a date on every line, so a stale fact, one that has gone out of date, looks stale.
Check yourself: where does it live?

For each fact, choose one: save it as a note, fetch it again with a tool, or leave it only in the current window. (a) "Dana prefers afternoons." (b) Friday's calendar. (c) The 2 pm slot Dana is choosing between in this chat. (d) Dana's training status.

Hint

Show the answer

(b) Fetch with a tool. It changes constantly, so a saved copy would be wrong by tomorrow.

Recap: the window dies with the visit, so write down what the next visit needs, load it first thing, and check anything that can go stale against the real system.

6. Context design: deciding what to keep, fetch and save 10 min

Now put the three kinds of memory together and decide, for each thing the assistant needs, where it should live. This is the call you will defend at the design review, and the cost per request is the reason it matters.

Here is the decision done in full for the makerspace assistant. One row per thing it needs, where it lives, a reason in a few words, and a made-up token cost.

Total a busy call: 1,400 (rules and tools) + 20 (question) + 40 (notes) + 900 (retrieval) + 300 (calendar) + about 100 (replies) = 2,760 tokens, or about $0.008 at the made-up price.

The "paste the manual in" design replaces the 900 with 60,000: 1,400 + 20 + 40 + 60,000 + 300 + 100 = 61,860 tokens, about $0.19. That is about 22 times more per call (61,860 / 2,760).

How did each row get its answer? It came from four short questions, which work as a rule of thumb:

  1. Is it needed on almost every call? Then keep it in the window, and keep it small.
  2. Is it big and needed only sometimes? Then retrieve a few pieces.
  3. Does it change faster than your notes would be updated? Then fetch it with a tool each time.
  4. Must it survive the end of the visit? Then save it as a note, and re-check anything that can go stale.

What would change the decision? A small manual, say 10 pages, could just go in whole. A very long visit would push you to clear or summarise more often.

A student record that changes constantly would turn the notes row into a tool-only row. And a tighter budget would push you to shrink the 800-token system prompt, since it is paid on every call.

Why it matters in the real world

What goes into the window on each call decides what a request costs and how well the assistant answers. The memory design decides whether a student re-explains their situation at every visit, and what student data you hold.

The three decisions in your mission are exactly this table: what to keep in context, what to save between sessions, and how to find the right page in a long manual.

Summary

  • The model sees only the window on each call, and everything counts: rules, tool descriptions and its own replies.
  • Between steps, the program resends the whole message list, so the window and the bill grow with every step; clear or summarise what is done.
  • Big knowledge like manuals is retrieved a few pieces at a time instead of carried.
  • Between sessions, only what is written outside the window survives: notes that the program stores and loads, checked against the real source before acting.
  • More room is not better; the aim is the smallest set of tokens that does the job.
