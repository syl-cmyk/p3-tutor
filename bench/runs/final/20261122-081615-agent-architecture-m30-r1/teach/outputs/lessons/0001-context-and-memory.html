Context and memory: what an agent sees now, and what it can look up later

By the end of this lesson you can decide, for any agent, what goes into the context window on each call, what is carried between steps, what is saved between sessions, and what is fetched on demand.

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your makerspace assistant has to answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. This lesson gives you the words and a decision table to make those calls and defend them at your design review.

We'll follow your assistant all the way through. It uses three kinds of information: the long machine manuals, the booking calendar that changes by the minute, and each student's training status, which is small but must last between visits. Our student is Dana.

Warm-up: two recall questions

1. In the agent loop, who actually runs a tool: the model or the program around it?

Check your answer

The program. The model only asks for the action and the program carries it out. Keep that in mind, because memory and retrieval below work the same way.

2. Without being handed any text, what does a model know?

Check your answer

Only what it picked up in training. Anything newer or more specific has to be handed to it as text, and today's lesson is about how you choose that text.

Part 1. Context window: everything the model can see on one call

The model has no memory of its own between calls; it only reads what the program hands it each time. So the first job is to know exactly what is in that handover and how fast it fills up.

One word first. A token is a chunk of text, roughly a short word or part of a word. The model reads and writes in tokens, and the bill is counted per token (Claude Docs: pricing). Every token count in this lesson is a made-up number, chosen to keep the arithmetic easy.

Now the main term. The context window is all the text the model can look at when it writes a reply, including the reply itself. It works like the model's working memory, and it is a different thing from the training data it learned from (Claude Docs: context windows).

Everything counts: the instructions (the system prompt), every message, every tool result, the tool descriptions (the written menu of tools the model may ask for), and the output (Claude Docs: context windows).

Worked example (made-up token counts)

Dana asks: "Is the laser cutter free Friday, and how do I change the lens?"

  1. Call 1 input: instructions (about 400 tokens), the 3 tool descriptions (about 600) and Dana's question (about 25). That is about 1,025 tokens in.
  2. The model asks for check_calendar, and the program runs it.
  3. Call 2 input: everything from call 1, plus the model's tool request (about 25), plus the calendar result (about 150). That is about 1,200 tokens in, because call 1 got sent again.
  4. The model writes its answer (about 100 tokens), and the answer joins the history. Call 3 would carry all of it again, about 1,300 tokens, plus Dana's next message.
  5. Now a different, longer chat: 5 turns, where each turn adds about 300 tokens. The inputs would be about 1,025, 1,325, 1,625, 1,925 and 2,225, which is about 8,100 tokens sent in total.

This is the agent loop you already know: each step is a separate model call, and the program, not the model, runs the tools. A longer history means more tokens go in on every later call, and since the bill is per token, that adds up. (The cost point is my own reasoning, not a figure from the docs.)

A common mix-up

"The model remembers my last message by itself." It feels that way because chat looks continuous. But if Dana says "book it" and the program left out the earlier messages, the model has no idea what "it" is. The program resends the history on every call.

A common mix-up

"The window only holds my question." In call 1 above, the question is 25 of 1,025 tokens, about 2%. The rest is instructions and tool descriptions that the model needs every single time.

So the window is the whole handover, it is rebuilt on each call, and it only ever grows unless you do something about it. That "something" starts with asking how much is too much.

Part 2. Context rot: why a bigger window is not a better answer

A window has a size limit, but a more important limit is that the model gets worse at using a long context. So the aim is the smallest set of useful text, not the most text.

This getting-worse has a name: context rot. As the token count grows, accuracy and recall degrade (Claude Docs: context windows). So what you put in matters as much as how much room there is.

Here's a way to picture it. The model has an "attention budget", and every token you add uses up some of it. The guiding aim is the smallest possible set of high-signal tokens, meaning only text that helps with this question (Anthropic Engineering).

Deciding what goes in on every call has a name too: context engineering. That is the skill this whole lesson is about.

Worked example (made-up token counts)

Two ways to give the assistant the 80-page laser cutter manual. Option A pastes the whole manual into every call, about 40,000 tokens. Option B pastes only the 2 relevant pages, about 1,000 tokens. Compare them over a 6-call conversation.

  1. Option A sends 40,000 manual tokens on each of 6 calls: 240,000 in total.
  2. Option B sends 1,000 tokens on each of 6 calls: 6,000 in total.
  3. 240,000 divided by 6,000 is 40, so A moves 40 times more text, before we even ask whether the answers get worse.
  4. In A, the lens-change step is one small piece among about 39,000 unrelated tokens. In B, the pages are all about the job.
  5. Same idea for the calendar. Dumping 30 days of bookings is about 8,000 tokens; only Friday's slots is about 200. Over 6 calls that is 48,000 against 1,200, again 40 times.

To be clear about what is cited and what isn't: the arithmetic uses made-up numbers, and the only sourced claim is that quality degrades as tokens grow. The 40-times cost gap is just multiplication, and it matters because your sponsor's budget is small.

A common mix-up

"A 1M-token window means I can put everything in." Windows go up to 1M tokens depending on the model (Claude Docs: context windows), but that number is how much fits, not how well it gets used. And Option A would still cost 40 times Option B.

A common mix-up

"Context rot only matters when the window is full." The docs say accuracy and recall degrade "as token count grows", not "at the limit". Option A at 40,000 tokens is nowhere near 1M, and it already has far more text to sift through than Option B.

Short recap: more text costs more and buries the useful part. In a long run, that creates a steady problem, which is what you do with the history as it piles up.

Part 3. Carrying state between steps: what to keep, shrink or drop as a run gets long

Inside one long run, the history keeps growing, so you have to decide what stays word for word, what gets shortened and what gets dropped. This comes right after rot because it is the first thing you do about it.

There are three moves.

  1. Clear old tool results. Delete a big result you no longer need and keep, at most, a short line about it. It is one of the safest, lightest-touch moves (Anthropic Engineering), and the API lists it as a feature (Claude Docs: context windows).
  2. Compaction. When the conversation nears the limit, summarize it and continue in a fresh window that starts with the summary (Anthropic Engineering). The API can also do this on the server, in beta (Claude Docs: context windows). My advice: keep decisions and open problems, and drop repeated output.
  3. Keep a pointer. Hold a lightweight identifier, like a file path or a booking id, and load the real content only when you need it. This is called just-in-time loading (Anthropic Engineering).

Each move has a price. A summary can lose a detail that matters later, and a cleared result costs a new call if you need it again. Calendar results are the clearest case for dropping, because they go stale.

Worked example (made-up token counts)

A 12-step run where Dana asks about the laser cutter and the 3D printer.

  1. Steps 1 to 4: laser calendar (150 tokens), laser manual pages (1,000), printer calendar (150), printer manual page (1,000). The history grows by about 2,300 on top of the fixed 1,025.
  2. Step 5: clear the two calendar results and keep one short line: "laser: free Fri 2 pm; printer: busy Fri". That saves about 300 tokens and removes text that could go stale.
  3. Step 8: after more manual pages and calendar lookups for Dana's next questions, the history has grown to about 7,000 tokens, close to a 7,500-token limit the team chose for itself.
  4. Step 9: compaction. The summary, about 200 tokens, reads "Dana wants Friday afternoon; laser free 2 pm; printer busy; Dana is trained on laser, not printer." The history drops to about 1,225.
  5. Step 10 carries on with the fixed 1,025 plus the 200-token summary.
  6. What if the summary had left out "not trained on printer"? At step 11 the assistant could happily book the printer for Dana.
A common mix-up

"Summarizing is free and safe." It is tempting because the summary looks complete. But the step 11 case above shows how one dropped line, Dana's missing printer training, turns into a wrong booking.

A common mix-up

"Old tool results should always stay, so nothing is lost." Friday's calendar from step 1 becomes wrong if Dana books a slot at step 6. Keeping it means the model sees two conflicting facts about the same slot.

Recap: clear what goes stale, summarize what is long, and point at what you can fetch later. All of that happens inside one run, and none of it survives the end of the session.

Part 4. Persistent memory: notes that last between sessions

Everything so far disappears when the session ends. To remember Dana next week, the assistant has to write things down outside the window and read them back later.

A new session starts with an empty window. Memory, in this lesson, means the program stores information in files or a database, and the model reads it back by calling a tool (Claude Docs: memory tool). Writing notes outside the window and pulling them back later is called structured note-taking (Anthropic Engineering).

Take Anthropic's memory tool as one example: it runs on your side. The model asks for file operations under a /memories folder, your program carries them out against storage you control, and the result goes back as a tool result. The commands are view, create, str_replace, insert, delete and rename (Claude Docs: memory tool).

It is the same loop as before: the model asks, the program acts. At the start of a task, the model views its memory folder first (Claude Docs: memory tool).

One contrast. What a model learned in training sits in its weights, which researchers call parametric memory. Notes and searchable documents live outside the weights (Lewis et al., RAG paper).

What should you save? These are my design choices, not rules from a source. Save facts that change slowly, like training status and preferences. Don't save calendar availability, which is stale by Friday, or the manual, which already has its own home.

Keep the folder safe: restrict the model to /memories, cap file sizes, delete files nobody has opened in a long time, and keep sensitive data out (Claude Docs: memory tool). Also my opinion: treat a note about training status as a handy cache, and check it against the university's official record before booking, because a note can be stale or wrong.

Worked example (made-up token counts)

Two sessions, a week apart.

  1. Session 1. Dana says: "I finished the laser cutter safety training today." The model calls memory with view /memories. The folder is empty.
  2. The model calls create /memories/students/dana.md with "Trained: laser cutter (Nov 20). Prefers afternoons." The program writes the file and returns "File created successfully at: /memories/students/dana.md".
  3. The session ends and the window is discarded.
  4. Session 2, a week later. Dana says: "Book the laser cutter Friday." The window starts with only instructions and tool descriptions, about 1,025 tokens. The model calls view /memories, sees students/dana.md and views it, about 30 more tokens.
  5. The note says "Trained: laser cutter", so the model (after checking the university's record, if your design requires it) calls check_calendar and books an afternoon slot.
  6. Later, Dana passes 3D printer training. The model uses str_replace to update the line instead of creating a duplicate file.
A common mix-up

"Memory means the model learned Dana." Nothing in the weights changes. Delete dana.md and session 3 knows nothing about her.

A common mix-up

"Memory saves itself." The model only requests operations; your program has to build the handler and the storage (Claude Docs: memory tool). If you never build the handler, "Trained: laser" is never written.

A common mix-up

"Save everything." A note "Laser free Fri 2 pm" saved on Monday is wrong by Friday. Save slow facts, look up fast ones.

Recap: the window forgets, the notes remember, and the program is what connects them. Some information, though, is too big even for notes.

Part 5. Retrieval: finding the right page in a long manual

Some information is too big to keep in the window or in notes, like the manuals, so the assistant looks up only the part it needs for each question. This is retrieval, and it is how Part 2's "smallest useful text" is done in practice.

Retrieval means searching an outside source and putting only the best matches into the window. Its best-known form is retrieval-augmented generation (RAG): a model's own stored knowledge combined with an external source it can search. The idea was motivated by limits of knowledge held only in weights, such as showing where an answer came from and updating what the model knows (Lewis et al., RAG paper).

Here is the usual shape. These steps are plain-words advice, not a quote from the paper.

  1. Ahead of time, cut each manual into chunks, say one section or page each.
  2. At question time, search the chunks. A keyword search scores them by shared words; a meaning-based search scores them by how close the meanings are. You don't need the math for either.
  3. Put the top few chunks in the window, with their page names.
  4. The model answers from them and cites the page.

You can wire this two ways. In a fixed wiring, the program always searches first. Or you give the model a search tool and let it decide when to call it, which is just-in-time loading. A hybrid, with some data loaded up front and the rest on demand, is often the best fit (Anthropic Engineering).

Retrieval can miss, and then the model may fall back on general knowledge. My advice: tell it to say "not found in the manual" when nothing good comes back.

And note the difference from Part 4. Retrieval looks up shared documents; memory holds one student's facts. The call has the same shape in both: the model asks, the program searches or reads, a result comes back.

Worked example (made-up numbers and manual text)
  1. Dana asks: "What's the max material thickness for the laser cutter?"
  2. The model calls search_manuals(query="laser cutter max material thickness").
  3. The program searches 400 chunks (4 manuals, about 100 chunks each) and returns the top 3, each about 300 tokens: "LC-40 manual p.12, Specs: cuts acrylic up to 10 mm"; "p.14, Materials not allowed: PVC"; "p.9, Focus the lens".
  4. The window grows by about 900 tokens instead of 40,000.
  5. The model replies: "Up to 10 mm acrylic (LC-40 manual, p.12). PVC is not allowed (p.14)."
  6. A miss: Dana asks how thick it can go before it "burns through", but the manual only says "maximum cut depth". A keyword search returns the wrong chunks, so the model should reply "I could not find that in the manual" and not guess.
A common mix-up

"Retrieval makes the model learn the manual." Delete the chunk and the next answer changes, because nothing in the weights was touched. The manual stays outside, as external memory the model searches (Lewis et al., RAG paper).

A common mix-up

"Retrieval always returns the right page." The "burns through" versus "maximum cut depth" miss above shows it doesn't. Your program must handle "nothing good found".

A common mix-up

"Retrieval and memory are the same." Max thickness is shared manual content, so you search for it. Dana's training is about one person, so you keep it in notes.

Recap: search big shared documents, keep small personal facts in notes, and always plan for a miss.

Worked example (made-up token counts)

Sam asks: "Can I use the 3D printer Saturday? I'm Sam."

  1. Identify the pieces: instructions and tool descriptions, Sam's training status, the printer manual, Saturday's calendar, the chat.
  2. Decide each home, as in the table: program, notes, search, live call, window.
  3. Estimate the window. Designed: 1,000 + 30 + 600 (2 manual chunks) + 150 = about 1,800 tokens. All-in: 1,000 + 30 + 35,000 (whole manual) + 8,000 (whole calendar) = about 44,000. That is roughly 24 times more.
  4. Say what is saved at the end: Sam's training status is unchanged, so nothing is written.
  5. Name one risk and its guard: a search miss, guarded by "say not found"; or a stale note, guarded by checking the university's record.

The third option. Availability changes fast, so the note went stale. The other three are wrong because notes can hold printer facts, the manual belongs to retrieval, and nothing deletes notes at session start.

Summary
  • The model sees only the context window, and the program resends it on every call.
  • More is not better: context rot plus cost, so curate.
  • In a run, clear, summarize, or point instead of pasting.
  • Between sessions, only what is written to notes survives.
  • Look up big documents by retrieval, and keep per-person facts in notes.

Say it in your own words: where does Dana's training status live, and when does it enter the window?
