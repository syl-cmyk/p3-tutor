Lesson 1 · 30 minutes

Context and memory: what an agent sees on each call and what it keeps

An agent's "memory" is just text: whatever is sent to the model on each call, plus whatever is saved outside it and loaded back in. By the end of this lesson you can say what goes into an agent's context window on each call, what must be saved outside it to survive between steps and sessions, and when to load information into the window by retrieval or by notes.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Your sponsor's model budget is small, so what you put in front of the model on every call is a money decision as well as a design one.

Every number for the makerspace in this lesson is a made-up example, so you can see the arithmetic. Swap in your own sizes later.

Part 1. Token: the unit a model reads, writes and bills by 3 min

Everything an agent reads and writes is counted in small pieces of text, and those pieces are what you pay for. So before we talk about what the agent sees, we need the unit it is measured in.

Take a real message a student might send: "Is the laser cutter free on Friday?" The model doesn't read it letter by letter or word by word. It reads small pieces called tokens: the pieces of text a model processes (pricing page). Input tokens are what you send in, and output tokens are what the model writes back; you're billed for both.

Is | the | laser | cutter | free | on | Friday | ?

That's 8 tokens in this simplified split. Real splits vary by model, so treat this one as a sketch.

A word the model hasn't seen much splits into more pieces. A made-up part number like "LC-120-E214" might come out as LC | - | 120 | - | E | 214, which is 6 tokens for one "word". Again, a simplified split.

Worked example: what does one call cost?
  1. Size the message. A typical 10 kB web page is about 2,500 tokens (pricing page). That works out to roughly 4 characters of English per token, which is a rough rule. Our message has 35 characters, so about 9 tokens, close to the 8 above.
  2. Size the manual. Say the laser-cutter manual is 120 pages. About 200,000 tokens is about 500 pages (contextual retrieval article), so say 400 tokens a page, again a rough figure. Then 120 × 400 = 48,000 tokens, and the 120 pages are a made-up size.
  3. Price the input. One example price is $2 per million input tokens (Claude Sonnet 5.5 on the pricing page). So 48,000 × 2 / 1,000,000 = $0.096.
  4. Price the output. The same example charges $10 per million output tokens, 5 times as much. A 200-token reply costs 200 × 10 / 1,000,000 = $0.002, while 200 input tokens cost $0.0004.
  5. Do one more. The calendar tool might return 40 booking rows, say 1,200 tokens. That's 1,200 × 2 / 1,000,000 = $0.0024 every time those rows are sent.

So the manual alone costs about 10 cents each time you send it. Keep that number in mind; most of this lesson is about not paying it over and over.

A common mix-up

"A token is a word." It's tempting because short common words like "Friday" often are one piece. But a long part number or an oddly spelled word splits into several pieces, and the same text gives different counts on different models: models from Claude 4.7 on produce about 30% more tokens for the same text (pricing page). Don't guess; count with the provider's token-counting tool.

A common mix-up

"Only what I type costs money." Input tokens (everything sent) and output tokens (everything the model writes) are both billed, at different rates. In the example above the reply costs five times more per token than the message.

Why it matters: your budget is spent in tokens, so every later choice in this lesson is really a choice about tokens. Recap: a token is a small piece of text, we estimate about 4 characters each, and input and output are priced separately.

Part 2. Context window: what the model can see on one call 4 min

The model only sees what is sent to it on each call, and that has a size limit. So at every step, someone is choosing what goes in.

The context window is all the text a model can reference when it writes a response, including the response itself (context windows doc). Let's trace the very first call for the message "Can I use the laser cutter Friday at 2?" The sizes are made up.

Trace: what your program sends on call 1
  1. System instructions: text that tells the assistant who it is and which rules to follow. Say 400 tokens.
  2. Tool descriptions for search_manual, check_calendar and book_slot: say 600 tokens. Tool descriptions count as input too, along with the system prompt and every message (context windows doc).
  3. The student's message: say 15 tokens.
  4. Total sent: 400 + 600 + 15 = 1,015 tokens.
  5. The model's reply: say 40 tokens, a request to check the calendar. It also takes up room in the window.

Now price that first call. The input is 1,015 × 2 / 1,000,000 = $0.00203. The 40-token reply costs 40 × 10 / 1,000,000 = $0.0004, so call 1 costs about $0.0024 in total.

A second student might ask, "Is the 3D printer free Saturday?" Same instructions, same tool descriptions, a different 12-token message. So the base is 400 + 600 + 12 = 1,012 tokens, and almost all of it is the same text sent again.

Here's the way to think about it: your program resends text on every call, so the model has only what is in that list. Nothing is waiting inside it from last time. If the manual's text isn't in the window, the model can't read the manual.

A common mix-up

"The model remembers the manual because I showed it last week." Try the trace with an empty window:

  1. The student asks, "What did I ask yesterday?"
  2. Your program sends the 1,015-token base plus that question. Yesterday's chat isn't in it.
  3. The model has nothing to answer from, so the honest reply is "I can't see that."

So how big can a window be? Up to 1M tokens, depending on the model (context windows doc). That's about 20 manuals of our made-up size. Sounds like plenty, but bigger isn't better.

As the token count grows, accuracy and recall degrade. That is called context rot (context windows doc). Context is a finite resource with diminishing returns, so you want the smallest set of text that does the job (Anthropic context engineering).

A common mix-up

"A bigger window means I can paste everything." You can, and you'll pay for it. A 48,000-token manual adds $0.096 to every call at $2 per million, and the model gets worse at finding the one line you need.

Why it matters: the window is both what limits what the assistant knows right now and what sets the cost of each call. Recap: window = system instructions + tool descriptions + messages + the reply, all counted. The API also adds a little text of its own when tools are on (a few hundred tokens), so treat our 1,015 as a made-up base before that extra (pricing page).

Part 3. Context accumulation and compaction: what is kept between steps 5 min

In the loop, every step is a new call, and the window grows as results pile up. So you decide what stays, what gets cleared, and what gets summarized.

Here's one request with four calls: "Book me the laser cutter for Friday afternoon, and tell me the kerf setting for 3 mm acrylic." Each call sends the whole history again, because each message and response accumulates in the window and earlier turns are kept completely (context windows doc). Sizes are made up; the base is the 1,015 tokens from Part 2.

Trace: four calls, one request
  1. Call 1 sends 1,015 tokens. The model asks for check_calendar(laser, Friday), a 40-token reply.
  2. Your program runs the tool. 40 booking rows come back, say 1,200 tokens.
  3. Call 2 sends 1,015 + 40 + 1,200 = 2,255 tokens. The model asks for search_manual("3 mm acrylic kerf"), say 40 tokens. The result is say 1,500 tokens.
  4. Call 3 sends 2,255 + 40 + 1,500 = 3,795 tokens. The model asks for book_slot, say 25 tokens. The result is say 30 tokens.
  5. Call 4 sends 3,795 + 25 + 30 = 3,850 tokens. The model writes the final answer.

Total input billed: 1,015 + 2,255 + 3,795 + 3,850 = 10,915 tokens. At $2 per million, that's 10,915 × 2 / 1,000,000 = $0.0218, about $0.022 for the input side of one request.

The question was 15 tokens, and the request was billed 10,915 input tokens. That's about 11 times the first call alone.

A common mix-up

"The model remembers earlier steps by itself." It doesn't. Your program resends the history. If your code drops the calendar result from the list, the next call has no idea what the calendar said.

A common mix-up

"Cost is the size of the question." The trace says otherwise: 10,915 billed input tokens for a 15-token question. What you keep resending dominates.

Three levers: clear, summarize, cache

Clear. Once the booking is made, the 40 calendar rows are dead weight. Dropping old tool results is one of the lightest forms of compaction, which means shrinking the history so the work can go on (Anthropic context engineering).

Clear them before call 4 and it sends 3,850 − 1,200 = 2,650 tokens. The request now totals 9,715 input tokens, about $0.019. That saves $0.0024 per request, which is $2.40 over 1,000 requests.

One more clearing case. The student follows up: "Thanks! And for 6 mm?" Say the final answer was 120 tokens and the new question is 10. Without clearing, that call sends 3,850 + 120 + 10 = 3,980 tokens.

Now clear all three tool results (1,200 + 1,500 + 30 = 2,730 tokens) and keep the model's three short requests (40 + 40 + 25 = 105). The call sends 1,015 + 105 + 120 + 10 = 1,250 tokens, about a third of the size.

Summarize. When a long job nears the window's limit, summarize the history and start a new window from the summary (Anthropic context engineering, context windows doc).

Cache. Prompt caching lets a repeated start of the prompt be read at a fraction of the price. On most models a cache read is 0.1 times the normal input price, and on the Sonnet 5.5 example it is 0.05 times (pricing page). But caching changes what you pay, not whether the tokens count against the window (context windows doc).

Check yourself

A request makes 3 calls. The base is 1,000 tokens, and after each of the first two calls a 500-token tool result is added (ignore the model's own requests). How many input tokens are billed in total?

Hint

Show the answer

4,500. Call 1 sends 1,000, call 2 sends 1,000 + 500 = 1,500, call 3 sends 1,500 + 500 = 2,000, so the sum is 1,000 + 1,500 + 2,000 = 4,500.

Why it matters: per-request cost in a loop is dominated by what you keep resending, and that's the lever your sponsor's budget leaves you. Recap: each call resends everything, so clear what's done.

Part 4. Retrieval: loading only the page you need 5 min

A long manual should not ride along on every call. Keep it outside the window, search it, and put in only the few passages that answer the question.

Before any student asks anything, split the manual into chunks: pieces usually no more than a few hundred tokens (contextual retrieval article). Store each chunk with its manual name and page number. Then retrieval means searching those stored chunks and loading only the best few into the window.

Trace: "What does error E-214 on the laser cutter mean?"
  1. The student's message arrives. The window holds the instructions and tool descriptions, say 1,000 tokens.
  2. The model asks for search_manual("laser cutter error E-214").
  3. Your program searches the stored chunks and returns the best 3, say 3 × 300 = 900 tokens, each with manual name and page.
  4. The model reads only those and replies: "E-214 means the exhaust fan isn't detected; check the cable at the back panel (laser manual, p. 62)."

Input for the final call: 1,000 + 900 = 1,900 tokens, or 1,900 × 2 / 1,000,000 = $0.0038. Sending the whole manual instead would be 1,000 + 48,000 = 49,000 tokens, or $0.098. For that final call, that's about 26 times more (0.098 / 0.0038 = 25.8). The search request needs an earlier call of about 1,000 tokens (roughly $0.002) on the retrieval side, so over the whole request the gap is smaller, but still big. The error text and page are made up.

Two ways to search, in plain words. Search by meaning (embeddings) finds text that talks about the same thing in different words. Search by exact words (a method called BM25) finds the same letters and numbers.

"E-214" is the exact-words case: embeddings can miss crucial exact matches (contextual retrieval article). So exact-word search is the better fit for identifiers like error codes.

Trace: the meaning case, "Why does my cut look burnt?"
  1. The student asks, "Why does my cut look burnt?" The window again holds 1,000 tokens of instructions and tools.
  2. The model asks for search_manual("burnt edges on acrylic cut").
  3. No chunk contains the word "burnt". But a search by meaning finds the chunk titled "Scorching and charring: speed and power settings", and returns it with 2 neighbours, say 900 tokens.
  4. The model answers with the speed and power advice and the page number.

Combining both kinds of search with the fix below cut the missed chunks (top-20 failures) by 49% in the article's tests (contextual retrieval article).

Here's the failure to know. A chunk like "Check the cable at the back" loses which machine it is about. The fix is to attach a short note to each chunk saying which manual and section it belongs to (contextual retrieval article).

And a shortcut: if the material is under about 200,000 tokens (about 500 pages), you can include all of it and cache it (contextual retrieval article). Our 48,000-token manual qualifies. A cache read at 0.05 times the example price is 48,000 × 0.10 / 1,000,000 = $0.0048 a call for the manual alone, so about $0.0068 with the 1,000-token base, against $0.0038 for retrieval. The first call also pays a one-time cache write, at 1.25 times the normal input price for a 5-minute cache, and the cache expires (pricing page).

Count the search call too and retrieval is about $0.0058 a request, so on cost the two are close. The real difference is that caching leaves 48,000 tokens in the window on every call, with the context rot from Part 2. So retrieval is the safer pick as manuals pile up, and the shortcut suits one small manual.

Keep light references, like a page number, and load the data on demand with tools instead of carrying everything (Anthropic context engineering). Retrieval and notes are really the same move: both keep text outside the window and load a small piece in when it's needed. That's why both count as memory.

A common mix-up

"Retrieval means the model searches the manual itself." It doesn't. Your program runs the search and returns text, the same rule as the tool loop. The model only sees the chunks that come back.

A common mix-up

"Retrieval always finds the right page." It doesn't. In the article's tests, a baseline setup missed the right chunk in its best 20 about 5.7% of the time (contextual retrieval article). So have the assistant show the page it used, and test with real student questions.

Why it matters: this is how the assistant answers from a long manual within a small budget. Recap: split ahead of time, search per question, load a few chunks, cite the page.

Part 5. Memory: notes the agent saves outside the window 5 min

When a session ends, the window is gone. Anything the assistant must know next visit has to be written down somewhere outside it, and read back in.

Here's one student across two visits, using a memory tool. The file name and the student are made up. The model only asks for file operations, and your program runs them against storage you control (memory tool docs).

Trace: Monday, visit 1
  1. The student says, "I just finished the laser cutter safety training."
  2. The model calls the memory tool: create /memories/students/riley.md with "Laser cutter: trained 2026-11-23. Prefers mornings."
  3. Your program writes the file and returns "File created successfully at: /memories/students/riley.md".
  4. The reply: "Got it, you're cleared for the laser cutter." The session ends and the window is discarded.
Trace: Thursday, visit 2, a new empty window
  1. The student says, "Can I book the laser cutter tomorrow at 9?"
  2. The model calls view /memories/students/riley.md, and your program returns the file text.
  3. The model sees the trained status, calls check_calendar, then book_slot.
  4. The reply confirms the booking.

Two details the short trace skipped. First, your program has to tell the model which student this is, say in the system instructions ("Student: riley"), because a new window starts empty. Second, the model should look in its memory folder before anything else and assume it could be interrupted, meaning the window could be reset at any moment, so a real Thursday starts by viewing /memories (memory tool docs). The API adds that instruction for you.

A second student is a separate file. Say Sam asks about the laser cutter on Thursday: the model views /memories/students/sam.md, finds no laser training, and tells Sam to book the training first. Memory is per student, so the file name carries the student.

Long jobs use the same trick. Write progress notes at the end of a session and read them at the start of the next, which is called structured note-taking (Anthropic context engineering). Memory also keeps what must survive a summary (memory tool docs).

Here's a made-up progress note for a student planning a project across machines: "Done: laser parts booked Friday 9. Next: ask about 3D printer filament. Open question: wood thickness." The next session reads it first, so the work picks up where it stopped.

Notice there are now three kinds of "memory", and they're easy to blur:

KindWhat holds itWho writes itAt session end
Within one callThe windowYour program assembles itGone
Between steps of one requestThe history, resent each callYour program appends each resultGone, unless saved
Between sessionsNotes, files or a databaseThe model asks, your program writesKept

What to save, and what not to

  • Save: training status and stated preferences. Small and stable.
  • Don't save the manual. That belongs to retrieval.
  • Don't save live bookings. They belong to the calendar tool, because notes go stale. A stale note saying "slot free" is the same failure as the outdated chatbot fact from the warm-up.

Two safety lines. Only let the memory tool touch paths under the memory folder, and don't store sensitive information in it (memory tool docs).

A common mix-up

"The model learned my training status, so it will remember." On Thursday the window is empty. Without the file read in step 2, the assistant would ask for training again, or worse, book without checking.

A common mix-up

"Save everything, just in case." Every note read back costs tokens each visit. A 5,000-token notes file read on a call costs 5,000 × 2 / 1,000,000 = $0.01, and adds noise. Keep the directory organized and delete files nobody has opened in a long time (memory tool docs).

Why it matters: it's the difference between an assistant that treats each student as a stranger and one that doesn't. Recap: notes live outside the window, the program writes them, and the model reads them back at the start.

Part 6. Context budget: deciding what goes where 5 min

Now you can place every piece of information in the right spot: in the window, retrieved, or saved. Here is one worked decision, then one for you.

Worked example: the placement table for the assistant
InformationWhereWhy
Role and rules (about 200 to 400 tokens)Always in the windowNeeded on every call, and small
Tool descriptionsAlways in the windowThe model can only call what it can see
Machine manuals (say 48,000 tokens each)RetrievalToo big and mostly irrelevant on any one call
Booking calendarTool call, then clear after useChanges constantly, so a saved copy goes stale
Student training statusNotes file, read at the start of a sessionMust survive the session, and is small

Cost check: with retrieval and clearing, a typical call sends about 3,000 tokens instead of about 50,000. That's an illustration, not a measurement. At $2 per million, 3,000 tokens is $0.006 a call and 50,000 is $0.10.

A common mix-up

"One mechanism should cover everything." Try it. Put the manual in notes and the model writes and rereads 48,000 tokens. Put the calendar in notes and it goes stale. Keep training status only in the window and it vanishes when the session ends.

Summary 1 min

  • Tokens are the unit of reading, writing and cost.
  • The window is everything the model sees on one call, and bigger is not better.
  • Between steps, the program resends the history, so clear or summarize what is no longer needed.
  • Retrieval loads only the passages that answer the question.
  • Notes are files outside the window that carry facts between sessions.
