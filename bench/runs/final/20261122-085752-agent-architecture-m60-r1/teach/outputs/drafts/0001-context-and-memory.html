Context and memory: what an agent can see on each call, and what it can keep

By the end of this lesson you can decide what goes into an agent's context window on each call, what gets saved between sessions, and how it finds one fact in a large body of text.

Objective O3: what the assistant keeps in context, saves between sessions, and how it finds the right page About 60 minutes Builds on the agent loop
Why this matters for you

Your design review will ask three things: what does the assistant keep in context, what does it save between sessions, and how does it find the right page in a long manual. This lesson gives you an answer to each, with numbers you can defend.

It also keeps your sponsor's small model budget in view. Almost every decision here is about cost as much as it is about correctness.

Context window: the text the model can see on one call 9 min

The model knows only the text you hand it on each call, and there is a limit on how much text that can be. So the first thing to learn is what that text is made of and how it is counted.

One word first, because it is how everything is counted. A token is a piece of text that a model reads and writes, usually a few characters up to a short word (my plain-words version of how the pricing page describes tokens). As a rough English rule, 100 tokens are about 75 words (OpenAI help page on tokens).

The exact count depends on the model's tokenizer, the language and the kind of content, so treat that rule as an estimate (pricing page). A short email of 150 words is roughly 200 tokens. A page of a manual, at about 500 words, is roughly 650 tokens by the same rule. In this lesson I use 500 tokens a page to keep the arithmetic clean, so a real manual may run higher. Newer Claude tokenizers can also produce about 30% more tokens for the same text, so count with your model's own numbers.

Worked example: one call, counted

A student types "Is the laser cutter free on Friday?" Your program does not send just that sentence. Here is what actually goes to the model, with made-up round numbers:

  1. The program sends the instructions that tell the assistant who it is and how to behave (the system prompt): 800 tokens.
  2. It sends the tool descriptions for search_manual, check_calendar and book_slot: 600 tokens in total.
  3. It sends the student's question: 30 tokens.
  4. Input total: 800 + 600 + 30 = 1,430 tokens.
  5. The model reads all of it and writes back a tool request, check_calendar for Friday: 40 tokens of output.

In code, the shape is simple. Your program builds these three things and passes them to the model:

system   = "You are the makerspace assistant. ..."             # 800 tokens
tools    = [search_manual, check_calendar, book_slot]         # 600 tokens
messages = [{"role": "user", "content": "Is the laser cutter free on Friday?"}]  # 30 tokens

The messages list is the conversation so far. Right now it has one entry. In the next part you'll watch it grow.

That whole bundle, plus the reply the model writes, has a name. The context window is all the text a model can look at when it writes a response, including the response itself (context windows doc).

Anthropic's engineers describe the same idea as the set of tokens included when sampling from the model (Effective context engineering).

Everything in that bundle counts: the system prompt, every message in the list (tool results included) and your tool definitions. The output the model generates for that turn counts too (context windows doc).

The window has a size limit. Current models go up to 1M tokens, and some other models have 200k (context windows doc).

Sizes and prices change, and they differ by model. When your team picks a model, read its row in the "All models" table of the context windows doc and its price on the pricing page, not this lesson. The 600 tokens for tool descriptions is also a round number: real counts run higher, because tool use adds its own overhead tokens (pricing page). I use Claude's docs because they explain the general idea well, and I'm not claiming every provider works the same way in every detail.

Here is a second call, so the first one doesn't look special. Later the same student asks "What's the maximum acrylic thickness for the laser cutter?" (28 tokens). That is a fresh conversation in a fresh window.

  1. Instructions: 800 tokens.
  2. Tool descriptions: 600 tokens.
  3. The question: 28 tokens.
  4. Input: 800 + 600 + 28 = 1,428 tokens. The model replies with a tool request for search_manual, 40 tokens.

See the pattern? The instructions and tool descriptions are the same 1,400 tokens every time, whatever the student asks. They are a fixed cost of every call you will ever make.

Now cost, because you'll need it in the next part. Providers bill input tokens and output tokens at different rates, and output costs more. For the numbers in this lesson I'll use $2 per million input tokens and $10 per million output tokens, which is the same order as the Claude Sonnet 5.5 row on the pricing page.

Treat those as illustrative. Read the real price for the model you pick before you tell your sponsor a number.

Let's price the first call. Input: 1,430 × $2 / 1,000,000 = $0.00286. Output: 40 × $10 / 1,000,000 = $0.0004. Together that is about $0.0033, a third of a cent.

That's tiny. It stops being tiny once calls repeat, which is the next part.

A common mix-up: "The window is just my message"

It's tempting because the message is the only part you typed. But in the call above, the student's own words are 30 of 1,430 tokens, about 2%. The instructions and tool descriptions are the other 98%.

The docs are explicit that system prompt, messages, tool results and tool definitions all count. So when you design the assistant, an 800-token instruction block is a real cost you pay on every call.

A common mix-up: "Output is free, only the input counts"

It's tempting because the model's words feel like the answer, not the cost. But the 40-token tool request and, later, the 60-token reply both sit in the window and are billed, at the higher output rate: $10 per million against $2 per million for input in our example.

Output is fewer tokens, but each one costs five times as much. Both sides matter for your budget.

Recap for this part: the window is the instructions, the tool descriptions, the conversation and the reply, all counted in tokens. The model sees nothing else. Next: what happens on the second call.

Message history: what is kept between steps, and what it costs 11 min

The model does not remember anything between calls; the program sends the whole history again each time. That is why every step of the loop gets more expensive than the last.

Worked example: two calls for one request

Same request as before, "Is the laser cutter free on Friday?", followed all the way to the answer. Same made-up numbers, same illustrative prices.

  1. Call 1. Input is 1,430 tokens (800 + 600 + 30). The model answers with a tool request for check_calendar: 40 tokens out.
  2. The program runs the tool, not the model (you recalled this in the warm-up). The calendar comes back as a 350-token result.
  3. Call 2. The program adds the model's 40-token request and the 350-token result to the history and sends everything again: 1,430 + 40 + 350 = 1,820 tokens in. The model writes the 60-token reply, "Friday 2 to 4 pm is free."
  4. Input billed for the request: 1,430 + 1,820 = 3,250 tokens. Output: 40 + 60 = 100 tokens.
  5. Cost: 3,250 × $2 / 1,000,000 = $0.0065 for input, plus 100 × $10 / 1,000,000 = $0.0010 for output. Total: $0.0075.

Look at step 3 again. The 1,430 tokens from call 1 were sent a second time. Nothing was "remembered": the program built a longer list and sent it whole.

That is how the API works in general: each turn's input holds all the previous history plus the new message, and the output becomes part of the next turn's input (context windows doc). Tool requests and tool results count as input tokens when they are sent back (pricing page).

Now the follow-up. A minute later the student says "Book 2 pm.", 20 tokens. That new call includes everything before it: 1,820 (the last input) + 60 (the reply) + 20 (the new message) = 1,900 tokens before the model writes a word.

Each new call starts higher than the one before. A long chat is a staircase.

A longer request: three calls

Suppose the student asks "Is the laser cutter free Friday, and what's the maximum acrylic thickness?" Two tools are needed, so there are three calls. The manual search returns a 900-token result, a number you'll earn in part 4, and the final reply is 80 tokens.

  1. Call 1: 1,430 in. The model asks for check_calendar (40 out).
  2. Call 2: 1,430 + 40 + 350 = 1,820 in. The model asks for search_manual (40 out).
  3. Call 3: 1,820 + 40 + 900 = 2,760 in. The model writes the 80-token reply.
  4. Input billed: 1,430 + 1,820 + 2,760 = 6,010 tokens. Output: 40 + 40 + 80 = 160 tokens.
  5. Cost: 6,010 × $2 / 1,000,000 = $0.01202, plus 160 × $10 / 1,000,000 = $0.0016. Total about $0.0136.

One extra tool step nearly doubled the cost of the request: from $0.0075 to $0.0136. Every step is another full read of the history.

Second contrast: paste the whole manual in

Suppose the team skips all cleverness and pastes the laser cutter's whole manual into the prompt. Made-up numbers again: 120 pages at about 500 tokens a page is 60,000 tokens. (That 500 is my own round number, not a measured one.) Go back to the two-call request from the first example.

  1. Call 1 input: 1,430 + 60,000 = 61,430 tokens.
  2. Call 2 input: 1,820 + 60,000 = 61,820 tokens.
  3. Total input across the request: 61,430 + 61,820 = 123,250 tokens.
  4. Cost: 123,250 × $2 / 1,000,000 = $0.2465 for input, plus the same $0.0010 for output = $0.2475.
  5. Compare: $0.2475 / $0.0075 = 33 times more for the same answer.

That 33 is my arithmetic on made-up numbers, not a benchmark. The direction is what matters: stuffing material into every call multiplies your bill by the number of calls. Hold that thought, because part 4 is the fix.

Prompt caching makes a repeated prefix cheaper: reads cost a fraction of the normal input price, 0.1× on most models and 0.05× on Sonnet 5.5 (pricing page). But cached text still takes up room in the window: caching changes what you pay for those tokens, not whether they count (context windows doc). I won't teach caching further here.
A common mix-up: "The model remembers the earlier steps by itself"

It feels that way because the chat reads like a conversation with someone who listens. But try it: delete the 350-token calendar result from the list before call 2. The model can no longer know which Friday slots are free, because it is a function of the text it receives (that's your record 0001: text in, text out).

The model does not change while you chat. What looks like memory is the program resending the list. That is my plain-words explanation, and it follows from how the API resends history, shown above.

A common mix-up: "Cost is per question"

It's tempting because the student asked one question and you picture one charge. But cost is per call, and each call re-reads the whole history. In our first trace the student asked once, yet you paid for 3,250 input tokens, not 1,430.

When you estimate your budget, count calls per request first, then tokens per call.

Check yourself

Call 2 of a request carried 1,820 input tokens. The model then asks for another tool, and that tool returns a 500-token result. Roughly what does the next call carry compared with call 2?

Show the answer

Over 2,300 tokens. The program resends the 1,820 tokens of history and adds the model's new tool request and the 500-token result, so every call costs more than the one before.

Recap: the model never keeps anything; the list does, and the list is resent in full. Two consequences: cost is per call, and a long history makes every future call heavier. Next: why heavier is also worse, not just pricier.

Context rot and trimming: keeping the window small and useful 10 min

A bigger window does not mean better answers, because the model gets worse at using text as the window fills. So you keep the smallest set of useful text in it and trim the rest as the work goes on.

Worked example: a long session, three options

A student spends 40 turns setting up a series of bookings. Made-up numbers: by call 40 the history is 38,000 tokens, and 30,000 of those are old tool results, such as calendar dumps of 350 tokens each that were fetched again and again, plus long manual pages.

  1. Do nothing. Every further call carries 38,000 tokens. At $2 per million, that is 38,000 × $2 / 1,000,000 = $0.076 of input for each call, before the model writes anything.
  2. Clear old tool results. Drop the 30,000 tokens of old results, and leave a one-line record such as "calendar checked for Friday". The history falls to 38,000 − 30,000 = 8,000 tokens, so the next call costs 8,000 × $2 / 1,000,000 = $0.016. That saves $0.060 on every remaining call.
  3. Compaction. Replace the 40 turns with a summary of about 600 tokens: "booked Fri 2 pm laser; student prefers mornings; waiting on safety training". Restart with that summary, the 1,400 tokens of instructions and tools, and the last few turns, say 2,000 tokens. The window is now about 4,000 tokens, and a call costs about $0.008.
  4. Over ten more calls: doing nothing costs 10 × $0.076 = $0.76, clearing costs 10 × $0.016 = $0.16, and compaction costs 10 × $0.008 = $0.08. Sub-dollar numbers, but multiply by every student, every day.

Step 2 has a name: clearing means removing old tool results from the history once you no longer need them. It's one of the safest, lightest-touch ways to trim, because an old result can usually be fetched again if it is needed (Effective context engineering).

Step 3 has a name too: compaction means summarizing a long conversation and starting a fresh window from the summary. Claude Code does this, and keeps the summary plus the five most recently accessed files (same article).

Here is what clearing does to the list itself, since you'll write this part. Before: the message list holds the question, then five calendar results of 350 tokens each, then the replies in between. After: the same list, except four of the five calendar results are replaced by the one-liner "[calendar result removed; call check_calendar again if needed]".

The model still sees that a calendar check happened. It just doesn't carry the 1,400 tokens of old slot data around.

Why bother trimming if the window is huge? Because of context rot: as the token count grows, accuracy and recall get worse (context windows doc).

One way to picture it is an "attention budget": the model has only so much attention to spend, and every extra token spends some of it. So the aim is the smallest set of high-signal tokens that gets the job done (Effective context engineering).

Each option loses something. Clearing loses the old results, so if you need them you pay for another tool call. A summary can drop a detail, and the model will not know it was dropped.

My own advice, not a sourced rule: when you tune a summary, check first that it keeps every fact you would be hurt to lose, and only then make it shorter. A short summary that misses something does damage, and a slightly longer one costs a fraction of a cent per call.

Compaction and tool-result clearing also exist as built-in features of the API: the docs list server-side compaction (a beta) and context editing, which includes tool result clearing. The memory tool doc sums up the difference: context editing clears specific tool results on the client, and compaction summarizes the whole conversation on the server (memory tool doc). You can also write either one yourself in a few lines of Python.
A common mix-up: "Bigger window means I can stuff everything in"

It's tempting because a 1M-token window sounds like infinite room. But you still pay for every token on every call (that's the 33× from part 2), and recall degrades as the window fills.

Try it with the numbers: filling just 100,000 tokens of a 1M window costs 100,000 × $2 / 1,000,000 = $0.20 of input on a single call, and that repeats on every call after it. The size is a ceiling you must stay under, not a target to fill.

A common mix-up: "Summaries lose nothing"

It's tempting because a summary reads smoothly. But suppose the summary says "booked Fri 2 pm laser; prefers mornings" and leaves out "has not finished the safety training". The assistant could then book a machine the student cannot use.

A summary is a guess about what matters. Check it against the facts that gate real decisions.

Check yourself

A session has a 20,000-token history, of which 15,000 tokens are old calendar results the student will not need again. Which trim is the lightest-touch fix?

Show the answer

Clear the old calendar results and leave a one-line note. It cuts 15,000 tokens, keeps the conversation, and the results can be fetched again.

Recap: more text is not better, because recall degrades and every token is paid for. Clear what you can fetch again, summarize when you must, and check the summary for the facts you cannot afford to lose. Next: the opposite problem, material too big to put in at all.

Retrieval: fetching only the page that matters 12 min

When the material is too big to put in the window, keep it outside and pull in only the few pieces the question needs. Retrieval is how the assistant finds the right page in a long manual.

Worked example: finding the laser settings

A student asks "What speed and power for 3 mm acrylic on the laser cutter?" The laser cutter manual is the made-up 120 pages, 60,000 tokens.

  1. Offline, before any question. The program splits the manual into chunks, pieces of about 300 tokens each, and builds an index. 60,000 / 300 = 200 chunks.
  2. The model calls the tool. It writes search_manual("3 mm acrylic speed power laser").
  3. The program scores the 200 chunks against that query and returns the top 3, about 900 tokens, each tagged with the manual's name and page.
  4. The model reads them and replies with the setting and the page it came from.
  5. The saving. 900 / 60,000 = 1.5% of the manual, so about 98.5% fewer manual tokens on the call than pasting the manual in.

That's retrieval: keep the big material outside the window, search it, and put only the best-matching pieces into the window. Cutting a knowledge base into chunks of no more than a few hundred tokens is the standard first step (Introducing Contextual Retrieval).

The model never sees the other 197 chunks. They stay in your files.

How does the program "score" a chunk? There are two common ways, and they catch different questions.

Take a second case. A student types "error E-12". That code is invented for our sample manual. BM25 is a scoring method that looks for exact words and phrases, so it nails this one: the chunk containing "E-12" ranks first (contextual retrieval post).

Now a student types "my cut edges look burnt". The manual might say "scorching" or "charring", never "burnt", so exact words miss it. Embeddings turn text into numbers that capture meaning, so a search by embeddings finds the chunk about scorching because it means the same thing (contextual retrieval post).

Combining both beats embeddings alone (contextual retrieval post). A sensible first design for your manuals is to run both and merge the results.

Second trace: the exact-word query

The same machinery, on the invented error code.

  1. Student: "The laser cutter shows error E-12. What do I do?"
  2. Model: search_manual("error E-12 laser cutter").
  3. The program scores all 200 chunks. The chunk titled "Error codes, page 88" contains "E-12" and scores highest, and two neighbouring chunks about the cooling system follow.
  4. The program returns those 3 chunks, about 900 tokens, each tagged "Laser cutter manual, page N".
  5. Model: "E-12 means the cooling water flow is low. Check the tank level (manual, page 88)."

Only 900 manual tokens crossed into the window. The other 59,100 never did.

One more knob. Top-k is how many chunks you hand to the model. Too few, and the answer may not be among them. Too many, and you refill the window you just emptied.

Here is the trade at 300 tokens a chunk, with input at $2 per million:

Top-kManual tokens sentInput cost per call for the manual part
3900$0.0018

All 200 (pasted)60,000$0.1200

In Anthropic's test, passing the top 20 chunks worked better than the top 10 or the top 5 (contextual retrieval post). That's one result on one test set, not a rule. For your manuals, try a few values of k on real student questions and watch both answer quality and token cost.

Do you need retrieval at all?

Here is a decision rule. If your whole knowledge base is under about 200,000 tokens, you can put it in the prompt and use prompt caching, with no retrieval at all (contextual retrieval post). Pages are my own conversion: at 500 tokens a page, 200,000 tokens is a few hundred pages.

Check it against the makerspace. One 60,000-token manual would qualify. The 15 manuals, at 900,000 tokens in my made-up example, do not, so retrieval is needed.

Even for the single manual, remember part 2: pasting it cost about 33 times more in our trace, even before caching discounts. So the team should still run its own numbers.

There's also a "just-in-time" version. The agent keeps light pointers, such as a manual name and page number, and loads the actual page only when it needs it (Effective context engineering).

A trace: the search returns "Laser cutter manual, page 47: acrylic settings" as a pointer with a two-line excerpt. If the excerpt is not enough, the model asks for page 47 in full, about 500 tokens, and nothing else. A hybrid is common too: fetch a few things up front for speed, and let the agent explore for more (same article).

A common mix-up: "Retrieval means the model searched its memory or the web"

It's tempting because the answer appears out of nowhere. But search_manual is a tool your program runs on the makerspace's own files, the same loop you already know. The model sees only the three chunks it returns.

If a manual is not in your index, the assistant cannot find it, however famous the machine.

A common mix-up: "The top result is always the right one"

It's tempting because the search ranks results. But a chunk that says "reduce speed to 60%" with no machine name can be returned for the wrong machine. Anthropic's post shows the same trap: a chunk saying a company's revenue grew by 3% names no company and no period (contextual retrieval post).

A cheap fix of my own, not the post's method: tag every chunk with its manual and section before you index it, and show those tags to the model.

Memory across sessions: notes the agent writes and reads 12 min

When a session ends, the window is gone. Anything the assistant should know next time has to be saved outside the window and read back in, either as notes it writes or as records it looks up.

Worked example: two sessions, one student

This trace is my own illustration of how the memory tool's pattern would look in your assistant. Session 1, Monday. Riley says "I prefer morning slots and I finished the laser safety course."

  1. The model first checks for notes: it calls the memory tool with view /memories. (The memory tool's protocol is to view the memory folder before doing anything else.)
  2. The program returns an empty folder. That is not an error: it just means a first session.
  3. The model creates /memories/students/riley.md with one line: "prefers mornings".
  4. The session ends and the window is discarded.

Session 2, Thursday.

  1. A new window opens with only the instructions, the tool descriptions and Riley's first message: 1,430 tokens.
  2. The model views /memories, finds riley.md (about 30 tokens) and reads it. The window is now 1,430 + 30 = 1,460 tokens.
  3. Riley asks for a slot, and the assistant offers a morning one.

Memory here means files that persist between sessions, kept outside the window; the notes are what the model writes into them. The memory tool is built exactly like this: the model asks for file operations under /memories and your application runs them and returns the result (memory tool doc).

The general pattern is called structured note-taking: the agent regularly writes notes that persist outside the window, and reads them back later (Effective context engineering). It holds up on long tasks: the article's example is an agent playing Pokemon that keeps precise tallies across thousands of game steps.

A third session: changing a note

Notes go stale too, so the model also has to update them. Next Monday, Riley says "Mornings don't work anymore, I have a class. Afternoons from now on."

  1. The model views /memories and reads riley.md: "prefers mornings".
  2. It sees the conflict with what Riley just said.
  3. It edits the file with a str_replace command: "prefers mornings" becomes "prefers afternoons (changed in week 6)".
  4. The window for this session so far: 1,430 + 30 = 1,460 tokens, then a few tokens more for the edit.

The newest thing the student said wins, and the file stays one line long. A note that only ever grows eventually costs more than it helps.

Not everything belongs in a note

Look back at what Riley said on Monday: a preference and "I finished the laser safety course". The note we wrote stored only the preference. That was on purpose.

A lookup is a tool that reads the current answer from the real record each time, instead of trusting a saved copy. Here, check_training(student_id) reads the team's database. A note written Monday can be stale by Thursday, and a wrong "yes" lets someone use a machine unsafely.

My rule of thumb, which is my own advice and not from a source: notes are for soft, useful, low-risk facts, such as preferences and what was already tried. Lookups are for facts that change or that gate safety.

Practical points on the memory tool. It is client-side, so your program decides where the files live, in a folder or a database, and it must allow only paths under /memories: a path like /memories/../../secrets.env is an attack you have to block. Cap how big a file can grow, and delete files nobody has opened in a long time. The tool has six commands: view, create, str_replace, insert, delete and rename (memory tool doc). Whether to keep per-student notes at all is a privacy question for your team to decide.

The memory doc also sketches a pattern for long jobs that span many sessions: keep a progress log, and let each new session open by reading it (memory tool doc). It pairs well with compaction from part 3: summarize inside a session, and save the lasting bits as notes.

A common mix-up: "Memory means the model learned something"

It's tempting because Thursday's offer feels like the assistant got to know Riley. But after Monday the model itself has not changed. Thursday's morning slot came from a 30-token file read into a fresh window.

Test it: delete riley.md before Thursday and the morning offer disappears, even though the model is exactly the same. That's my plain-words framing; the mechanism is files that your app reads and writes.

A common mix-up: "Everything the assistant knows about a student should go in notes"

It's tempting because one place feels tidy. But say Monday's note reads "completed laser safety course", and the safety record shows the certificate expired on Wednesday. By Thursday, the note is wrong, and the assistant would book a machine Riley may not use.

That is why training status comes from the lookup, and the note holds only soft facts.

Designing the assistant's context: worked example, then your turn 12 min

Now put the pieces together: for each thing the assistant needs, decide whether it sits in the window, is retrieved, is a note, or is a lookup. Do one together, then one yourself.

Worked example: book the laser cutter and remember a preference

The request: "Book the laser cutter for 3 mm acrylic on Friday afternoon and remember I like mornings." Go need by need, using the four places from the table in part 5.

  1. The assistant's instructions. In the window, always: 800 tokens.
  2. The tool descriptions. In the window, always: 600 tokens.
  3. Acrylic advice from the manual. Retrieve. Top 3 chunks, 900 tokens, instead of 60,000.
  4. Friday's slots. Calendar tool, a 350-token result. Once the booking is made, clear that result from the history (part 3).
  5. Riley's training status. A lookup, fresh, never a note.
  6. "I like mornings." Write a note to /memories for next time.

Now tally the window for the final call. I simplify: count one 40-token tool request, and lump the booking confirmation and the small training-lookup answer into 60 tokens.

1,430 (instructions, tools and question) + 40 (a tool request) + 900 (manual chunks) + 350 (calendar result) + 60 (confirmation and lookup) = 2,780 tokens.

Pasting the manual instead would start above 60,000 tokens on every call. That's more than 20 times the 2,780, before the history even grows.

Notice the pattern. Only the first two items are always in the window. Everything else is fetched when needed, trimmed when finished, or kept outside.

And the price: 2,780 × $2 / 1,000,000 = $0.00556 of input for that last call, against $0.12 for the manual alone if you pasted it. That gap is the budget argument you'll make at your review.

Step 3 (blank). Add up the input of the last call from these numbers: system 800, tools 600, question 40, three manual chunks 900, calendar result 350, training result 60, and three tool requests of 40 each.

Three tool requests of 40 is one product to compute first. Then add the seven groups, one at a time, keeping a running total.

Show the solution

Step 2. (b) retrieve: the blade advice is in a big manual, so fetch the top chunks. (c) calendar tool: a current result, 350 tokens, cleared when you're done. (d) lookup: check_training reads the record fresh. No need here is a note, because nothing soft was said about Sam.

That's your process for any new request: list the needs, put each in its place, and add up the window so you know what a call costs. Run it on the real requests your team expects before the design review.

Check yourself

The final call's tally is 2,870 tokens. The team wants it under 2,300 without losing the manual advice. Which change helps most?

Show the answer

Return fewer chunks. Top 1 instead of top 3 saves 600 tokens (2,870 to 2,270), and the manual advice stays. A bigger window does not shrink what you send. Fewer chunks does carry a risk that the answer is missing, so test it on real questions.

Recap: window for what is always needed, retrieval for big outside material, notes for soft facts that outlive the session, lookups for facts that change or gate safety. That's the whole design vocabulary for this objective.

Summary
  • The model sees only the window: instructions, tool descriptions, history, tool results and its own reply, all counted in tokens.
  • The program resends the whole history on every call, so cost and clutter grow with every step.
  • Trim: clear old tool results, summarize when you must, and keep only high-value tokens.
  • Retrieve: keep big material outside and fetch the few pieces needed.
  • Remember: save low-risk notes outside the window, and look up anything that changes or gates safety.

Say it in your own words: in two sentences, explain why the assistant can book Thursday's slot correctly even though Monday's window is gone. Try it before you scroll up.

Why it matters: every token you send is paid for on every call, so deciding what sits in the window, what is fetched and what is saved is how your team keeps the assistant correct and inside its small budget. One simplification to remember: the memory and training tools add to the tool descriptions, so real windows run a bit above this lesson's round numbers.
