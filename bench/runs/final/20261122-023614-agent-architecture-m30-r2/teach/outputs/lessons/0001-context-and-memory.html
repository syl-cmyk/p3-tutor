Lesson 1 · 30 minutes

Context and memory: what the model sees on each call and what the agent keeps

By the end of this lesson you can decide, for any piece of information an agent needs, whether it belongs in the context window, in a saved note, or in a searchable store that is looked up only when needed.

Objective O3: what the assistant keeps, saves and looks up About 30 minutes Builds on: the agent loop
Why this matters for you

Your makerspace assistant has to answer from long manuals, remember each student's training status, and stay inside a small budget. All three come down to one choice: where each piece of information lives.

Here's the whole idea in two lines. An agent's model sees only the text sent on each call, and memory is whatever you save outside that text and send back in later.

Now a failure. On Monday a student called Priya tells the assistant she finished the laser cutter safety training. On Wednesday she opens a new chat:

Priya (Monday):    I passed the laser cutter safety training.
Priya (Wednesday): Can I book the laser cutter?
Assistant:         I don't see any training on record, please complete it first.

Why did it forget? That is today's lesson.

Context window: everything the model can see on one call 5 min

The model knows only what is in the text it is handed on each call, and that text has a size limit. So before anything about memory, you need to know what counts as "handed over" and how it is measured.

The measure is the token: a chunk of text, roughly three-quarters of an English word on average (a rule of thumb, not an exact rate). "Is the laser cutter free on Friday?" is 7 words and about 9 tokens.

The context window is all the text the model can reference when it writes a response, including the response itself. It is the model's working memory, not what it learned in training (Context windows docs). The context is whatever text is actually in the window on this call.

Worked example: one call, packed (illustrative numbers)

The student asks "Is the laser cutter free on Friday?" Here is everything on that one call:

  1. System prompt (the standing instructions you write for the model): "You are the makerspace assistant. Be brief. Never book without checking the calendar." A realistic full prompt is longer; we'll say 800 tokens.
  2. Tool descriptions: check_calendar and book_slot, written out so the model knows how to ask for them. 600 tokens together.
  3. The student's message: "Is the laser cutter free on Friday?" About 9 tokens.
  4. Model's reply: a request to run check_calendar. About 40 tokens, and it counts too.

Going in: 800 + 600 + 9 = 1,409 tokens. Coming out: 40. The window holds input and output together, and the system prompt, every message, tool results, tool definitions and the output all count (Context windows docs).

Look at what's in that bar. Only the 9-token message came from the student, and the rest is your design: the instructions you wrote and the tools you described. You'll pay for those 1,400 tokens on every single call.

Windows are big on current models, up to about a million tokens, depending on the model. The limit is still real, and as you'll see in a minute, every token in it has a price.

A common mix-up

"The model remembers the earlier chat, because it was trained on it or has it stored somewhere." It's a tempting idea, because chatbots feel like they remember. Try this: call the model once with only "My name is Priya", then call it again with only "What is my name?"

The second call has no name anywhere in it, so the model can't know it. It "remembers" only when your program sends the first message again. That fits what you already know: the model's knowledge is its training plus the text it is given.

Why it matters: everything you want the assistant to know on a call has to be written into this window by your program.

Context accumulation: what is kept between steps, and what it costs 6 min

Inside one request, the agent loop keeps adding to the window, because every step is a new call that gets sent the whole history again. That growth is what you pay for and what makes the model worse, which is why what stays in the window is a design choice.

"Kept between steps" means the message history your program re-sends on each call. The model itself keeps nothing, so each call's input is all the previous history plus the new message (Context windows docs).

Worked example: three calls for one request (illustrative numbers)

The student says: "Is the laser cutter free Friday, and book 2 pm if so." That message is 25 tokens. The base from Part 1 is still 800 + 600 = 1,400.

  1. Call 1 input: instructions 800 + tools 600 + message 25 = 1,425. The model replies with a request for check_calendar (40). The window now holds 1,465.
  2. The program runs the tool. The result is Friday's slot list for the laser cutter as JSON: 300 tokens.
  3. Call 2 input: everything from call 1 (1,465) + the tool result (300) = 1,765. The model replies with a book_slot request (45). The window holds 1,810.
  4. The program runs book_slot. The result, "Booked, Fri 2 pm", is 15 tokens.
  5. Call 3 input: 1,810 + 15 = 1,825. The model writes the final answer (35). The window ends at 1,860.

Add up what you sent: 1,425 + 1,765 + 1,825 = 5,015 input tokens across the three calls. The window at the end holds only 1,860. The same text was sent again on each call, so cost grows faster than the window does.

Try a "what if". Suppose the slot list had been 3,000 tokens, not 300, because the calendar tool returned the whole week. Calls 2 and 3 would each carry 2,700 extra tokens, so the input total would be 5,015 + 5,400 = 10,415. One chatty tool result roughly doubled the bill.

Check your provider's price list, because input and output tokens usually have different rates, so both columns matter for your budget. Prompt caching can lower the price of repeated text, but it changes what you pay for those tokens, not whether they count (Context windows docs). We won't go into caching here.

Cost is only half the problem. As the window fills, the model's accuracy and recall get worse, an effect called context rot (Context windows docs). The model has a limited attention budget, so the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering).

You have three ways to shrink what is kept, and you'll mostly use the first one:

  • Clear old tool results. Once the slot list has been used, drop it from the history. This is among the lightest forms of trimming (Effective context engineering).
  • Summarise earlier steps. Replace a long stretch of history with a short summary of it. This is called compaction.
  • Keep a pointer, not the whole thing. Keep a file name or a manual page number, and load the content only if a later step needs it.
A common mix-up

"A bigger window means I can stop caring what goes in." It's tempting because a million tokens sounds endless. Say the assistant pastes the whole 40-page laser cutter manual, about 20,000 tokens, into every call of the example above.

The input bill goes from 5,015 to about 65,000 tokens (5,015 + 3 x 20,000), and the answers can get worse, not better, because of context rot.

A common mix-up

"You pay for each token once." Look at the numbers again: the window ends at 1,860, but you paid for 5,015 input tokens. The slot list alone was 300 tokens in the window, and it was sent on calls 2 and 3.

Why it matters: your budget is per token, so the cost of a request is set by what you keep in the window and how many steps the loop takes.

Persistent memory: what is kept between sessions 6 min

When a session ends, the window is gone, so anything the assistant should know next visit has to be written down outside it and read back in. That is all "memory" means for an agent: notes that live outside the window.

A session is one conversation from start to end, with one window. Memory is information saved outside the window and loaded back when it's needed. Let's fix Priya's problem.

Worked example: Priya across two visits (illustrative numbers)

The store is one small file per student, students/priya.json.

Monday, session 1:

  1. Priya says: "I passed the laser cutter safety training."
  2. The model asks to call save_note(student="priya", text="student says she passed laser cutter safety training, Mon 16 Nov, not yet checked with instructors").
  3. Your program writes that line into the file and returns "saved".
  4. The model replies: "Got it, I've noted that." The session ends and the window is thrown away.

Wednesday, session 2, empty window:

  1. Your program starts by reading students/priya.json and putting its 40 tokens into the window. (Or the model calls a read_notes tool.)
  2. Priya says: "Can I book the laser cutter Friday at 2?"
  3. The model sees the note. Because it says "not yet checked", the model first calls a check_training tool that reads the instructors' record, then check_calendar, then book_slot, and the reply confirms the booking. The note told it what to look for, and the instructors' record is what it trusts.

The note costs about 40 tokens. Replaying all of Monday's chat on every visit would cost something like 1,800.

Notice who does the work. The model only asks for a read or a write, and your program carries it out, exactly like any tool in the agent loop. This is called client-side memory (Memory tool docs).

What if Priya passes the 3D-printer training next week? The model calls save_note again, and the file now holds two lines, about 80 tokens. Notes grow a little with every visit, so keep them short and drop what's no longer true, or they'll slowly turn into the Part 2 problem.

The agent writing its own notes, then reading them back later, is called structured note-taking (Effective context engineering). Anthropic's memory tool is one ready-made version of it: the files live under a /memories directory, and the model looks at that directory before it starts a task. Your program decides where the files really live, and it has to check every path so the model can't reach outside that directory (a "directory traversal" attack) (Memory tool docs).

Keeping each student's notes in a separate file is our own advice, not something the docs promise: it also keeps one student's note out of another's window. For agents that span several sessions, design your saved state so that picking it back up is fast (Context windows docs).

A common mix-up

"The model learns from our chats, so it will remember next time." It feels that way, but nothing in the model changes between Monday and Wednesday. With an empty Wednesday window it answers "no training on record", exactly the failure we opened with.

A common mix-up

"Memory means storing the whole conversation." Monday's chat was about 1,800 tokens and the note is 40. Replaying everything makes you pay for every old token on every visit, and it also fills the window, as in Part 2.

A common mix-up

"The model's note is the truth." If a student says "I'm certified on the laser cutter" and no instructor has signed off, writing it down just stores a wrong note. For a safety gate, have the assistant read the instructors' records with a tool, not trust a self-reported note.

Recap: the window is for this visit and vanishes. Notes are for next time and stay. And this solves the "remember each student's training status between visits" requirement with a few lines of Python and a file or a database row.

Retrieval: finding the right page in a long manual 7 min

The manuals are far too long to put in the window on every call, so the assistant looks up only the few passages that match the question. This is the third place information can live: a store you search, not one you carry.

Retrieval means searching a store and putting only the best matches into the window. To make a manual searchable, you split it into chunks, pieces of a few hundred tokens each (Contextual Retrieval). Our own advice: keep each chunk with its page number, so the assistant can cite it.

Worked example: the laser cutter manual (illustrative numbers)

Setup, done once before any student asks: the 20,000-token manual is split into about 60 chunks of about 330 tokens each, each tagged with its page. Then a student asks a question.

  1. The student asks: "What's the max material thickness for the laser cutter?"
  2. Your program (or a search_manuals tool the model calls) turns the question into a search and scores every chunk against it (a score is just how well a chunk matches the question; more on that below).
  3. The 3 best-matching chunks come back, about 330 tokens each, so about 1,000 tokens in total. Each is labelled, for example "laser_cutter_manual p.14".
  4. Those 3 chunks go into the window, and the model answers with the page cited: "Up to [thickness from the chunk] (manual p. 14)". The real limits come from your real manual, so never copy a number from an example like this one.

Compare with Part 2: about 1,000 tokens per lookup versus 20,000 for the whole manual. That's about 20 times fewer input tokens on each call.

How many chunks should come back? Three is our illustrative choice. Five would cost about 1,650 tokens and make it likelier that the right page is among them, while one is cheaper but riskier. It's a dial you tune against your budget.

Scoring "against the question" can work in two ways. Search by meaning (embeddings) finds chunks that talk about the same thing, even in different words. Search by exact words (keyword search, often BM25) finds chunks that contain the same string.

Now a second case. The student types "Error E-214" (a made-up code, for this example). Search by meaning might return general error-code pages, while search by exact words finds the string "E-214" itself. Using both together works better than meaning alone; Anthropic's own example is a query for "Error code TS-999" (Contextual Retrieval).

Retrieval has a weak spot: a chunk can lose what it refers to. A chunk saying "The company's revenue grew by 3% over the previous quarter." doesn't name the company or the quarter (Contextual Retrieval). For us that means keeping the machine name and the section title with every chunk, so "max thickness is 6 mm" (a made-up value) never floats free of "laser cutter".

There's a related idea for agents, just-in-time retrieval: keep a light reference, like a file path, and load the content only when it's needed. The trade-off is that looking things up at runtime is slower than having it ready, and the model needs good guidance on when to look (Effective context engineering).

A common mix-up

"Retrieval means the model has learned the manual." Update the manual last week and the assistant finds the new text the same day, with no retraining, because you changed the store, not the model. That is also the fix for the outdated-fact problem you noticed with chatbots.

A common mix-up

"Retrieval always returns the right page." The search returns the 3 nearest chunks even when none is relevant. Ask about a machine that isn't in the manuals and you still get 3 chunks, so the assistant needs an instruction to say "not found" when the passages don't answer the question.

A common mix-up

"We must build retrieval." Not always: if the whole knowledge base is under about 200,000 tokens (roughly 500 pages), you can put all of it in the prompt, and prompt caching makes that faster and cheaper (Contextual Retrieval). At 20,000 tokens per manual that's a real option, but with our small budget the cost line from Part 2 still applies. It's a trade-off, and the choice is yours.

Why it matters: this is how the assistant finds the right page in a long manual without carrying the whole manual on every call.

Placement: deciding what goes in the window, in notes, or in a search store 8 min

Now you have three places information can live, and each trades cost for convenience. The skill is picking one for each thing the assistant needs.

The rule, in four lines:

  • In the window: what's needed on almost every call and is small, like instructions, tool descriptions and today's request.
  • In notes: small facts about one person or one task that must survive the session, like a student's training status.
  • In a search store: large reference material where each question needs only a little of it, like the manuals.
  • Check three things: how big it is, how often it's needed, and whether it's per person. The task matters too: compaction suits long back-and-forth, and note-taking suits work with clear milestones (Effective context engineering).

A common mix-up

"Pick one memory method for everything." Put the manual in notes and you read a 20,000-token note on every visit. Put the calendar in the window as a saved copy and you hold a stale 4,000-token copy that's wrong an hour later. Each wrong placement has a visible cost in the numbers above.

Why it matters: this is the design-review argument you'll have to defend: what the assistant keeps in context, what it saves, and how it finds the right page.

Summary and go further 3 min

There are three places information can live, and the window is the only one the model sees directly. So the job is choosing, call by call, what to put in it.

  • The model sees only the window on every call, and everything in it costs tokens.
  • Within a request, the loop re-sends the history at each step, so cost and clutter grow. Keep only what the next step needs.
  • Between sessions, only what you save outside the window survives. Keep notes small and per person.
  • For big reference material, retrieve a few passages per question instead of carrying the whole thing.
  • Choose the place by size, how often it's needed, and whether it's per person.

Say it in your own words: explain to a teammate why the assistant forgot Priya's training on Wednesday, and which of the three places you would use to fix it.

The opening failure now has a plain answer. Wednesday's window was empty, and nothing had been saved outside it. A small note, read in at the start of the visit, is all it takes.

Why it matters in the real world: the cost per request and the memory design are exactly what you'll defend at the design review in five weeks.
