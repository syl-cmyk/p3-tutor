Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can take a piece of information an agent needs and decide whether it belongs in the context window, in saved notes between sessions, or in a store that gets searched on demand.

An agent's context is the text the model is handed on a call. Its memory is whatever the program keeps and hands over again later.

Why this matters for you

Your makerspace assistant has to answer from long manuals and remember each student's training status between visits. This lesson shows where each of those goes.

A token is a small chunk of text, a rough rule of thumb being three-quarters of a word. Windows are counted in tokens. The counts below are made up to show the arithmetic; real ones depend on the model.

Warm-up

In the agent loop, who runs the tool: the model or the program?

Check your answer

The program. The model only asks; the program runs the tool and sends the result back.

Context window: what the model can see on one call

The model can only use the text it is handed on each call, and that text has a size limit. So every call, someone is choosing what goes in.

Trace: one question
  1. The student asks: "How thick can the laser cutter cut acrylic?"
  2. The program builds call 1: instructions (the system prompt) 800 tokens, three tool descriptions 600, the question 18. That is 1,418 tokens.
  3. The model picks search_manual("laser cutter acrylic max thickness"), about 30 tokens.
  4. The program runs it. A 350-token manual passage comes back: "Acrylic: up to 10 mm at 60 W."
  5. Call 2 sees everything so far: 1,418 + 30 + 350 = 1,798 tokens. Reply: "Up to 10 mm. Thicker sheets need the other cutter."

That whole pile is the context window: everything the model sees on one call, counted in tokens. It has a ceiling, and even below it the model recalls the contents less accurately as it fills, which is called context rot (Anthropic Engineering).

A common mix-up

"The model looks things up in the manuals by itself." It looks that way, but the 10 mm figure arrived only because the tool result was added to the window. Without the search, the model would guess from training.

Message history: what is kept from one step to the next

Between steps, the model keeps nothing on its own. The program sends the whole conversation again each time, so the window keeps growing unless you trim it.

Trace: "Book the laser cutter for me on Friday afternoon."
  1. Call 1 input: 1,418 tokens. The model picks get_calendar(laser_cutter, Friday).
  2. Result: free 10:00 to 12:00 and 14:00 to 15:00, 120 tokens.
  3. Call 2 input: 1,418 + 30 + 120 = 1,568 tokens. The model picks book_slot(laser_cutter, Friday 14:00, 1 h).
  4. Result: "Confirmed, booking #4412", 40 tokens.
  5. Call 3 input: 1,568 + 30 + 40 = 1,638 tokens. Reply: "You're booked Friday 14:00 to 15:00, booking #4412."
  6. Input tokens read across the three calls: 1,418 + 1,568 + 1,638 = 4,624.

Each step is a separate call. "Memory" inside a conversation is just the program re-sending the history. By this arithmetic (the lesson's own; real pricing varies), the input tokens you pay for across a task add up faster than the conversation grows: 4,624 read, against 1,638 at the end. That matters on a small budget.

A common mix-up

"The model remembers step 1 because it was just there." If the program forgot to re-send the calendar result, call 3 would see only the question and have no 14:00 slot to book.

Context limits: what to do when the window fills up

A long session fills the window with old results the model no longer needs. So you trim or summarize them, rather than count on a bigger window.

Trace: a staff member checks 20 machines
  1. Each calendar result is 2,000 tokens. After 20 checks, the history holds 40,000 tokens of old calendars, and the one booking that matters is buried in them.
  2. Fix A, clear old tool results: drop the 20 calendars and keep a one-line record of each, like "get_calendar(laser_cutter) was called". Those records add up to about 1,000 tokens, and a calendar can be fetched again if needed.
  3. Fix B, compaction (summarizing the history): the model writes a 300-token summary ("Booked #4412, laser cutter Fri 14:00; 3D printer is full until Monday") and a fresh window starts from it.
  4. With Fix B, the next call sees about 1,700 tokens (the 1,418 from before plus the 300-token summary) instead of about 41,400.

The aim is the smallest set of useful tokens, not the biggest window. Clearing old tool results is one of the lightest forms of compaction (Anthropic Engineering).

A common mix-up

"A bigger window fixes it." Windows of every size get cluttered (Anthropic Engineering). Those 40,000 tokens bury the booking at any size, and every call re-reads them.

Memory notes: what is kept between sessions

When a session ends, the window is gone. Anything the assistant should know next time has to be written down outside it, as notes the program stores.

Trace: two sessions, three days apart
  1. Monday. Dana says: "I just passed the laser cutter safety training." The model asks to create the file /memories/students/dana.md (shorthand for the memory tool's create command) with "Laser cutter: trained Monday. 3D printer: not trained."
  2. The program writes the file and returns "File created successfully". Reply: "Noted, you're cleared for the laser cutter."
  3. The session ends and the window is thrown away.
  4. Thursday. A new session starts with an empty history. Dana asks: "Can I book the 3D printer?"
  5. The model first asks to view /memories/students/dana.md. The two lines come back, about 25 tokens.
  6. Reply: "Not yet. You need the 3D printer training first. The laser cutter is fine."

The memory tool is just files: the model asks to view, create or edit one, and your program does it, so the notes sit in storage you control (Memory tool docs). My advice for privacy: one file per student, with every path checked so one student's session can't read another's.

A common mix-up

"The model remembers students from earlier chats." Without the notes file, Thursday's session can't know Dana's training and has to ask again. Only what was written down survives.

Retrieval: finding the right page in a long manual

Some knowledge is too big for the window and too big to write as notes. So the assistant searches it and pulls in only the few passages that fit the question.

Trace: 12 manuals
  1. 12 manuals of about 120 pages is 1,440 pages. At a rough 400 tokens a page, that is about 576,000 tokens. Under about 200,000 tokens (about 500 pages) you can simply paste it all in (Anthropic Engineering), and this is nearly three times that.
  2. The student asks: "How do I change the nozzle on the 3D printer?"
  3. The model picks search_manual("3D printer change nozzle").
  4. Ahead of time, the program cut the manuals into chunks, short pieces. It returns the top 3 chunks, about 300 tokens each, 900 in all.
  5. Reply: "Heat the nozzle to 200 C, then unscrew it. See the 3D printer manual, page 41."

One catch: the chunk "Heat to 200 C, then unscrew" doesn't say which machine it's from, so a search can miss it. The fix is to add a line to each chunk before storing it: "From the 3D printer manual, chapter Changing the nozzle." Adding that line cuts missed retrievals (Anthropic Engineering).

This is just-in-time retrieval: keep a light pointer, like a search or a file path, and load the content only when you need it (Anthropic Engineering). A search tool is described and called like any other tool.

A common mix-up

"Retrieval always beats pasting the text in." One 48,000-token manual fits in the window, but pasting it in means every call re-reads 48,000 tokens (the re-sending cost from earlier). A search of about 900 tokens is far cheaper, and it pays off even more at 576,000.
