Context and memory: what an agent can see now and what it can recall later

An agent's context is the text the model sees on a call, and its memory is whatever you store outside that text and load back in. By the end of this lesson you can say what is inside the model's context on one call, what carries over between steps and sessions, and when to use notes or retrieval for what the window can't hold.

Why this matters for you

Your makerspace assistant must answer from long manuals and remember each student's training status. This is how you decide where each fact lives, and what it costs.

Warm-up recall

1. In the agent loop, who runs the tool, the model or the program?

Check your answer

The program. The model only asks; the program runs the tool and sends back the result.

Context window: what the model can see on one call

The only thing the model knows about this conversation, student or manual is the text it is handed on each call. That handed-over text is the context, and it has a size limit.

One call: "Is the laser cutter free Friday?" (illustration numbers, not real limits)
  1. The program sends the fixed text, meaning the instructions and tool descriptions it sends on every call: 1,200 tokens (a token is a chunk of text, the unit the model counts in).
  2. It adds the student's message: 30 tokens. Total in: 1,230.
  3. The model reads only that. It knows nothing else about this student or the manual.
  4. It writes a tool request, check_calendar(machine="laser cutter", day="Friday"): 60 tokens. Its own output counts toward the window too.

A token is a chunk of text. Models are billed by the token, so the more tokens you send, the more you pay (input and output are priced differently).

The context window is all the text the model can reference on one call, including its own reply. It acts like working memory, and it is not the training data (Claude docs).

A common mix-up

"The model remembers me from last time." Tempting, because chat feels continuous. But if a student sends "and what about Saturday?" in a brand new call with nothing else in it, the model can't tell which machine you meant, because nothing in the window says so.

Step-to-step state: the context grows with every step

Between steps the model remembers nothing by itself. The program sends the whole history again each time, so the context grows and so does the cost.

The Friday request, two calls
  1. Call 1 input: 1,200 + 30 = 1,230 tokens. Output: the tool request, 60.
  2. The program runs check_calendar, like in the agent loop, and gets the Friday slots back: 400 tokens.
  3. Call 2 is a fresh call. Its input is 1,200 + 30 + 60 + 400 = 1,690 tokens, and it contains all of call 1. Output: the reply, 80.
  4. Input tokens paid across both calls: 1,230 + 1,690 = 2,920, not 1,690.

Each turn re-sends the history (Claude docs). So every extra step makes the next call longer, and on a small budget that adds up fast.

A common mix-up

"The model keeps its place between steps, so earlier steps are free." Say a task makes ten tool calls that return 400 tokens each. Call 11 re-sends 4,000 tokens of results.

Context rot and compaction: keeping the window small

A bigger window doesn't mean you should fill it. Models get worse at using long contexts, so you decide what stays in and what gets shrunk.

Same assistant, after a long chat

A student asked about booking, three machines and safety rules. The context is at 40,000 tokens, and 30,000 are old calendar results already acted on.

  1. Clear the old calendar results, since they were needed once: 40,000 down to 10,000.
  2. Summarize the chat part of the rest (10,000 minus the 1,200 fixed text is 8,800) into "Student wants the laser cutter Friday 2pm, booked, confirmation #A12": 8,800 down to 800.
  3. Continue with the fixed text (1,200) plus the summary (800): 2,000 tokens.

Context rot means accuracy and recall get worse as the token count grows (Claude docs). Compaction means summarizing a conversation that is nearing the limit and continuing with the summary (Anthropic engineering post).

Three ways to shrink: clear old tool results (a light form of compaction), summarize, or keep a short reference such as a file path instead of the content.

A common mix-up

"A 1M-token window means I can paste in every manual." Some current models allow up to 1M tokens (Claude docs). But ten manuals of 360,000 tokens each is 3,600,000, which overfills it. Even a window that fits them degrades with length and bills every token on every call.

Session memory: notes kept outside the window

When a session ends, the window is gone. Anything the assistant should know next visit has to be written down outside it and read back in.

Training status between visits
  1. Session 1: a student passes the laser cutter safety training. The assistant calls save_note("student 4471: laser cutter training passed, 2026-11-20"), and the program writes it to a file or database.
  2. The session ends. The window is discarded and the model keeps nothing.
  3. Session 2, a week later: the program loads that student's notes at the start of the context, about 40 tokens.
  4. The student asks "Can I book the laser cutter?" The assistant sees the note and books, without asking for proof again.

This is structured note-taking: the agent writes notes to storage outside the window and reads them back later. A to-do list or a NOTES.md file both work (Anthropic engineering post).

Think of the window as short-term memory, within a session, and stored notes as long-term memory, across sessions. The model only asks to save; the program does the saving and the loading. A second note could be "prefers mornings", in the same file.

A common mix-up

"The model learned the student's status, so it knows it next time." The model itself isn't changed by a chat. Delete the notes file and session 2 starts blank, so the assistant asks for training proof again.

Retrieval: loading only the right page of a long manual

The assistant can't fit a whole manual in its window, and it doesn't need to. It keeps a way to find the right page and loads only that.

Long laser cutter manual (invented example)

120 pages at 3,000 tokens is 360,000 tokens. Pasting it would cost that on every call.

  1. Student: "What material can't I put in the laser cutter?"
  2. The assistant calls search_manual(machine="laser cutter", query="prohibited materials").
  3. The program matches the query against an index of the manual (a lookup list built ahead of time from its text), so "prohibited materials" finds the pages that use those words, and returns the top 2 pages with page numbers: 6,000 tokens.
  4. The model reads them and replies "No PVC or vinyl, it releases chlorine gas (manual p. 14)."
  5. The pages are 6,000 tokens, 1.7% of pasting everything (6,000 / 360,000), before the fixed text.

Retrieval means looking up the relevant piece and loading it into the context just in time. The agent keeps a light reference, like a page number or file path, and loads the content only when needed (Anthropic engineering post).

A second question, "How often do I clean the lens?", would bring back different pages. You can also mix: load small always-needed facts like opening hours up front, and look up the manual (same post).

A common mix-up

"Retrieval is memory the model has, like recall." It's a lookup the program does, and it can miss. If "prohibited materials" returns the wiring page, the model has nothing correct to read and may still write a confident answer, so search quality and tool descriptions matter.

Memory design: deciding whether a fact lives in the window, in notes or in retrieval

Now you can decide, for each piece of information the assistant needs, whether it belongs in the window, in notes, or in a retrievable store.

Worked example

The assistant needs (a) its rules, (b) a student's training status, (c) page 14 of the laser cutter manual.

  1. (a) Window. It is fixed text, small and needed every call.
  2. (b) Notes. It is small and needed across sessions.
  3. (c) Retrieval. It is large and needed rarely.
Your turn

Sort into window, notes or retrieval: (1) what the student asked two messages ago; (2) which printer the student prefers; (3) the 80-page 3D printer manual.

Hint

Ask two things: is it needed after this session, and how big is it? For (1), it is in the conversation right now.

Show a solution

(1) window: it is in the conversation now. (2) notes: small, and needed in later sessions. (3) retrieval: big, and needed rarely. Cost check: pasting the 3D printer manual is 80 × 3,000 = 240,000 tokens on every call.

  • The window is everything the model sees on one call, and the output counts too.
  • Each step re-sends the history, so context and cost grow; shrink it by clearing and summarizing.
  • Between sessions only saved notes survive, and the program reloads them.
  • For big sources, retrieve just the pages you need, just in time.

Why it matters: this is how your assistant stays inside a small model budget while still answering from long manuals.
