Context and memory: what an agent sees now, and what it can look up later

By the end of this lesson you can say what an agent has in front of it on each model call, what survives from one step and one session to the next, and when to keep something in the context, save it as a note, or retrieve it on demand.

Objective O3: context, memory and retrieval About 30 minutes Builds on: what a model is, and the agent loop
Why this matters for you

Your mission says you need to decide what the assistant keeps in its context, what it saves between sessions, and how it finds the right page. That is this lesson.

It is also where your small model budget gets spent or saved.

Warm-up: two quick recall questions

1. In the agent loop, who actually runs a tool: the model or the program around it?

Check your answer

The program. The model only asks for the tool call, and the program runs it and sends the result back as text.

2. Why can a chatbot state an outdated fact with total confidence?

Check your answer

It knows only its training plus the text it is given. Anything newer than training, it simply does not have. Today's lesson is about that second half: the text it is given.

Part 1. Context window: everything the model can see on one call 6 min

The model only knows what is in the text you hand it on each call, and that text has a size limit. So before we talk about memory, we need to see what is in that text and how it grows.

Worked example: one request, call by call

A student asks: "Is the laser cutter free Friday, and what's the max material thickness?" Every token count below is illustrative: I made the numbers up to keep the arithmetic easy. (A token is a small chunk of text; I'll define it right after the trace.)

  1. Call 1. The model sees instructions (800 tokens), tool descriptions (1,200) and the student's question (30). That is 2,030 tokens, and the model asks for check_calendar.
  2. The program runs the tool. The model's request (about 50 tokens) and the calendar result (400) get appended to the pile.
  3. Call 2. The model sees everything from call 1 plus that request and result: about 2,480, call it 2,500. It asks for search_manual.
  4. The program runs that tool. The search request (about 70 tokens) and 3 manual pages (1,200 tokens) get appended.
  5. Call 3. The model sees about 3,750 tokens and writes the final answer.
  6. The student replies "book it". Call 4 carries those 3,750 tokens, plus the answer and the new message. The pile never shrinks by itself.
  7. Notice: the model never "remembered" call 1. The program re-sent the whole pile on every call.

Now the two words. A token is a chunk of text the model reads and writes, often a bit shorter than a word (a rule of thumb, not an exact rule). A manual page is about 400 tokens, which follows from 200,000 tokens being about 500 pages (Contextual Retrieval).

The context window is all the text the model can reference when it writes a reply, including the reply itself (context windows docs). Its size is a limit in tokens, and it depends on the model: the docs list a 1M-token window for Claude Sonnet 5.5 and 200k for some other models. The lesson holds at any size.

Each request carries the earlier history as input, and everything counts: the system prompt (your instructions), every message including tool results, and the tool definitions (context windows docs).

A common mix-up: "The model remembers earlier calls by itself"

It's tempting because a chat feels continuous. But imagine the program sent only the newest tool result on call 3: the model would not even know the student asked about Friday. It sees only what gets sent.

A common mix-up: "The window only holds the student's chat"

In the trace, 2,000 of the 3,750 tokens were instructions and tool descriptions. The student's own words were 30. All of it counts toward the limit, and all of it is input you're billed for (caching can make repeats cheaper, but they still count).

Check yourself

On call 3 of the trace, what does the model actually have in front of it?

Show the answer

The second option. The model has no memory of its own between calls, so the program sends the whole pile each time.

Quick recap: instructions, tool descriptions, history and results all sit in one pile, measured in tokens. The program re-sends the pile on every call.

Why this matters: all of it counts toward the limit and the bill, on every call.

Part 2. Context rot: why a bigger window does not mean better answers 4 min

A bigger window lets you fit more, but it does not mean the model uses all of it well. So the job is to choose what goes in, not to fill it up.

Worked example: "just paste all ten manuals in"

Your team is tempted to do exactly that. The numbers below are illustrative, using the 400 tokens per page from Part 1.

  1. Size. 10 manuals × 120 pages × 400 tokens = 480,000 tokens per call. The 3 relevant pages are 1,200 tokens.
  2. The question. "What's the laser cutter's max thickness for acrylic?" The right number sits on one page among 1,200.
  3. What can go wrong. The model grabs the 3D printer's limit instead of the laser cutter's. Both pages talk about thickness, and the right one is buried.
  4. The cost. A 5-step loop re-sends the pile every step: 5 × 480,000 = 2,400,000 input tokens for one question.
  5. The focused version. Send the 1,200 tokens of right pages plus about 1,800 for instructions, tool descriptions and the question, so about 3,000 tokens per call: 5 × 3,000 = 15,000 input tokens.
  6. Prices. They vary, so compare token counts, not dollars.

Why does the model slip? As the number of tokens grows, its accuracy at recalling something from them goes down: this is called context rot (context windows docs). The model has a limited "attention budget", and the drop is a gradient, not a cliff (Effective context engineering).

So there is no magic line below which everything is safe. As a rule of thumb, each extra irrelevant page makes the right answer a bit less likely.

A big window doesn't make the pile free (check your model's pricing for long prompts). 480,000 tokens would fit in a 1M window, and it would still count as input on every call (caching can lower the price of repeats, not the size of the pile).

One more case: the tool descriptions. Say you had 10 tools instead of the two in our trace, and each has a 400-token description. That is 4,000 tokens on every call, even when the question is just "is Friday free?". It's a smaller leak than the manuals, but it repeats on every single call, so it adds up the same way.

A common mix-up: "A bigger window means the model reads everything equally well"

It's tempting because "fits" sounds like "works". The laser cutter versus 3D printer mix-up above is the real case: the facts were all there, and the wrong one got used.

A common mix-up: "If it fits, it is free"

2.4 million input tokens versus 15,000 for the same question. Same answer, if you're lucky, at 160 times the usage.

Check yourself

The manuals total 480,000 tokens and your model's window can hold them. What's the best design?

Show the answer

The third option. Fit is not the test; the smallest useful set is.

Quick recap: more in the window means more cost per call and a bit less recall. Pick on purpose.

Why this matters: it keeps the assistant accurate and keeps the sponsor's budget alive. The goal is the smallest set of facts that makes the right answer likely.

Part 3. Within-session state: what is kept between steps, and how to trim it 5 min

Inside one conversation, the program keeps the transcript and re-sends it, so the pile only grows. When it gets too big, you have to shrink it on purpose.

Worked example: a long booking chat

The student checks 6 calendars on different days, each result 2,000 tokens, before choosing Friday 2pm. All numbers are illustrative.

  1. Turn 12. The context is 25,000 tokens. 12,000 of them (6 × 2,000) are old calendar listings nobody needs any more.
  2. Option A, clear old tool results. Drop the 6 listings. Keep the rest of the chat, including "student chose Friday 2pm" and the booking confirmation (they're already in the other 13,000). The context falls to about 13,000.
  3. Option B, summarize. The model or the program writes a 300-token summary of the whole chat, and the next window starts from that summary plus the most recent turns.
  4. Option C, start fresh. An empty window, with only what you carry over by hand.
  5. What each costs. Clearing loses the listings, which is fine because the tool can fetch them again. A summary can drop a detail, such as "student is allergic to the resin", so tell it what must survive.
  6. After any option, the model sees only the shrunken version. Whatever was dropped is gone from its view.
Way to shrinkWhat it doesWhat you risk
Clear old tool resultsRemoves old tool output, keeps the restOutput is gone, so re-fetch if needed
SummarizeReplaces history with a short summaryA detail may be left out
Start freshEmpty window plus what you carry overEverything not carried over is gone

The names: summarizing a conversation that is nearing the limit is called compaction, and removing old tool output is tool result clearing, one of the lightest forms of compaction (Effective context engineering). Both can be switched on in the API, under context editing and compaction, though some of these features are still in beta (docs).

Old listings can be re-fetched, so clearing them is cheap, and a summary should be told what must survive. Decide the trim rule before the chat gets long, not after it has already gone wrong.

A common mix-up: "Trimming is safe because the model will remember the important bits"

After a summary, the model knows only what the summary says. If "needs the 40 W laser" was left out, it is gone.

A common mix-up: "The transcript is saved somewhere the model can reach"

The program holds it, and the model sees it only when the program sends it. Nothing reaches back.

Check yourself

A summary of a long chat leaves out that the student needs the 40 W laser. What happens on the next call?

Show the answer

The first option. Whatever the shrunken pile lacks, the model lacks.

Quick recap: the pile grows by itself and shrinks only when you shrink it. Clear what is stale, summarize what is long, and say what must survive.

Why this matters: this is the loop from your last lesson with its cost made visible: each step is another call that carries the whole pile.

Part 4. Memory across sessions: notes the agent writes and reads back 5 min

When the conversation ends, the window is gone, so anything the assistant should know next week has to be saved outside it. The usual way is to give the agent a tool to write and read notes.

Worked example: a student's training status

Your mission says the assistant must remember each student's training status between visits. The student ID s4821 and the note's contents are made up for illustration.

Session 1, Monday

  1. Student: "I just finished the laser cutter safety training."
  2. The model calls the memory tool: create /memories/students/s4821.md with "Laser cutter safety training: done 11/17. Needs: 3D printer training."
  3. The program, not the model, runs the file write against its own storage and returns text like "File created successfully at: /memories/students/s4821.md".
  4. The session ends. The window is thrown away.

Session 2, a week later, a brand new window

  1. Student: "Can I book the laser cutter Friday?"
  2. First the model views /memories/students/s4821.md. The memory tool adds an instruction to check memory before anything else.
  3. The note comes back. Training is done, so the model calls check_calendar and books.
  4. Session 2's window is thrown away too. The note stays, ready for session 3.

That's the memory tool: files under /memories that persist between sessions, which Claude creates, reads, updates and deletes (memory tool docs). A note is just one of those files.

It works client-side: the model asks for a file operation and your application runs it. You decide where the data lives, such as a per-user folder or a database, and you control retention (memory tool docs).

What to save, and what not to. Save short, durable facts: training done, preferred morning slots. Skip anything sensitive, and don't keep listings that go stale by tomorrow. The docs say Claude usually refuses to write sensitive information, but you should still validate what gets stored, cap file sizes and periodically delete notes nobody has opened in a long time (memory tool docs).

A training status must be exact, so it could live in a real database that the tool reads, while the model's notes hold softer things like "prefers mornings".

(The docs show this multisession pattern for software projects; the training-status setup is our adaptation.)

A common mix-up: "The model remembers the student because it was told"

Session 2 starts with an empty window. Without the view call, the assistant would ask for the training status all over again.

A common mix-up: "Notes are automatically in the context"

They count only once read. A note that gets read costs tokens on that call, so keep notes short and organized. Notes work because the agent reads them back after the window resets (Effective context engineering).

A common mix-up: "The model's memory lives inside the model or at the vendor"

With the memory tool, it lives in your application. If you delete the file, the memory is gone.

Check yourself

Show the answer

Quick recap: write a short note, end the session, and read the note back in the next one. The window forgets; the notes don't.

Why this matters: a student's status is the main reason this assistant needs memory at all, and it gives your design review a clear answer on where that data lives.

Part 5. Retrieval: finding the right page in a long manual 5 min

Memory is for what the assistant has learned about a student, and retrieval is for finding facts in material that already exists, like manuals. Instead of loading the whole manual, you search it and load only the best few pages.

Worked example: the manuals

Question: "How thick can I cut acrylic on the laser cutter?" Page numbers and token counts are illustrative.

  1. Ahead of time. The program splits each manual into chunks of a few hundred tokens each (say 400, in this example) and builds a searchable index of them. An embedding is a list of numbers that captures a chunk's meaning, so chunks with similar meanings end up close together (Contextual Retrieval).
  2. The question arrives and goes through the same process.
  3. The index returns the 3 closest chunks: "Laser cutter, materials table" (p. 14), "Acrylic settings" (p. 22) and "Safety: ventilation" (p. 9).
  4. Those chunks, about 1,200 tokens, go into the context. The model answers from them and cites page 14.

That whole recipe is retrieval, formally retrieval-augmented generation: find relevant information in a knowledge base and append it to the prompt (Contextual Retrieval). It is the fix for the 480,000-token problem from Part 2.

You can wire it two ways. The program can always retrieve first, or search_manual can be a tool the model chooses to call, like in the loop. We'll compare those choices in the next lesson.

One more case: the chunk that lost its context. Take a chunk that says just "Maximum thickness is 6 mm." It names no machine, so it can match the wrong question. The source shows the same thing with a chunk about a company's revenue growing 3% that names neither company nor quarter (Contextual Retrieval).

The fix is to add context to each chunk before indexing: "Laser cutter manual, materials table: Maximum thickness is 6 mm."

In the source's own tests, the share of relevant chunks missed in the top 20 went from 5.7% to 3.7% with contextual embeddings, to 2.9% with keyword matching added, and to 1.9% with a final re-sorting step (reranking) added (Contextual Retrieval). Better, never zero.

Exact terms are different. A code like "Error code TS-999" is better found by keyword matching, which is strong on unique identifiers and technical terms (Contextual Retrieval). A made-up "E-17" on your own machine would work the same way.

The shortcut. If your material is under about 200,000 tokens (about 500 pages), you can skip retrieval and put it all in (Contextual Retrieval). But the pile is re-sent on every call, so retrieval can still be cheaper. Your ten manuals are about 480,000, so retrieval is needed anyway.

A common mix-up: "Retrieval means the model has learned the manuals"

Replace a manual and the very next question uses the new page, with no training. The model only reads what came back.

A common mix-up: "Retrieval always finds the right page"

The "6 mm" chunk with no machine name is one way it misses, and the 5.7% miss rate above is another. Context on chunks lowers it but never to zero.

A common mix-up: "Retrieval and memory are the same"

Retrieval searches material someone wrote ahead of time. Memory is what the agent wrote down itself. Both end the same way: text added to the window.

Check yourself

The third option. Retrieval changes what is handed to the model, not the model.

Quick recap: split once, index, find the closest chunks for each question, and put only those in the window. Add context to chunks, and use keyword search for exact codes.

Why this matters: this is the "how it finds the right page in a long manual" part of your mission, and the cost fix from Part 2.

Part 6. Choosing what to keep: worked example, practice, summary 5 min

Now put the three tools together: for each piece of information, decide whether it stays in the window, goes in a note, or is retrieved when needed. Each fact should live in the place that matches how long you need it.

The rule: will it be needed on the next call (keep it in the window), in a later session (save a note), or only now and then from a big pile (retrieve)?

Worked example: book the 3D printer for Tuesday

The student asks to book the 3D printer for Tuesday. The assistant needs four things.

ItemDecisionReason
(a) The printer's filament limitsRetrieveIt sits in a long manual, and you need only a few lines.
(b) Whether the student passed 3D printer trainingNote or databaseIt must outlast this chat, and it must be exact.
(c) The Tuesday calendarWindow, cleared laterIt's a tool result needed during this chat. Clear it once the booking is done.
(d) The student's name, typed in this chatWindowIt's needed only now, and it is already there.

  • (a) The student's preferred time of day, mentioned in 3 sessions.
  • (b) The safety rules for the band saw, in a 40-page manual.

Your turn
Hints, one per item

Item (a): will it be needed after this chat ends? Item (b): how long is the pile it sits in? Item (c): is it still true? Item (d): when is it needed, and where is it already?

Show the solutions

(a) Note. It outlasts the chat, and a slightly wrong value does little harm. The window alone fails, because the window is thrown away. Retrieval fails too, as there is no big pile to search.

(b) Retrieve. It's a long document, and you need a few lines. Pasting all 40 pages into the window wastes tokens on every call, and a note cannot usefully hold 40 pages that already exist elsewhere.

(c) Window, then clear it. It's a tool result that mattered a moment ago and is stale now. Saving it as a note would plant an out-of-date fact for the next session.

(d) Window. It's needed only now. A note is overkill unless you want the assistant to greet them by name next week, and retrieval has nothing to search.

Summary
  1. The model sees only the window: instructions, tool descriptions, history and results, sized in tokens.
  2. More in the window is not better: accuracy can drop and cost grows with every call.
  3. Within a session the program re-sends and can trim the pile. Across sessions the agent needs notes.
  4. Retrieval finds the right chunks in big material, and the model only reads what comes back.
  5. Everything ends up as text in the next call's window.

Why this matters in the real world: these choices are the answer to cost and accuracy questions at your design review.
