Context and memory: what an agent sees on each call, and what it keeps

By the end of this lesson you can work out what an agent's model sees on each call and what each call costs, and you can choose what to keep in context, what to look up on demand, and what to save between sessions.

Objective O3: context, memory and retrieval in an agent About 60 minutes Builds on: the model and agent-loop sessions (learning records 0001 and 0002)
Why this matters for you

Your makerspace assistant has to answer from long machine manuals and remember each student's training between visits, all inside a small budget. Both jobs come down to one question: what text goes into the model on each call?

Context window: everything the model can see on one call 12 min

The model starts every call knowing nothing except the text it is handed, so the first thing to learn is what is in that text and how big it gets. This comes first because every later choice, what to look up and what to save, is a choice about this text.

Let's build the words up one at a time. A token is a small piece of text: a short word, part of a longer word, or a bit of punctuation. It's the unit the model reads, the unit it writes, and the unit you're billed in.

A rough rule, and it's this lesson's own, is 3 to 4 characters per token. A 10 kB web page comes to about 2,500 tokens (pricing), which is the same ballpark. Newer models can produce about 30% more tokens for the same text (token counting), so for real budgets, count instead of guessing.

Maya's sentence is about 70 characters, so roughly 17 to 23 tokens. In the table it's 40 because the app adds a student ID and a time stamp around it (illustrative).

The rule is only approximate, and newer tokenizers give about 30% more tokens for the same text. So before you trust a size, ask the token counting endpoint, which is free and still gives an estimate (token counting).

Next, the context window is all the text the model can use on one call, and that includes the reply it is writing (context windows). Everything in the request counts toward it: the system prompt, every message including tool results, and the tool descriptions.

Last, input tokens are everything you send in, and output tokens are what the model writes back. They're billed separately, and output costs more per token. For Claude Sonnet 5.5 the listed price is $2 per million input tokens and $10 per million output tokens (pricing).

Prices change, so recheck the page before your review. Also, when tools are on, the API adds a hidden tool-use prompt to every call (286 tokens for this model on that page), which the tables below leave out to keep the sums small. Every dollar figure in this lesson uses that example rate.

One more fact explains the whole table. Between calls the model keeps nothing, so the only way it can "remember" the first step is if the program sends the first step again. That's why each row of the table contains the rows above it.

Worked example: the four calls, one by one

Follow Maya's request through the loop you already know, and watch what the program puts into each call.

  1. Call 1. The program sends the instructions for the assistant (800 tokens), the tool descriptions (700) and Maya's message (40). That's 1,540 input tokens. The model writes 60 tokens: a request for get_training_status("maya"). It runs nothing itself.
  2. The program acts. It runs the tool and gets a 150-token result, such as "Laser cutter: passed 14 Nov, valid for 12 months" plus a few more fields.
  3. Call 2. The program sends everything from call 1 again (1,540), plus the model's 60-token reply, plus the 150-token result. That's 1,750 input tokens. The model writes 70 tokens asking for check_calendar("laser cutter", "Friday").
  4. The program acts. The calendar tool returns 400 tokens: the whole Friday schedule, with Friday at 2 free.
  5. Call 3. Everything from call 2 (1,750), plus the 70-token reply, plus the 400-token calendar. That's 2,220 input tokens. The model writes 80 tokens asking for book_slot.
  6. The program acts. The booking tool returns 60 tokens: a confirmation.
  7. Call 4. Everything from call 3 (2,220), plus the 80-token reply, plus the 60-token confirmation. That's 2,360 input tokens. The model writes 120 tokens, the final answer: "You're trained on the laser cutter and Friday at 2 was free, so I've booked it."

Notice that call 4 contains calls 1 to 3 again. The program re-sends the whole history every time.

Here's call 2 as a sketch, so you can see the pieces stacked in order. The layout is simplified and isn't the exact request format.

[instructions]  You are the makerspace assistant. Check training before booking...   800 tokens
[tools]         get_training_status, check_calendar, book_slot (descriptions)       700 tokens
[user]          Maya (student 4417): Can I use the laser cutter Friday at 2? ...     40 tokens
[assistant]     asks: get_training_status(student_id="4417")                         60 tokens
[tool result]   laser cutter: passed 14 Nov, valid 12 months ...                    150 tokens
                                                                        total   1,750 tokens

Now the arithmetic, step by step, at the example rate.

  1. Add the inputs: 1,540 + 1,750 = 3,290, then + 2,220 = 5,510, then + 2,360 = 7,870 input tokens billed.
  2. Add the outputs: 60 + 70 = 130, then + 80 = 210, then + 120 = 330 output tokens billed.
  3. Price the input: 7,870 ÷ 1,000,000 × $2 = $0.01574.
  4. Price the output: 330 ÷ 1,000,000 × $10 = $0.0033.
  5. Add them: $0.01574 + $0.0033 = $0.01904, so about $0.019 for one booking.

Compare 7,870 billed with 2,360, the size of the last call. You paid for 3.3 times the final context, because every earlier piece was paid for again on each call.

The start of every call is the worst repeat. The instructions and tool descriptions, 800 + 700 = 1,500 tokens, are sent four times, which is 6,000 of the 7,870 input tokens, about three quarters. So short instructions and short tool descriptions save money on every single call.

A common mix-up: "The model remembers the earlier steps by itself"

It feels that way, because the answer in call 4 builds on the earlier steps. But in call 2 the model can "see" the training result only because the program put those 150 tokens into the request. Leave them out and call 2 has no idea what was checked (context windows).

A common mix-up: "I pay for each token once"

Look at the 150-token training result. It's paid for in call 2, again in call 3 and again in call 4, which is 450 input tokens for one small result.

A common mix-up: "The context window is how much the model knows"

The window is only the working text for this call. The model also has what it learned in training, which isn't in the window, and that tells it nothing about Maya.

Recap. The window is everything in one call: instructions, tool descriptions, messages, results and the reply. The program re-sends it all on every call, so the bill is the sum of the growing inputs, not the size of the last one.

Context curation: keeping the window small and useful 9 min

A bigger window does not mean you should fill it, because more text costs more and the model uses long text less well. So you decide what goes in each call, and the rest should stay out until it is needed.

The model has two problems with long text, and one is easy to miss. The first is cost, which you just saw: every token in the window is billed on every call. The second is quality: as the token count grows, accuracy and recall degrade, a phenomenon called context rot (context windows).

So aim for the smallest set of high-signal tokens that gets the job done (context engineering post). Choosing which tokens go in is called context engineering.

Worked example: paste the manual, or send only what's needed

Same four calls as before, but suppose the model also needs the laser manual to answer. The manual is 24,000 tokens (illustrative), and it arrives with the training result, in call 2.

  1. Paste path, call 1. Unchanged: 1,540.
  2. Call 2. 1,750 + 24,000 = 25,750.
  3. Call 3. 2,220 + 24,000 = 26,220, because the manual is part of the history now.
  4. Call 4. 2,360 + 24,000 = 26,360.
  5. Add up. 1,540 + 25,750 = 27,290, then + 26,220 = 53,510, then + 26,360 = 79,870 input tokens. At $2 per million that's 79,870 × 2 ÷ 1,000,000 = $0.15974, about $0.16 for input alone.
  6. Only what's needed. Send just the three short passages that answer the question, 1,200 tokens in total, instead of 24,000. Calls 2 to 4 become 1,750 + 1,200 = 2,950, then 2,220 + 1,200 = 3,420, then 2,360 + 1,200 = 3,560.
  7. Add up. 1,540 + 2,950 = 4,490, then + 3,420 = 7,910, then + 3,560 = 11,470 input tokens. That's 11,470 × 2 ÷ 1,000,000 = $0.02294, about $0.023.
  8. Compare. 79,870 ÷ 11,470 is about 7. Sending only what's needed is about seven times cheaper on input.

The extra 72,000 tokens in the paste path are the 24,000-token manual carried three times (79,870 minus the original 7,870). These are the lesson's own numbers at an example rate, not measurements. Part 3 shows how the three passages get found.

Cost is only half the problem. In the 80,000-token version the model also has to find the one relevant sentence inside a huge window, and it does that less reliably than in the small one.

Here are the tools you have for keeping the window small. Each one answers the question "does the model still need this text right now?"

  • Just-in-time loading: keep a small pointer, such as a file path, a stored query or a link, and load the content only when it's needed (context engineering post). A pointer like "laser manual, section 4.2" is about 10 tokens instead of 24,000.
  • Clearing old tool results: once a result has been used, remove it from the history (context windows).
  • Compaction: when a long conversation nears the limit, summarize it and continue in a fresh window with the summary (context engineering post). The server-side version is in beta (context windows).

A second case of pointing instead of pasting. Say the assistant can look at a maintenance history for the laser, 6,000 tokens (illustrative). Pasted into call 2 for one step, it's carried by calls 2, 3 and 4: 3 × 6,000 = 18,000 tokens.

If instead the model holds a pointer, /logs/laser-maintenance.txt, and asks only for last week's lines (500 tokens), the same three calls carry 3 × 500 = 1,500.

Clearing is the same idea after the fact. Back in the booking trace, once call 3's reply has asked to book, the model no longer needs the 400-token calendar. If the program clears it and a few tokens remain (say 10), call 4 is 2,360 − 400 + 10 = 1,970, which saves 390 tokens, or 390 × 2 ÷ 1,000,000 = $0.00078. That's tiny here, and it matters when the cleared result is big and the request is long.

A common mix-up: "A 1M-token window means I can paste the whole manual library"

It's tempting because Claude Sonnet 5.5 really does have a 1M-token window (context windows). But fitting is not the same as working well. A 24,000-token manual carried in 3 calls is 72,000 tokens for one question, and even if it fits, accuracy drops as the text grows.

A common mix-up: "Old tool results are harmless once used"

The 400-token calendar result is paid for again in call 4, even though the model no longer needs the details once it has asked to book Friday at 2. Clearing it after use saves those tokens on every later call.

A common mix-up: "Compaction loses nothing"

A summary of a long chat can drop a detail that mattered, such as "Maya is allergic to the resin we use". What must survive should be written down as a note, not left to the summary. Part 4 shows how.

Check yourself

Recap. More text means more cost and worse recall. Point to big things, load them when needed, clear what's used, and compact only when the history gets long.

Retrieval: finding the right page in a long manual 10 min

If the whole manual is too big to carry, you need a way to fetch only the part that answers the question. That is retrieval, and it is how the assistant finds the right page without paying for the rest.

The first step is cutting the manual up. A chunk is a piece of a document, usually no more than a few hundred tokens (contextual retrieval). Your 24,000-token laser manual becomes about 60 chunks of 400 tokens each, so any one page can be fetched alone.

Then you need a way to score each chunk against the question. There are two common ways:

  • Search by meaning: each chunk is turned into a list of numbers that encode what it means (an embedding), the question is turned into numbers the same way, and the closest chunks win (contextual retrieval). It can match "vinyl" with a chunk about "PVC" even though the words differ.
  • Search by words: a ranking method such as BM25 finds precise word or phrase matches (contextual retrieval). It's good for exact names and codes.

Finally, top-K means you take the K best-scoring chunks and put them in the window. K is your choice. This lesson uses 3, because the arithmetic stays small, but that's the lesson's own example: passing the top 20 chunks works better than the top 10 or top 5 (contextual retrieval).

One more idea, and it's the neat one: retrieval is just a tool. search_manual(query) works like the other three tools, so its result enters the window like any tool result, and it's paid for in every later call.

Worked example: "Can I cut vinyl on the laser?"
  1. Maya asks: "Can I cut vinyl on the laser?"
  2. The model asks: it writes a request for search_manual("vinyl laser cutter"). It doesn't run anything.
  3. The program searches. It has already split the 24,000-token manual into about 60 chunks of 400 tokens. It scores each chunk against the query and returns the top 3, 1,200 tokens in total.
  4. What comes back (illustrative): rank 1, "2.3 Banned materials" (400 tokens); rank 2, "4.2 Cutting acrylic and wood" (400); rank 3, "6.1 Ventilation and fume extraction" (400).
  5. Why meaning matters here. Chunk 2.3 reads: "PVC and other chlorinated plastics: never cut. They release chlorine gas that harms people and corrodes the machine." It never says "vinyl", so a search by words alone could miss it. A search by meaning knows that adhesive vinyl is a PVC product and returns it.
  6. The model replies, now that the chunk is in the window: "Not on the laser. Vinyl is PVC, and the manual's banned-materials section says chlorinated plastics must never be cut."

The 1,200 tokens went in once, and they ride along in the later calls. That's the 11,470-token path from Part 2.

A second trace: an exact name
  1. Maya asks: "How do I replace the focus lens on the LC-40?" The makerspace has two lasers, the LC-40 and the LC-60 (illustrative).
  2. The model asks for search_manual("LC-40 focus lens").
  3. Search by words: it sees "LC-40" and "focus lens" in the chunk "Replacing the focus lens on the LC-40" and ranks it first. The chunk "Cleaning the lens on the LC-60" shares fewer exact words and ranks lower.
  4. Search by meaning: both chunks are about lenses on a laser, so their numbers are close, and it may rank the LC-60 chunk about as high as the LC-40 one. That's a wrong answer waiting to happen.
  5. The fix: run both searches and merge the results, so exact codes and loose wording are both covered (contextual retrieval).

One more problem: a chunk cut out of a manual can lose its surroundings. A chunk that says only "Do not exceed 60% power" doesn't name the machine or the material, so it matches many questions (contextual retrieval).

The fix is to add a short line of context to each chunk before you index it, such as "From the laser cutter manual, the acrylic power settings section". That's called contextual retrieval. The failure rate (how often the right chunk is missing from the top 20) fell from 5.7% to 3.7% with contextual embeddings, and to 2.9% when combined with word matching (contextual retrieval).

What does a bigger K cost? With K = 20 chunks of 400 tokens, the search result is 8,000 tokens. In the four-call booking, calls 2 to 4 each carry it: 7,870 + 3 × 8,000 = 31,870 input tokens, or 31,870 × 2 ÷ 1,000,000 = $0.064. That's more than the $0.023 of K = 3, and still well under the $0.16 of pasting the manual.

So K is a trade between recall and cost. The way to pick it is the lesson's own advice: write ten real questions, check whether the right section lands in the top K, and raise K only while that keeps improving.

A common mix-up: "Retrieval always returns the right page"

It returns the best-scoring chunks, which isn't the same thing. Even with the improvements above, about 2.9% of searches in Anthropic's tests still left the right chunk out of the top 20, and a chunk with no context ("Do not exceed 60% power") can match the wrong question.

A common mix-up: "Retrieval means search by meaning"

They're not the same thing. Searching by words is also retrieval, and for an exact name like "LC-40" it is often the more reliable one.

A common mix-up: "Always build retrieval"

Retrieval is extra machinery. If your whole knowledge base is smaller than about 200,000 tokens, it can go straight into the prompt without it (contextual retrieval).

So measure the total tokens of your manuals first, then decide. Suppose you measure 150,000 (an example only): sent on every call at $2 per million, that's 150,000 × 2 ÷ 1,000,000 = $0.30 per call, or $1.50 for a five-call request. Fitting is not the same as cheap.

Agent memory: notes that last between sessions 10 min

The window is wiped when a session ends, so anything the assistant should know next time has to be saved outside it. That is memory: files or records that the program stores and the assistant reads back when needed.

Let's name the pieces. A session is one run from the first message to the end. Memory is information saved outside the window that a later session can read. Notes are short files the assistant writes for itself, and writing them regularly, outside the context window, is a standard pattern for agents on long tasks (context engineering post).

You don't have to invent how this works. There's a memory tool that stores files under /memories and lets the model read them back in later conversations (memory tool). It's a tool like any other, so the model only asks, and your program runs each command and returns the result.

The commands are view, create, str_replace, insert, delete and rename. The tool is client-side, which just means your app does the real work and decides where the files live.

Worked example: two sessions for Maya
  1. End of session 1. The assistant asks the memory tool to create /memories/students/maya.md. The program writes the file. The note (about 90 tokens, illustrative) reads: "Prefers Friday afternoons. Works in acrylic. Asked about vinyl on 12 Nov; told no. Wants to learn the vacuum former."
  2. Session 2, a week later. Maya writes: "Can you book the laser cutter Friday at 2?" The window holds the instructions, the tool descriptions and her message, and zero tokens from session 1.
  3. The model looks first. The memory tool is set up so the model views its memory directory before doing anything else (memory tool). It asks to view /memories.
  4. The program lists the files and sends the listing back as a tool result. The model asks to view /memories/students/maya.md, and the program sends back the 90-token note. Now the note is in the window.
  5. The model checks the facts that change. The note says nothing about her laser training, and even if it did, training can expire. So it calls get_training_status, the tool that asks the booking system.
  6. It books Friday at 2 and updates the note with str_replace: "Booked laser, Friday 2 pm." The program runs that, too.

The loop is the one you know: the model asks, the program runs, the result goes into the window. Memory just adds one more kind of tool.

What does a good note look like? Short, specific and dated, so the next session can use it in one read. Here's a bad one next to a good one:

Bad:   Maya talked to me about lots of things today, including the laser,
       her project, and some questions about materials and scheduling...
Good:  Maya (4417), updated 12 Nov.
       - Prefers Friday afternoons.
       - Works in acrylic. Asked about vinyl; told no (PVC rule).
       - Open: wants a vacuum former training slot.

The good note is about 90 tokens, and every line is something the assistant can act on. The bad one grows each visit and says nothing.

What goes where? This is the decision from the objective, and the table is the lesson's own rule of thumb.

WhereWhat goes thereExample for the assistant
In the windowThis request's messages and the tool results in useMaya's message, the calendar for Friday

When an agent works across several sessions, design what it saves so that picking up again is fast (context windows). Memory also pairs well with compaction: compaction keeps the active context small, and memory preserves what must survive a summary (memory tool).

A system of record is the database that owns a fact, such as who is trained on which machine. That's the lesson's own advice: for facts that change, look them up there, and don't copy them into notes.

A common mix-up: "The model remembers me from last time"

Session 2 starts with zero tokens of session 1, unless the program loads the note. If your memory file isn't read, the assistant greets Maya like a stranger.

A common mix-up: "Memory means the model learned something"

Nothing in the model changed. A file was written, and a file was read. Delete the file and the memory is gone.

A common mix-up: "Save everything"

This is the lesson's own advice. A note that lists every message grows until reading it costs more than it helps, and it's re-sent on every call like any other text.

And a stale note can be wrong. If session 1 saved "Maya is trained on the laser" and her training later expires, a session that trusts the note books a student who isn't allowed to use the machine, so facts that change stay in the system of record.

Privacy: notes about students are personal data

Your code must validate every path in every command, so a request can't wander outside /memories (memory tool). The model usually refuses to write sensitive information to memory files, and for stronger guarantees you add your own validation. The same page advises capping file sizes and expiring old files.

Context budget: working out what a request holds and costs 14 min

Now that you know what goes in, what is looked up and what is saved, you can put numbers on a design and defend it. This part turns the ideas into one calculation you can do on paper for your design review.

The calculation uses one rule you've already seen: this call's input = last call's input + last call's reply + the new result. Fill in a table with that rule, add up the input column, and price it. Before you trust any size, measure it with the free token counting endpoint (token counting).

Worked example: a vinyl question and a booking, five calls

Maya writes: "Can I cut vinyl on the laser Friday at 2? I did the training last week." The design has four tools: search_manual, get_training_status, check_calendar and book_slot. The memory note (90 tokens) is loaded by the program at the start. That is a simplification: reading it through the memory tool would add two more calls.

Sizes (illustrative): instructions 800, the four tool descriptions 900, the note 90, Maya's message with its ID and time stamp 45.

  1. Call 1. 800 + 900 + 90 + 45 = 1,835 input. The model writes 60 tokens asking for search_manual.
  2. Call 2. 1,835 + 60 + the search result (3 chunks, 1,200) = 3,095 input. It writes 60 tokens asking for get_training_status.
  3. Call 3. 3,095 + 60 + the training result 150 = 3,305 input. It writes 70 tokens asking for check_calendar.
  4. Call 4. 3,305 + 70 + the calendar 400 = 3,775 input. It writes 80 tokens asking for book_slot.
  5. Call 5. 3,775 + 80 + the booking result 60 = 3,915 input. It writes 120 tokens, the final answer.

The one line for a design review: "Retrieval cuts input tokens about sevenfold and the cost about sixfold on this request: from about 107,000 to about 16,000 tokens, and from about $0.22 to about $0.036 (at today's listed price)." At 100 requests a day that would be about $3.58 against $21.82, a made-up volume only to show scale.

One more lever from Part 2, on the same table. Clear the 400-token calendar result after call 4's reply asks to book, and call 5's input drops from 3,915 to 3,515. That saves 400 tokens, or 400 × 2 ÷ 1,000,000 = $0.0008 on this request.

It's small because only one call comes after it. Clearing the 1,200-token search result after call 2 would save it in calls 3, 4 and 5, which is 3 × 1,200 = 3,600 tokens. Early clearing of big results saves the most.

A common mix-up: "Cost depends on the length of the final answer"

In the worked example, the output was 390 tokens of 16,315 billed in total (15,925 + 390), so the input is 98% of the tokens. The history re-sent on each call dominates. Output does cost 5 times as much per token, so it's about 11% of the dollars ($0.0039 of $0.03575), which is still much less than the input.

A common mix-up: "Prompt caching removes the window limit"

Caching changes what you pay for tokens, not whether they count toward the window (context windows). A cache read costs 0.1 times the base input price on most models and 0.05 times on Sonnet 5.5, which is $0.10 per million instead of $2 (pricing). The cached tokens are still in the window, and they still affect how well the model uses it.

Before a design review, expect three questions, and answer them with the table. What's in the window on the biggest call? Which pieces repeat in every call, and could they be shorter? What would the total be if the biggest result were pasted instead of retrieved?

Recap. The rule is last input plus last reply plus new result. Add the column, price it, and compare designs. The biggest savings come from keeping big results out of the history, because every token is paid for in each later call.

Why this matters in the real world. A sponsor with a small model budget wants to know what one request costs before you build it. If you can show the table and the one-line claim, your design is something the team can check and defend, and you'll notice a bad design on paper rather than on the invoice.

Summary and go further 3 min

The idea in short: the model only sees the window, the window is re-sent and paid for on every call, and everything else is fetched or saved on purpose.

  • The context window is everything the model sees on one call, including its reply, measured in tokens.
  • The program re-sends the history on every call, so input cost grows with each step.
  • Keep the window small: point to big things and load only what is needed (retrieval).
  • Save what must outlive a session as notes. Keep changing facts in their system of record and look them up.
  • You can price a design on paper before building it.

Why it matters. This is how you keep the sponsor's budget and still give answers students can trust. A small window answers faster and misses less, and a note in the right place means the assistant remembers what matters.
