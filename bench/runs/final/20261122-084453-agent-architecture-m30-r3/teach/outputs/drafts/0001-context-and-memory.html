Context and memory: what an agent sees on each call and what it can carry between sessions

By the end of this lesson you can decide, for any agent, what goes into the context window on each call, what is saved outside it for later, and how the agent finds the right piece of a long document.

Objective O3: context and memory in an agent About 30 minutes Builds on your earlier sessions: the model, and the agent loop
Why this matters for you

Your makerspace assistant has to answer from long machine manuals and remember each student's training status between visits, on a small budget. The window, retrieval and notes are your three tools for that.

All token counts, names and students in this lesson are made up for teaching. They are illustrative, not measurements of a real system.

Context window: what the model can see on one call 5 min

The model can only use the text that is handed to it on each call, so the first design question is what gets handed over. An agent has no memory of its own: anything lasting has to be stored outside the window and put back in.

Warm-up recall

1. In the agent loop, who actually runs the tool: the model or the program?

2. Is each step of the loop one model call, or one long continuous thought?

Check your answers

1. The program runs it. The model only writes a request such as "check the calendar for Friday", and the program does the work and sends back the result.

2. Each step is its own call. So the real question for today is: if every step is a separate call, what does each call carry with it?

Let's start with one real call. A student types: "Is the laser cutter free Friday afternoon?" Before the model sees anything, the program packs a bundle of text.

Worked example: the window on call 1 (illustrative numbers)
  1. Instructions (the system prompt): "You are the makerspace assistant. Answer from the manuals..." That is 400 tokens.
  2. Tool descriptions for check_calendar, search_manual and book_slot: 800 tokens.
  3. The student's question: 25 tokens.
  4. Total sent on this call: 1,225 tokens. The model's reply has to fit in the space that is left.

A token is a small piece of text, often a short word or part of a longer one. As a rough planning figure for English (the real count depends on the model), a token is about three quarters of a word, so the 25-token question is a bit under 20 words.

The context window is everything the model can see on one call: the instructions, the tool descriptions, the messages, the tool results and the reply it writes. Context is just the set of tokens the model is given when it writes (source), and the window limit covers all of it (Context windows doc).

Current Claude models have windows of up to 1M tokens, depending on the model (Context windows doc). That number is not the point. Curation is: what you choose to put in.

A common mix-up: the model remembers earlier calls

It is tempting to think the model carries the chat in its head. Try it: send the call "Book it" alone. The window holds the instructions and those two words, so the model has no idea what "it" is.

That matches what you learned before: the model knows only its training plus the text it is given.

A common mix-up: the window is the training data

They are different things. The window is the model's working memory for this call, and it is different from the large body of data the model was trained on (Context windows doc).

Example: the manual PDF your team uploaded last week was never in the training. The model can only use it if it is in the window.

Check yourself

A student's second message is only "Book it." The program sends just that message plus the instructions. What does the model do?

Show the answer

The second option. Only the instructions and "Book it" are in the window, so the model has nothing to resolve "it" against.

Conversation history: what is kept between steps, and what each step costs 5 min

Between steps the model remembers nothing, so the program sends the whole history again on every call. That makes every step a little more expensive than the one before.

Here's a bigger request: "Is the laser cutter free Friday, and what is the max cut speed for 3 mm acrylic?" It needs two tools, so the loop makes three calls.

Worked example: three calls (illustrative numbers)
  1. Call 1 sends 1,225 tokens (from part 1). The model writes a request for check_calendar(laser, Friday): 60 tokens.
  2. The program runs it, as you learned in the agent loop. The result is "Friday 13:00 to 15:00 free": 350 tokens.
  3. Call 2 sends 1,225 + 60 + 350 = 1,635 tokens. The model asks search_manual("laser acrylic 3 mm speed"): 70 tokens.
  4. The result is one manual page: 1,800 tokens.
  5. Call 3 sends 1,635 + 70 + 1,800 = 3,505 tokens. The model writes the final answer: 90 tokens.
  6. Add up the input of all three calls: 1,225 + 1,635 + 3,505 = 6,365 tokens. The window at the very end holds only about 3,595.

This is the history: every earlier message, tool request and tool result, kept by the program and resent in full each time. Each user message and assistant response accumulates in the window, and previous turns are preserved completely (Context windows doc).

Everything in the request counts: the system prompt, every message including tool results, and the tool definitions (Context windows doc). The total of 6,365 is the lesson's own arithmetic from that rule: the input sent over all three calls, before any caching discount.

Look at call 3. The manual page is 1,800 of its 3,505 tokens, a bit over half. So a big tool result is the main thing to watch, and tools should return information in a token-efficient way (source).

Why you care: your sponsor's budget is small, and cost grows with every step, not just with every question.

A common mix-up: you only pay for the new message

It feels natural, since you only typed one new thing. But the example above sent 6,365 tokens in total for a conversation whose final window is about 3,600.

A common mix-up: tool results are free

The tool did the work, so it seems free. But the 1,800-token manual page is part of the input on every later call, not just the call that fetched it.

Check yourself

A fourth call follows. The last answer was 90 tokens and the student adds a 30-token question. How many tokens does call 4 send?

Show the answer

The third option: 3,505 + 90 + 30 = 3,625.

Context rot and compaction: why a full window is not a better window 5 min

Fitting more into the window does not make the model use it better, so you choose what stays. When history grows, you trim it by clearing old tool results or by summarising.

Back to the example. After call 3 the student asks a follow-up, and the window holds 3,595 tokens. Of those, 1,800 are the old manual page nobody needs anymore.

Worked example: two ways to trim (illustrative numbers)
  1. Option A, clear the old tool result. Replace the 1,800-token page with a 20-token placeholder: "manual page for laser, p. 14, cleared; search again if needed". The window drops from 3,595 to about 1,815.
  2. Option B, summarise. After a 40-message chat about a project, replace the first 35 messages with a 300-token summary: "Student wants to cut 3 mm acrylic on Friday 13:00 to 15:00, has finished laser training, not yet booked." Keep the last 5 messages word for word.
  3. What can go wrong: the summary drops "not yet booked", and the assistant tells the student they are already booked.

Compaction means taking a conversation that is nearing the window limit and summarising its contents so the chat can go on (source). Option B is compaction.

Option A, tool result clearing, is one of the safest, lightest-touch forms of compaction (source). Both compaction and clearing old tool results are standard ways to manage a growing window (Context windows doc).

Why bother, if the window is huge? Because as the token count grows, accuracy and recall degrade. That is called context rot (Context windows doc).

One way to think about it: the model has an "attention budget" that it spends on everything in the window (source). Every extra token spends a little of it.

A common mix-up: a bigger window means I can put everything in

Picture a window of 120,000 tokens holding 12 machine manuals, while the student asks about one machine. The paragraph that answers the question is a needle in a haystack, and the model's accuracy and recall can slip as the haystack grows.

A common mix-up: a summary loses nothing

Look at Option B again. One missing phrase, "not yet booked", flips the assistant's answer from right to wrong. A summary is a guess about what will matter later.

Check yourself

The window holds an old 1,800-token manual page that the student no longer needs. Which fix is the lightest?

Show the answer

The first option. The page is the biggest piece and the least likely to be needed again, so swap it for a pointer.

Retrieval: finding the right page in a long manual 6 min

When the material is too long to put in every call, keep it outside the window and fetch only the few pieces the question needs. That is retrieval, and it is how the assistant stays cheap while the manuals stay long.

Here's the size of your problem. Say you have 12 machine manuals of 40 pages each. That is 480 pages, and at about 400 tokens a page it comes to roughly 190,000 tokens (an assumption for teaching, in line with the rule that about 500 pages is 200,000 tokens, from the contextual retrieval post).

Worked example: one question, retrieval against pasting (illustrative numbers)
  1. Student: "What speed do I use for 3 mm acrylic on the laser?"
  2. Pasting everything sends 190,000 tokens on every call, and the loop from part 2 resends it on each step.
  3. With retrieval, the manuals were split once, ahead of time, into chunks of about 300 tokens each. That is about 630 chunks. The tool search_manual scores the chunks against the question and returns the top 3, so 900 tokens come back.
  4. The model answers from those 3 chunks: "Speed 20 mm/s at 60 W (laser manual, p. 14)".
  5. A problem shows up. One chunk says "Keep the setting at 60 and do not exceed it", and it does not say which machine or which setting. On its own it is useless, or worse, misleading.
  6. The fix: before indexing, add one line of context to each chunk, such as "From the laser cutter manual, section 4, cutting acrylic."

A chunk is a small piece of a long document, cut ahead of time so you can fetch just the pieces you need. Retrieval is searching those chunks and adding only the best few to the call.

The step-6 fix is the idea of contextual retrieval. In Anthropic's own test, combining contextual embeddings with contextual keyword search cut the top-20 retrieval failure rate from 5.7% to 2.9% (Introducing Contextual Retrieval). That is their test, not a promise for your makerspace.

There are two ways to search. Search by meaning uses embeddings, which turn text into numbers so similar ideas land close together: it can match "slow down for thick plastic" to a chunk that says "feed rate".

Search by keywords, using a method called BM25, matches exact words: it finds an error code such as "E-204". Real systems use both, because BM25 complements embeddings for exact terms like identifiers (source).

Notice you never put the whole manual in the window. You keep a way to find it, and load only the piece you need, just in time (source).

The rule of thumb in the same post: if your knowledge base is smaller than about 200,000 tokens (around 500 pages), you can just put all of it in the prompt, and prompt caching makes that faster and cheaper. Your 190,000-token example sits right at that edge. Treat "retrieve or paste?" as a decision you will defend at the design review, because the manuals will grow.
A common mix-up: retrieval means the model memorised the manuals

The model gets about 900 tokens per question and has seen nothing else. Ask a different question and different chunks arrive.

A common mix-up: retrieval always finds the right page

The "do not exceed 60" chunk is one case: found, but meaningless without its label. Another: a keyword-only search for "slow down for thick plastic" misses a chunk that says "reduce feed rate", since the words differ.

Check yourself

A student asks about error code E-204 on the 3D printer. Which search most likely finds the exact chunk?

Show the answer

The second option. Exact identifiers are what keyword search is for, which is why real systems use both kinds of search.

Notes: memory that survives between sessions 6 min

When a chat ends, the window is gone, so anything the assistant should know next visit has to be written down outside it. The assistant writes short notes, then reads them back when a student returns.

Meet Sam, student ID s-4821. Watch what happens across two visits.

Worked example: two sessions (illustrative)

Session 1, Monday

  1. Sam: "I finished the laser safety training. Can you remember that?"
  2. The model requests a notes action: create /memories/students/s-4821.md with "Laser: safety training done 2026-11-16. 3D printer: not started."
  3. The program, not the model, saves the file on its own storage and replies "File created successfully at: /memories/students/s-4821.md".
  4. Model: "Done, you are marked as trained on the laser."
  5. The chat ends and the window is thrown away. The file stays.

Session 2, Thursday, a brand-new window

  1. Sam: "Book the laser for Friday."
  2. The call starts with about 1,225 tokens and knows nothing about Sam. The model first views the notes folder and reads the line about laser training.
  3. Then it calls check_calendar, then book_slot.
  4. Final answer: "Booked laser Friday 13:00 to 15:00."

This is the memory tool pattern. The model asks for file operations, and your application runs them, so you control where and how the data is stored (Memory tool doc).

The files live in a /memories folder and persist between sessions. The model is told to view its memory directory before doing anything else, and a progress-file pattern has each new session open by reading those files (Memory tool doc).

Because your code does the saving, your code also has to keep it safe. Validate every path so a request can't escape the notes folder, cap how large a file can grow, and delete files nobody has opened in a long time (Memory tool doc). Student data is personal, so bring the privacy question to your design review.

Notes are also the same idea as structured note-taking: an agent keeps a NOTES.md-style file outside the window and reads it back later (source). And a note is a good home for a fact a summary might drop, like "not yet booked" from part 3.

Anthropic's own test (an internal evaluation set for agentic search) found memory plus context editing beat the baseline by 39%, and context editing alone by 29% (Managing context). That is their test, not a general result. The useful idea is the split: memory stores information outside the window, and context editing clears stale tool results inside it.

What to write down, and what to leave out

The booking calendar is not memory. It changes constantly, so ask the calendar tool every time: a note saying "Friday free" would go stale by tomorrow.

Keep notes for slow-changing facts, like training status or a preferred machine. This part is my own advice, not the docs': if a note and the official training record ever disagree, the record should probably win, and your design review should decide that.

A common mix-up: the model remembers Sam from Monday

Thursday starts at 1,225 tokens with nothing about Sam. If the notes file is never read, the assistant asks Sam to prove the training all over again.

A common mix-up: notes are always right

A note says "Sam: laser trained", but the training was revoked on Wednesday. The note is now stale. Likewise, notes do not live in the window forever: the file is viewed only when needed.

Check yourself

Which fact belongs in Sam's notes file?

Show the answer

The third option. It is slow-changing and personal. The calendar is live, and the chunks are shared and fetched per question.

Putting it together: worked example, faded practice, summary 6 min

Context, retrieval and notes each answer a different question, and a good design uses each for what it is best at. Now you use them together on one request.

Sam, a week later, says: "Book the laser Friday afternoon, and which setting for 3 mm acrylic?"

Worked example: all three together (illustrative)
  1. The window starts with instructions and tools (1,200 tokens) plus Sam's question.
  2. The model views the notes: "Laser: trained". A small read, about 40 tokens.
  3. It calls check_calendar: 350 tokens, "Friday 13:00 to 15:00 free". This is not saved in notes, because it changes.
  4. It calls search_manual: 3 chunks, 900 tokens.
  5. It calls book_slot: a 30-token confirmation.
  6. It replies with the booking and the setting, and writes one more note line before the end: "Sam usually books the laser on Fridays."
  7. The window is thrown away. Only the note stays.

Faded practice

A student asks about the 3D printer: "What temperature for PLA, and is the printer free Saturday morning? I did the printer training last week." Treat the question as about 40 tokens, and use the instructions and tools from part 1.

Step 1 (given). The window at the start holds: instructions (400), tool descriptions (800) and the question (about 40). That is about 1,240 tokens.

Step 2 (fill in two of three). Which of the three needs comes from notes, which from a live tool and which from retrieval? Given: training status comes from notes. Your turn: the calendar and the temperature for PLA.

Step 3 (blank). Trace the calls with token numbers you invent, and state the total input sent across all of them.

Step 4 (blank). What, if anything, should be written to notes at the end?

Hint 1

Which of these facts changes between visits?

Hint 2

Which of these is too long to send whole? And remember, each call resends everything so far.

Show a solution

Step 2. The calendar is a live tool call (check_calendar), because it changes constantly. The PLA temperature comes from retrieval (search_manual), because manual text is long and shared.

Step 3, one possible trace.

  1. Call 1 sends 1,240. The model asks to view Sam's notes: 50 tokens. Result, "3D printer: not started": 40 tokens.
  2. Call 2 sends 1,240 + 50 + 40 = 1,330. The model calls check_calendar: 60 tokens. Result: 350.
  3. Call 3 sends 1,330 + 60 + 350 = 1,740. The model calls search_manual: 70 tokens. Result, 3 chunks: 900.
  4. Call 4 sends 1,740 + 70 + 900 = 2,710. The model writes the answer: 100 tokens.
  5. Total input: 1,240 + 1,330 + 1,740 + 2,710 = 7,020 tokens. Your numbers will differ, but the pattern is the same: each call is bigger than the last.

Step 4. One line such as "Sam says printer training was done last week; not yet confirmed." Not the calendar slot and not the chunks. Because the note disagrees with Sam's claim, the assistant should say the record doesn't show it yet (the "record wins" rule is my own advice, for your design review).

A common mix-up: memory means the model learns

No weights change. The program saves text to a file and loads it back into the next window. Training and fine-tuning are out of scope for you here, and nothing in this lesson touches them.

Summary

  • The window is everything the model sees on one call, and it is rebuilt on every call.
  • Between steps the program resends the history, so each step costs more than the last, and a full window is not a better window.
  • Retrieval fetches a few chunks of a long manual instead of sending it whole.
  • Notes outside the window carry slow-changing facts between sessions, while live things like the calendar stay tool calls.

Say it in your own words: explain to a teammate why the assistant needs notes and retrieval even though the model can have a window of up to 1M tokens.

Why this matters in the real world. Your sponsor's budget is small, and every token you resend costs money. At the design review, you can now argue what lives where: the window for the live chat, retrieval for the manuals, notes for each student.
