Context and memory in an agent: what it sees now, what it keeps, and what it looks up

By the end of this lesson you can say what goes into a model's context window on each call, what is carried between steps and between sessions, and when to fetch text by retrieval or save notes as memory instead of keeping everything in context.

In short: context is the text the model is handed on one call, and memory is anything saved outside that text so it can be brought back later.

Objective O3: decide what an agent keeps in context, saves, and looks up About 30 minutes Builds on: what a model knows, and the agent loop
Why this matters for you

Your makerspace assistant has to answer from long machine manuals and remember each student between visits, all on a small model budget. Where each piece of information lives decides both whether it works and what it costs.

Context window: what the model can see on one call

The model can only use the text it is handed on each call, and that text has a size limit. So before we talk about keeping anything, we need to know what that text is made of and how it is measured.

Warm-up recall

1. In the agent loop, who actually runs the tool, the model or your program?

Check your answer

Your program. The model only asks for the tool as text, and the program runs it and sends the result back. That hand-off is what we count today.

2. Why can a chatbot state an outdated fact with confidence?

Check your answer

It only knows its training plus the text it is given, and training stopped at some date. Today is about the second half: the text it is given.

Models read and write in tokens: small pieces of text, often a whole word, sometimes just part of one. Limits and costs are counted in tokens, so you can manage them by counting (token counting docs).

Here are two real counts from those docs. A request with the system prompt "You are a scientist" and the user message "Hello, Claude" counts as 14 input tokens. A different request, with one small weather tool described and the question "What's the weather like in San Francisco?", counts as 403. The two requests differ in more than the tool, so don't read the gap as the tool's price; the docs just say tool definitions count too (context windows docs).

Counts are estimates, and newer models can turn the same text into about 30 percent more tokens, so recount for the model you pick (token counting docs). Every token count in the makerspace examples below is a number I made up to keep the sums easy, not a measurement.

Now the first call your assistant makes. A student asks about the laser cutter.

Worked example: one call
  1. The student says: "Is the laser cutter free on Friday?" That is 20 tokens.
  2. The program builds the request. First comes the system prompt, the standing instructions that tell the model its job: 600 tokens.
  3. Next come the tool definitions, descriptions of each tool the model may ask for (check_calendar, book_slot, search_manuals): 900 tokens. Then the student's 20 tokens. Input total: 1,520.
  4. The model answers with a tool request, check_calendar(machine="laser cutter", date="Friday"): 40 tokens of output.
  5. Whatever a tool sends back later is a tool result, and it joins the request too. For now, everything the model knows about the makerspace is in those 1,520 tokens.

That whole stack is the context window: all the text the model can reference when it writes a response, including the response itself (context windows docs). Think working memory, the stuff on the desk right now, as opposed to what training put in its head. Current models go up to 1M tokens, depending on the model.

The window is also a cost lever. The whole stack goes out on every call, so what you put in it is what you pay to send. That is my own reasoning about cost, so check your provider's price list; caching can change the price, but not whether the tokens count (context windows docs).

A common mix-up

"The model remembers the makerspace because it was told once." It's tempting because chat feels continuous. But the 600-token system prompt is sent again on every call; leave it out of call 2 and the model has no idea it is the makerspace assistant.

A common mix-up

"Only my question counts." In the example the question is 20 of 1,520 tokens, about 1 percent. The rest is instructions and tool descriptions.

Conversation history: what is kept between steps

The model itself keeps nothing from one call to the next, so the program has to resend everything each time. That is why every step makes the next one bigger and costlier.

Each step of the agent loop is a separate call. The program holds the list of messages so far, the conversation history, and adds to it. Each call's input is all the earlier history plus the new message (context windows docs).

Worked example: two steps, then a third call
  1. The student says: "Is the laser cutter free on Friday?" Call 1 input is 1,520 tokens, as before.
  2. The model outputs the tool request check_calendar(machine="laser cutter", date="Friday"): 40 tokens.
  3. The program, not the model, runs the tool. It gets back {"free": ["10:00-12:00", "15:00-17:00"]}: a 150-token tool result.
  4. Call 2 input is the old 1,520, plus the 40-token request, plus the 150-token result: 1,710 tokens.
  5. The model replies: "Yes, it's free Friday 10 to 12 and 3 to 5. Want me to book one?" That is 30 tokens, and the loop stops.
  6. Input across the two calls: 1,520 + 1,710 = 3,230 tokens, even though only 190 tokens of new text appeared between them. Output: 40 + 30 = 70 tokens.
  7. The student answers "Book 3 to 5, please" (10 tokens). Call 3 input is 1,710 + 30 + 10 = 1,750, because the earlier turn is still in the history.

Notice the pattern: nothing is removed, so each call is the last one plus the newest text. Call 2 cost 1,710 input tokens, not 190. The more steps an agent takes, the more it re-sends.

One more detail from the trace. The model's 40-token tool request was output on call 1, then it came back as input on call 2, and again on call 3. That is my own reading of the loop, but it is why a long agent run gets pricey faster than its text length suggests.

Quick recap: the model forgets between calls, the program remembers, and you pay in tokens for the program's good memory.

A common mix-up

"The model remembers the calendar result on its own." It feels that way, because the reply on call 3 fits the earlier answer. But if your program forgot to append the 150-token result before call 3, the model would see no calendar data and might invent times.

A common mix-up

"A step costs only its new text." Step 2 carried 1,710 input tokens, not the 190 that were new.

Context rot and compaction: why a fuller window is not a better one

A big window does not mean the model uses everything in it equally well, and old tool results mostly sit there doing nothing. So the assistant should keep only what the next step needs and drop or shrink the rest.

Here's what that looks like. A student chats about the 3D printer and asks five questions in a row.

Worked example: five manual lookups
  1. Each answer needs a manual page. search_manuals returns about 3,000 tokens per lookup.
  2. After five lookups the history holds 1,520 + 5 × 3,000 = 16,520 tokens (ignoring the short replies).
  3. The next question is "what temperature for PETG?", and only the latest page matters.
  4. The program replaces the four older results with a one-line placeholder such as "[page 41 read, removed]". New size: 1,520 + 3,000 = 4,520 tokens.
  5. The next call is 12,000 tokens smaller, and the model has less to be distracted by.
  6. If the student keeps going for an hour, the program asks the model for a short summary of the chat and starts a new window with that summary.

Why bother, when windows reach 1M tokens? As the token count grows, accuracy and recall degrade, an effect called context rot, and what you curate matters as much as how much room there is (context windows docs).

The goal is the smallest set of high-signal tokens that gets the job done (Anthropic engineering). It's a cost link too: a 3,000-token page left in the history is resent on every later call.

Two fixes, lightest first.

  • Clear old tool results. This is one of the safest, lightest-touch fixes, and exactly what step 4 did (Anthropic engineering).
  • Compaction. When a conversation nears the limit, summarize it and start a new window from the summary (same post; the context windows docs cover it too).
A common mix-up

"A 1M-token window means I can leave everything in." Windows do go that high, yet recall degrades as tokens grow, and in the example 16,520 tokens are sent each call while only 3,000 matter.

A common mix-up

"Clearing results loses the answer." The student's questions and the model's replies stay; only the raw page text goes. If the student circles back to page 2, the model calls search_manuals again and the 3,000 tokens come back.

Retrieval: finding the right page in a long manual

When the manuals are too long to keep in the window, the assistant looks up only the few pieces it needs when a question comes in. That leaves the window small and the answer grounded in the real page.

Retrieval means searching a body of text for the pieces that match the question and putting only those in the context (Anthropic, Contextual Retrieval). In Part 3, search_manuals returned whole pages. Here it returns just the best few pieces.

Worked example: one lookup, then an error code
  1. The student says: "What power and speed for 3 mm acrylic on the laser cutter?"
  2. The model calls search_manuals(query="laser cutter acrylic 3 mm power speed", top_k=3). The top_k=3 just means "send back the best three matches".
  3. The program searches the manuals and returns three short pieces of about 300 tokens each, 900 in all. The best reads "Laser cutter manual, p. 52, cutting acrylic: 3 mm, 60% power, 12 mm/s".
  4. Those pieces become tool results in the history, just like in Part 2.
  5. The model replies: "For 3 mm acrylic on the laser cutter, use 60% power at 12 mm/s (manual page 52)."
  6. Second case: the student types "Printer shows E-47". A search by meaning returns general error-handling pages, while a search by the exact characters finds the piece containing "E-47". The program combines both.

Those pieces are chunks: the manuals are split ahead of time into small bits, a few hundred tokens or fewer (my rule of thumb). Each chunk is then indexed two ways. One is by meaning, with embeddings, where each chunk becomes a list of numbers that captures its meaning and can be searched by similarity.

The other is by exact words (BM25), which catches things like error codes that a meaning search can miss. The source's own example is the query "Error code TS-999" (Contextual Retrieval).

Chunks lose context. A chunk saying "revenue grew 3%" does not say which company or quarter, and for us a chunk saying "Set power to 60%" does not say which machine or material. The fix is a one-line label, such as machine and section, added to each chunk before indexing (Contextual Retrieval).

You can also keep a lightweight pointer, like a file path or page id, and load the full text only when it is needed (Anthropic engineering).

One honest caution: if the whole knowledge base is under about 200,000 tokens (roughly 500 pages), you can put it straight in the prompt, and prompt caching makes that cheaper (Contextual Retrieval). My advice for your team: count the manuals' tokens first, start without retrieval if they fit, and add it when they don't or when cost per request is too high.

Retrieval quality is measurable too. In Anthropic's tests the top-20 failure rate fell from 5.7% to 1.9% with contextual embeddings, contextual BM25 and reranking (Contextual Retrieval). You don't need to build that now.

A common mix-up

"Retrieval means the model has learned the manual." It only sees the 900 tokens returned for this question. Ask about a different machine next and it must search again.

A common mix-up

"A chunk explains itself." "Set power to 60%" could be the laser cutter or the engraver, with different material settings. Without a machine label, the search may hand back the wrong one.

A common mix-up

"Always build retrieval." If your manuals turn out to be well under the roughly 500 pages the 200,000-token mark stands for, you can skip it. Count yours first; the real reason to add retrieval is size or cost per request.

Persistent memory: notes that last between sessions

When a conversation ends, everything in the window is gone, so anything the assistant should know next time has to be written down outside it. The assistant can then read those notes at the start of the next session.

Between steps, your program holds the history. Between sessions, nothing is kept unless the program saves it. Memory here means notes the assistant saves outside the context, in files it reads back when needed (memory tool docs).

Worked example: Monday, then Thursday
  1. Monday. The student says: "I just finished the laser cutter safety training. Also, I always book mornings."
  2. The model calls memory(command="create", path="/memories/students/maya.md", file_text="Prefers morning slots. Said on Monday they finished laser cutter training (unverified, check the training record).").
  3. The program writes the file and returns "File created successfully at: /memories/students/maya.md".
  4. The model replies: "Nice, noted. I'll suggest mornings when you book."
  5. Thursday, a new window with an empty history. The student says: "Book the laser cutter Saturday."
  6. The model first looks at its memory folder, memory(command="view", path="/memories"), sees students/maya.md, and opens it with memory(command="view", path="/memories/students/maya.md"). The program returns the file's text each time.
  7. The model calls check_calendar(machine="laser cutter", date="Saturday") and gets {"free": ["09:00-11:00", "14:00-16:00"]}.
  8. Reply: "Saturday morning is free, 9 to 11. Want me to book it? I'll check your training record first."

The Thursday window held nothing from Monday until step 6 put the notes back in.

The memory tool is the same loop as any tool. The model asks for a file operation under a /memories folder: view, create, str_replace, insert, delete or rename. Your application runs it and returns the result, so the data lives in storage you control (memory tool docs).

When the memory tool is on, the API adds an instruction to the system prompt to view the memory directory first, so the model checks its notes before anything else (same page).

A few safeguards belong in your code: validate every path so it stays inside /memories, cap how big a file can grow, delete files nobody has opened in a long time, and validate and strip sensitive data before it is written (same page).

My own design advice, not the docs': a fact that decides whether a student may use a machine, like training status, should live in the makerspace's own record that the program looks up through a tool. The notes file holds soft things like "prefers mornings". A model-written note can be stale or wrong, so it is not a safety record.

So how is this different from retrieval? Retrieval reads a fixed body of text someone else wrote. Notes are written by the assistant for its future self. Both are memory in the sense that they live outside the window and come back on demand: retrieval is the library, notes are the assistant's own notebook.

A common mix-up

"The model remembers me between chats." Thursday's window starts empty. Without step 6, it has no idea the student likes mornings.

A common mix-up

A common mix-up

Context design: deciding where each piece of information lives

Every fact an agent needs has one best home: always in context, looked up when needed, or saved between sessions. Choosing the home for each fact is the design decision you will defend in review.

Worked example: a full request, every piece placed

Maya writes: "Can I use the CNC router tomorrow afternoon? I'm a new user."

  1. The system prompt carries the role and the rule "check the training record before booking": 600 tokens, always there.
  2. The tool definitions are also always there: check_calendar, book_slot, search_manuals, get_training_status (a new tool that looks up a student's record) and memory (from Part 5).
  3. The notes are read at the start: "prefers mornings".
  4. search_manuals("CNC router new user rules") returns two chunks, 600 tokens.
  5. get_training_status("maya") returns {"cnc_router": "not completed"}, kept for a few steps, then cleared.
  6. Reply: "Not yet. The CNC router needs the intro session first (manual p. 4). Want me to find one?" The model also calls memory to add "asked about CNC router; needs intro session" to Maya's notes.

Summary
  1. The model sees only the context window, and everything in it is counted in tokens.
  2. The program keeps the history between steps and resends it, so each step costs more than its own text.
  3. A fuller window is not a better one: trim old results and compact long chats.
  4. Retrieval fetches the few matching chunks from long manuals; notes carry facts between sessions.
  5. Place each fact where it belongs: always in context, looked up, or saved.

Say it in your own words: tell a teammate why the assistant doesn't paste all the manuals into every call.

Why it matters: your sponsor's budget is paid in tokens, so context choices are cost choices. Each of the three homes is a line you can defend at the design review. Cost and workflow choices come in later lessons, and tool descriptions are next in the mission.
