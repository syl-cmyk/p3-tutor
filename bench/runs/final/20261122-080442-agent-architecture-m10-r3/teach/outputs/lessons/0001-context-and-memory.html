Context and memory: what an agent sees now, and what it keeps for later

By the end of this lesson you can say what is inside the model's window at each step of an agent loop, what survives between steps and between sessions, and when to use retrieval or saved notes.

Objective O3: context, memory and retrieval in an agent About 10 minutes Builds on: the agent loop
Why this matters for you

Your makerspace assistant has to answer from long manuals and remember each student's training status. This lesson is how you decide where each piece of information lives.

Warm-up

In the agent loop, who runs the tool, the model or the program? And is each step a separate model call?

Check your answer

The program runs the tool; the model only asks for it. Yes, each step is its own model call, and that is exactly why today's topic matters.

Context window: what the model can see on one call

The model can only use the text it is handed on each call, and that text has a size limit.

Size is counted in tokens: small chunks of text. As a rough rule of thumb, one token is about three-quarters of a word, so 750 tokens is about a page and a half.

Worked example: the assistant's first call

A student asks: "Is the laser cutter free Friday?" Here is everything sent, with illustrative sizes (made up for teaching, not measured):

  1. System prompt: "You are the makerspace assistant..." (about 300 tokens).
  2. Descriptions of the tools search_manual and check_calendar (about 700).
  3. The student's question (about 10).
  4. The model's reply, which counts too (about 100).

Total: about 1,110 tokens.

That total is the context window: everything the model reads and writes on one call, with a fixed maximum size. The system prompt, messages, tool results, tool definitions and the output all count (context windows doc).

A common mix-up

"The window holds only my question." It doesn't: here the question is 10 of about 1,110 tokens.

"The window is what the model learned in training." Also no. Ask a question about a machine the model never saw in training and it can answer only if the manual text is in the window: the window is working memory for this call (context windows doc).

Context between steps: what the loop carries forward

The model remembers nothing from one call to the next, so the program sends everything again each step. That is why the window fills up and why cost grows.

Worked example: a booking request (illustrative numbers)

The student says: "Book the laser cutter Friday 2 pm."

  1. Call 1 input: 2,000 tokens (a longer prompt than before, plus a third tool, book_slot, and the question). The model asks to call check_calendar. Output: 100.
  2. The program runs the tool. The result is 500 tokens: "Fri 2 pm: free."
  3. Call 2 input: 2,000 + 100 + 500 = 2,600. The model asks to call book_slot. Output: 100.
  4. The result is 1,500 tokens: a confirmation plus a long policy text.
  5. Call 3 input: 2,600 + 100 + 1,500 = 4,200. Output: 150, the final reply "Booked."
  6. Input tokens paid for, before any caching discount: 2,000 + 2,600 + 4,200 = 8,800, though the text itself is only 4,200 long. Output total: 350.

The more that piles up, the worse the model's recall gets. That is context rot, and it grows as the text grows (context windows doc).

Two light fixes: clear old tool results, or summarise the history, which is called compaction (context engineering). The rule: keep only what helps.

A common mix-up

"The model remembers earlier steps by itself." Call 3 only knows the slot was free because the 500-token calendar result was inside the 4,200 tokens sent. Take it out and the model can't know.

"A bigger window means I can paste everything, for free." A 30,000-token manual pasted in is paid for again on every step: three steps are 90,000 input tokens for the manual alone. Context rot hurts quality too.

Notes between sessions: what survives when the conversation ends

When a session ends, the window is gone. So anything the assistant must know next time has to be written down outside the window and read back in.

A session is one conversation, from first message to end. Notes are text saved in a file or database by the program, outside the window. Memory is anything the assistant can bring back into the window later: notes are one kind, and retrieval, coming next, is the other.

Worked example: two visits by one student, Riley
  1. Monday: Riley says "I finished the laser cutter safety training." The model calls the memory tool: create /memories/riley.md with "Laser cutter training: done, Mon." The program saves the file.
  2. The session ends. The window is thrown away.
  3. Thursday: new session, empty window. The model calls view /memories, then view /memories/riley.md. The program returns the file's text.
  4. Riley asks to book the laser cutter. The window now says "training: done", so the model books it.

The memory tool is client-side: the model requests file operations and your app runs them, on storage you control (memory tool doc). It is one way to do notes, not the only way.

A common mix-up

"The model learns from the chat and will remember Riley." Training doesn't change during use. Delete riley.md and on Thursday the assistant asks about training again.

"The provider stores the memory." Not with this tool: your team decides where files live, how big they get and how long they last (memory tool doc).

Retrieval: finding the right page in a long manual

A long manual will not fit in the window every step, and it should not. So the assistant fetches just the pieces it needs, when it needs them.

A chunk is a short piece of a document, usually a few hundred tokens. Retrieval is a search that finds the chunks that best match the question and puts only those in the window; this is one common way to do it (contextual retrieval).

Worked example: one question (illustrative numbers)
  1. Riley asks: "What speed do I use for 3 mm acrylic on the laser cutter?"
  2. Ahead of time, the 40-page manual (about 30,000 tokens) was split into about 100 chunks of about 300 tokens.
  3. The model calls search_manual with "laser cutter acrylic 3 mm speed". The program returns the top 3 chunks, about 900 tokens.
  4. The model reads chunk 2, "Acrylic 3 mm: speed 20 mm/s, power 60%", and replies with the setting and the page number.
  5. Window cost: 900 tokens instead of 30,000.

Search can match exact words, like a machine's model number, or match by meaning. Many systems use both (contextual retrieval).

If a whole knowledge base is under about 200,000 tokens, you can skip retrieval and put it all in the prompt (contextual retrieval). Your assistant will have many manuals and pays for the window every step, so retrieval is the safer default; that's a cost and quality call to defend, not a rule.

A common mix-up

"The model searches the whole manual itself." The program runs the search, and the model only sees what comes back. Search "acrylic speed" and get the 3D printer's chunk "PLA speed: 60 mm/s" instead, and the model may guess wrong.

"Retrieval and notes are the same." Notes are what the assistant wrote about this student; retrieval reads a document your team wrote. Both end the same way: text in the window.

Context budgeting: deciding what goes where

Context budgeting is this lesson's name for one decision: where each piece of information lives. Every piece of information has to live somewhere: in the window now, in notes for later, or in a document to retrieve. So the last skill is sorting each item into the right place.

Worked example: four items sorted

Student's name and requestWindow nowSmall, and needed this step.
Training status of each studentNotesDiffers by student and must survive sessions.

For each item, say whether it goes in the window now, in notes, or in retrieval. Items: (a) "the student prefers morning slots, told in this chat"; (b) "the 3D printer's 25-page manual (about 18,000 tokens)"; (c) "the booking made 3 steps ago".

  1. First ask: does it need to survive after this chat ends? (Given: only (a) does, so it goes in notes.)
  2. For (b): ______
  3. For (c): ______
Hint

For (b), ask whether it is long and only a small piece is needed per question. For (c), ask whether it is still needed now, or can be cleared or summarised.

Show the solutions

(a) Notes: it matters on later visits. (b) Retrieval: long, and only a few chunks are needed per question. (c) Window now, then clear or summarise it once it's done; it isn't notes, because nothing about it needs to outlive this chat.

Why it matters: your model budget is small, and tokens in the window are paid for again every step. This is the choice you'll defend at your design review.

Summary and go further

Everything the model uses reaches it as text in the window, so the job is choosing what goes in.

  • The context window is everything the model reads and writes on one call, and it has a limit.
  • The model keeps nothing between calls, so the program resends the history each step, which is why long loops cost more.
  • Between sessions, only saved notes survive, and they matter only once read back into the window.
  • Retrieval puts a few matching chunks in the window instead of the whole manual.

Say it in your own words: why does the assistant know on Thursday that a student finished training on Monday?
