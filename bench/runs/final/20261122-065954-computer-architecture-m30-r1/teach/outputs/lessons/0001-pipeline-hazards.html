Pipeline hazards: why a pipeline stalls and what each stall costs

A hazard is anything that stops the next instruction from moving on in the next cycle. There are three kinds, and each one makes the pipeline wait for a different reason.

By the end of this lesson you can look at a short run of instructions in a 5-stage pipeline, say which kind of hazard (structural, data or control) holds each one up, and count the cycles lost.

Objective O2: explain why a pipeline stalls About 30 minutes
Why this matters for you

You want to know why a loop with many branches runs slower. You also want to know if more pipeline stages are worth it. Both questions come down to counting stall cycles, and that's exactly the skill you build here.

Pipeline timing: one instruction is not faster, many finish sooner 6 min

A pipeline doesn't make any one instruction quicker; it makes lots of them finish sooner. We start with the clock of a smooth pipeline, so you can see what a stall breaks.

Warm-up recall

1. Pipelining overlaps instructions. What does that raise?

Check your answer

Throughput: more instructions finish per second. Keep that word in mind, because today it gets a twist.

2. In a cache, how do you find out that an access is a miss?

Check your answer

The line at that index is empty, or the tag in the address differs from the tag stored there. The access then has to wait for slower memory, and waiting is today's whole theme.

Here are the rules of our toy machine. Every count in this lesson follows from them, so I'll say them once and reuse them.

  • Five stages: IF (fetch the instruction), ID (decode it and read registers), EX (execute), MEM (use data memory) and WB (write the result back to a register). Each stage takes one cycle, so a lone instruction takes 5 cycles. The Utah slides use the same five stages.
  • Registers: a write in WB happens in the first half of its cycle and a read in ID in the second half. So an instruction can read a register in the same cycle an earlier one writes it. That's our convention, and real designs do access registers in half cycles (Utah slides 11-12).
  • No shortcuts: a result can't be passed along early. That trick comes in a later lesson, so here a wait is plain waiting and easy to count.
  • Memory: instructions and data have separate memories, until part 3 changes that.
  • Branches: a branch is decided at the end of EX, and the machine stops fetching until then. That's our assumption; part 5 explains it.
Worked example: 5 instructions on the clock

Say each stage needs 2 ns. An unpipelined machine does all five stages for one instruction, so 10 ns, then starts the next one. The pipelined machine adds 0.2 ns per stage to hand work from stage to stage, so its clock tick is 2.2 ns. Call the instructions I1 to I5.

  1. Cycle 1: I1 is in IF. Nothing else has started.
  2. Cycle 2: I1 moves to ID, and I2 enters IF.
  3. Cycle 5: I1 is in WB and is done. At the same time I2 is in MEM, I3 in EX, I4 in ID and I5 in IF. Every stage is busy.
  4. Cycles 6 to 9: one more instruction finishes each cycle. I2 finishes in cycle 6, I3 in 7, I4 in 8 and I5 in 9.
  5. Five instructions took 9 cycles: 9 × 2.2 ns = 19.8 ns. Unpipelined, they'd take 5 × 10 = 50 ns.
  6. Now one instruction alone: 5 × 2.2 = 11 ns. That's slower than the 10 ns unpipelined.
  7. Scale up to 1,000 instructions. The first finishes in cycle 5, and 999 more follow, one per cycle, so 4 + 1,000 = 1,004 cycles. That's 1,004 × 2.2 = 2,208.8 ns, against 10,000 ns unpipelined.

The number to remember is the 4. The first instruction needs 5 cycles to come out, and every later one comes out one cycle after the one before. So N instructions take 4 + N cycles when nothing goes wrong.

A common mix-up

"Pipelining makes each instruction faster." It's tempting because programs do run faster. But one instruction takes 11 ns pipelined and only 10 ns unpipelined. The win is the crowd: 1,000 instructions in 2,208.8 ns instead of 10,000 ns.

Check yourself

A smooth pipeline runs 3 instructions with no waiting. In which cycle does the third one finish?

Show the answer

Cycle 7. The first instruction finishes in cycle 5, the second in 6 and the third in 7, which is 4 + 3.

Stall and bubble: a cycle where the pipeline waits, and what it costs 5 min

Sometimes an instruction can't move on when the clock ticks, so the pipeline waits. That wait is the thing we count, and every wait has a cause.

Let's make one wait happen. Take the same five instructions, I1 to I5. This time I3 isn't ready to leave ID when it should, so it has to wait one cycle there.

Worked example: one wait in a run of 5
  1. Cycles 1 to 3 are smooth: I1 is fetched in cycle 1, I2 in cycle 2, I3 in cycle 3.
  2. Cycle 4: I3 is in ID, but it can't go on.
  3. Cycle 5: I3 is still in ID. That repeated cycle is the stall, a cycle where an instruction can't move on and waits. I3 reaches EX in cycle 6.
  4. Cycle 5, the EX stage: I2 has already left and I3 hasn't arrived, so EX has nothing to do. That empty slot is the bubble. It travels down the pipe behind the stall: MEM in cycle 6, WB in cycle 7.
  5. I4 wants ID in cycle 5, but I3 is sitting there. So I4 stays in IF during cycle 5 and reaches ID in cycle 6.
  6. I5 can't overtake I4, so it's fetched in cycle 6. It finishes in cycle 10.
  7. Total: 10 cycles, instead of 9 for a smooth run.

A stall puts a bubble into the pipeline, which is just the stage doing nothing for a cycle. The result is still correct, only later. The hardware does this by inserting bubbles (no-operations) so the dependent instruction waits ([Wikipedia]).

A hazard is the cause of a stall: whatever stops the next instruction moving on. Now the formula, with this run as the example:

  1. Total cycles = 4 + N + stalls.
  2. The 4 is the fill time from part 1. N is the number of instructions: 5. Stalls is the number of waiting cycles: 1.
  3. 4 + 5 + 1 = 10 cycles, which matches the chart.
  4. CPI (cycles per instruction) is total cycles divided by N: 10 / 5 = 2.0. This is a tiny run, so the fill time inflates it. A smooth run of 5 would show 9 / 5 = 1.8.

Now a bigger case, where the fill hardly matters. A program runs 100 instructions and loses 20 cycles to stalls. That's 4 + 100 + 20 = 124 cycles, so CPI = 124 / 100 = 1.24.

With no stalls it would take 104 cycles. The 20 extra cycles are 20 / 104, about 19% more time. Over many instructions, stalls are what stops the CPI from sitting near 1.

A common mix-up

"A stall means the program got stuck or came out wrong." In the example the answer is exactly the same, it just arrives in cycle 10 instead of cycle 9. A stall costs time, never correctness.

One more thing before the check. You may be tempted to think every stall is a data problem, because data is what instructions pass around. It isn't. There are exactly three causes, and the next three parts show one each. Next up is a stall where no two instructions share a register: 9 cycles instead of 8.

Check yourself

A program of 50 instructions has 8 stall cycles. How many cycles does it take in total?

Show the answer

62 cycles: 4 for the fill, 50 for the instructions and 8 for the stalls.

Structural hazard: two instructions need the same hardware in the same cycle 5 min

The simplest cause of a stall is two instructions wanting one piece of hardware at the same moment. Nothing about the values matters here, only the hardware.

For this part only, give the machine one memory that holds both instructions and data, (Utah slides 9-10 show this case). Here lw loads a value from memory, and add, sub and or compute on registers. Only a load or a store touches data memory in MEM; the other instructions pass through MEM and do nothing. Here are four instructions:

lw  r1, 0(r2)
add r3, r4, r5
sub r6, r7, r8
or  r9, r10, r11
Worked example: one memory, one access per cycle
  1. Cycle 1: lw is fetched from memory. Cycle 2: add is fetched. Cycle 3: sub is fetched.
  2. lw goes on: ID in cycle 2, EX in cycle 3, then MEM in cycle 4, where it reads its data from memory.
  3. Cycle 4: or wants to be fetched, and that needs the same memory. The memory can serve one access per cycle, and the load is already in the pipe, so the load wins.
  4. or waits and is fetched in cycle 5. That's 1 stall.
  5. or then runs ID in 6, EX in 7, MEM in 8 and WB in 9.
  6. Total: 4 + 4 + 1 = 9 cycles, instead of 8.
  7. Look at the registers: r1, r3, r6 and r9 are all different. The instructions share no values at all, so this stall is not about data.

That's a structural hazard: multiple instructions contend for the same resource ([Utah slide 6]). The hardware is the problem, not the values it carries.

How bad can it get? Say 25% of a program's instructions are loads or stores. Each one blocks a fetch for a cycle, so CPI is about 1.25 (our own numbers).

The fix is more hardware: separate memories for instructions and data. With them, the same four instructions take 4 + 4 = 8 cycles and nobody waits.

A second case of the same idea: a register file with a single port would clash when one instruction writes in WB while another reads in ID. Our half-cycle rule (write first, read second) avoids that clash.

A common mix-up

"Every stall is a data hazard." It's tempting because instructions are all about data. But in the example r1, r3, r6 and r9 are four different registers and the pipeline still stalls: 9 cycles instead of 8.

Check yourself

With one shared memory, a machine runs sw r1,0(r2), add r3,r4,r5, sub r6,r7,r8 and xor r9,r10,r11. What happens to xor?

Show the answer

It waits 1 cycle. The store's MEM is in cycle 4, the same cycle xor's fetch would use the one memory, so xor is fetched in cycle 5.

Data hazard: an instruction needs a value an earlier one has not written yet 7 min

The next cause is about values: an instruction has to wait for a result that an earlier instruction hasn't stored yet. The hardware is free, but the answer isn't ready.

We're back to separate memories. Here are three instructions, where the second and third both use r1:

add r1, r2, r3
sub r4, r1, r5
or  r6, r1, r7
Worked example: waiting for r1
  1. add: IF in cycle 1, ID in 2, EX in 3, MEM in 4, WB in 5. It writes r1 in cycle 5.
  2. sub: IF in cycle 2. It wants to read r1 in ID in cycle 3, but r1 won't be written until cycle 5.
  3. sub sits in ID in cycles 3 and 4 (two stalls) and reads r1 in cycle 5. That works because the write is in the first half of cycle 5 and the read in the second half.
  4. sub then runs EX in 6, MEM in 7 and WB in 8.
  5. or: it's fetched in cycle 3, but sub is stuck in ID, so or stays in IF during cycles 3, 4 and 5. It enters ID in 6, then EX in 7, MEM in 8 and WB in 9.
  6. Total: 4 + 3 + 2 = 9 cycles. Smooth, it would have been 7.
  7. Notice that or never waited for r1, which was long written by cycle 6. It only waited for sub to get out of the way.

That's a data hazard: a dependent instruction cannot proceed because it needs a value that hasn't been produced yet ([Utah slide 6]). The specific shape here has a name, read after write: sub must read after add writes ([Wikipedia]).

The cost depends on how far apart the two instructions sit, and the gap here means how many instructions are between them:

Gap between writer and readerStallsWhy
0 (next to each other)2The reader wants r1 in cycle 3 and gets it in cycle 5.
1 instruction between1The reader reaches ID in cycle 4 and needs cycle 5.
2 or more between0The reader reaches ID in cycle 5 or later, and r1 is ready.

These counts are our own, from the half-cycle rule above. A later lesson on bypassing shrinks them, but we're not touching that here.

What if the value comes from a load instead of an add? In this machine, both write their result in WB in cycle 5, so a load costs the same stalls: 2 for a reader right behind it. Our counts match for both because there are no shortcuts yet.

Two common mix-ups

"Instructions only conflict when they're next to each other." The table shows a gap of 1 still costs a cycle, and only a gap of 2 or more is free.

"Any two instructions that use the same register stall." Look at sub r4,r1,r5 followed by or r6,r1,r7: both only read r1, so or loses 0 cycles to r1 (it reads r1 in cycle 6, long after the write in cycle 5). The problem is write, then read.

Check yourself

The code is lw r1,0(r2), then add r5,r6,r7, then sub r4,r1,r3. How many stalls come from r1?

Show the answer

1 stall. The load writes r1 in cycle 5. The sub is fetched in cycle 3 and would reach ID in cycle 4, so it waits one cycle and reads in cycle 5.

Control hazard: the pipeline does not know which instruction comes next 6 min

The last cause is about not knowing where to fetch from. After a branch, the machine can't tell which instruction follows until the branch is worked out.

A beq r1,r2,L jumps to the instruction at label L if r1 and r2 are equal, and carries on to the next instruction if not. Jumping is called taken; carrying on is called not taken, or falling through. Which of those two instructions to fetch is only known when the comparison is done. So the branch target is only known at the end of the branch's execution.

So here's our rule: after a branch, stop fetching until it's decided. Let's trace beq and the instruction it leads to. We assume r1 and r2 are ready, and the design is the one I stated up top.

Worked example: fetch waits for the branch
  1. Cycle 1: beq is fetched.
  2. Cycle 2: beq is in ID, reading r1 and r2. The machine doesn't know what to fetch, so it fetches nothing useful.
  3. Cycle 3: beq is in EX and compares the registers. Again nothing useful is fetched.
  4. End of cycle 3: the outcome is known.
  5. Cycle 4: the next instruction is fetched, the one at L (or the one after the branch, if it wasn't taken).
  6. Cycles 2 and 3 were wasted: 2 stalls.

That's a control hazard: the next instruction cannot be fetched because the outcome of an earlier branch is unknown ([Utah slide 6]). The cost is the number of stages up to and including the one that decides the branch, minus the one the branch already used for fetching. Here that's 3 − 1 = 2.

The same formula works for other designs. By it, deciding in ID would cost 2 − 1 = 1, and deciding in MEM would cost 4 − 1 = 3 (our own reasoning).

Now your mission question: why does a loop with many branches run slower? Take a loop with 5 instructions per iteration, the last one a branch, run 10 times.

  1. Each iteration takes 5 cycles of instructions + 2 stalls = 7 cycles.
  2. Ten iterations: 4 + 50 + 20 = 74 cycles.
  3. With no stalls it'd be 4 + 50 = 54. The branches cost about 37% more.
  4. If 20% of all instructions are branches, CPI = 1 + 0.2 × 2 = 1.4.

And the pipeline depth question. Imagine a 7-stage pipeline that decides the branch at the end of stage 5: the penalty is 5 − 1 = 4 cycles, double ours. That's our own reasoning, but it points one way: the more stages before the decision, the more stalls per branch. With 20% branches, CPI would be 1 + 0.2 × 4 = 1.8 instead of 1.4, so extra stages only pay off if the clock gets faster by more than that slowdown.

Two common mix-ups

"The stall only happens if the branch is taken." Here fetch waits for taken and not taken alike, 2 cycles either way, because the machine can't know which one it is until cycle 3 ends.

"A branch is a data hazard because it reads registers." Here r1 and r2 were already ready, and the cost came from not knowing the next address, not from a missing value.

Check yourself

In our design a branch is decided at the end of EX and falls through, not taken. How many cycles does fetch lose?

Show the answer

2 cycles. Fetch stops after the branch and restarts only once EX has finished, so taken and not taken cost the same.

Hazard classification: name the cause and count the cost 6 min

Now put the three causes together: for any run of instructions, ask what is being waited for, and add up the waits.

The three-question test
  1. Is some hardware being used twice in one cycle? That's structural.
  2. Is a value not written yet? That's data.
  3. Is the next instruction not known? That's control.
Worked example: all three kinds in one run

Separate memories, so no structural hazards. Here are four instructions, with sub being the one at L:

lw  r1, 0(r2)
add r3, r1, r4
beq r3, r0, L
sub r7, r8, r9
  1. lw: IF in 1, ID in 2, EX in 3, MEM in 4, WB in 5. It writes r1 in cycle 5.
  2. add: IF in 2. It needs r1, so it sits in ID in 3 and 4 and reads in 5: data, 2 stalls. Then EX in 6, MEM in 7, WB in 8.
  3. beq: IF in 3, and it stays in IF through cycle 5 because add holds ID. It enters ID in 6.
  4. beq needs r3, which add writes in cycle 8. So it sits in ID in 6 and 7 and reads in 8: data, 2 stalls. EX is in cycle 9 and the branch is decided at its end.
  5. sub: fetch waited, so it's fetched in cycle 10: control, 2 stalls. Then ID in 11, EX in 12, MEM in 13, WB in 14.
  6. Total: 14 cycles = 4 + 4 + 6.
InstructionCauseStalls
adddata (waits for r1)2
beqdata (waits for r3)2
subcontrol (next unknown)2
nonestructural0

One subtlety: sub sat idle in fetch for 4 cycles (6 to 9) while beq waited and then ran. The first 2 of those are already paid for by beq's data wait, so only the 2 after EX count as control.

As a check, a smooth run would end in cycle 4 + 4 = 8, and 8 + 6 stalls is 14. They agree.

Your turn: faded steps

Separate memories. Five instructions, with xor being the one at L:

add r1, r2, r3
or  r6, r7, r8
sub r4, r1, r5
beq r6, r0, L
xor r9, r10, r11

Step 1 (given): a smooth run would have add in IF in cycle 1 and WB in cycle 5, and or in IF in cycle 2 and WB in cycle 6. Each later instruction enters IF one cycle after the one before.

Step 2 (fill in): one of the later instructions has to wait for a register. Which instruction, which register, and which instruction writes it?

Step 3 (yours): count the stalls by cause, then the total cycles and the CPI.

Hint 1

What is the gap between add and sub? Look at the table in part 4.

Hint 2

In which cycle does add write r1, and in which cycle would sub first want to read it?

Hint 3

When does beq finish EX? Fetch restarts the cycle after that. Also check when or writes r6.

Show a solution

sub waits for r1 from add: it's in ID in cycle 4 and again in 5, so 1 data stall. beq is in IF in cycles 4 and 5, ID in 6 and EX in 7 (r6 was written by or in cycle 6, in time), so xor is fetched in cycle 8: 2 control stalls. Structural: none.

Total: 4 + 5 + 3 = 12 cycles, and CPI = 12 / 5 = 2.4.

Summary
  • A stall is a cycle where the pipeline waits, and a hazard is the cause.
  • Three causes: the same hardware twice (structural), a value not ready (data), and the next instruction unknown (control).
  • Total cycles = 4 + N + stalls, and CPI = total / N.
  • Pipelining raises throughput, not the speed of one instruction.
  • Why it matters in the real world: a loop full of branches runs slower because each branch costs stall cycles, and a deeper pipeline decides branches later, so it pays more per branch. Chip designers weigh that against a faster clock.
