Context and memory in an agent

By the end of this lesson you can say what is in the model's context at each step of the makerspace assistant's loop, what survives between sessions, and which of three tools (context, notes, retrieval) should hold each piece of information.

Objective O3: context and memory in an agent About 30 minutes Builds on your earlier session on the agent loop
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both jobs come down to one decision you will defend at your design review: what goes into the model's context, what is saved outside it, and what is fetched only when needed.

The context window 6 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Here is everything the model is given for its very first call:

  • the system prompt: your instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool descriptions: the names, purposes and arguments of check_calendar, search_manuals, check_training_record, book_machine;
  • the student's message.

All of this is text, and the model reads only text. That bundle is the model's context: the set of tokens included when the model is asked to write its next output (Anthropic, Effective context engineering for AI agents). A token is the small chunk of text the model reads and writes, often a short word or part of a longer one; a rough rule for English is that a page of text is several hundred tokens. The context window is the maximum number of tokens the model can take in and produce in one call. It is the model's entire working view: if something is not inside it, the model cannot use it.

If you guessed that tokens are "words" and the window is "how much the model can remember", you were close. Better: the window is not memory, it is the page the model is handed on each call. Current Claude models have windows of up to about one million tokens, and the API returns an error when the input alone is larger than the window (Claude docs, Context windows). Sizes change with models, so look up the current figure when you pick one.

Two things follow, and both matter for your budget. First, you pay for tokens: every token sent in, and every token written out, is billed. Second, a bigger window does not mean you should fill it. We will see why in a moment.

Check yourself

A student's booking was confirmed last week, and the confirmation is stored in your booking database. It is not in the text sent on today's call. Can the model use it to answer today's question?

No. Only text in the context on this call is available to the model. To use the booking, a tool must fetch it and the result must enter the context.

What is kept between steps 6 min

Now the question from the warm-up. In the agent loop, each step is a separate model call. Between calls, the model keeps nothing. What is kept is a list the program holds: the message history, every message so far, in order. On each call the program sends the whole list again, with the newest result added at the end. The model "remembers" the earlier steps only because they are re-sent as text.

Here is the laser-cutter request, step by step. The token counts are made up for the example, but the pattern is real.

CallWhat is in the contextInput tokens
1System prompt and tools (1,500), question (50)1,550
2Call 1 + the model's request (50) + calendar result (300)1,900
3Call 2 + request (50) + manual excerpt (2,000)3,950
4Call 3 + request (50) + training record (100)4,100

The student sees one answer. Your bill sees four calls, with a total of 1,550 + 1,900 + 3,950 + 4,100 = 11,500 input tokens, even though only about 2,500 tokens of new information ever arrived. Each step re-pays for the earlier ones. (Prompt caching can make a repeated start of the context cheaper; it reduces the price of the repeat, not the repeat itself. See Anthropic on contextual retrieval for how caching is described.)

A common mix-up

"The model remembers the earlier steps." It feels true, because the assistant seems to carry on a thought. But nothing persists inside the model between calls. If your program forgot to re-send the calendar result, the model on call 3 would not know the laser cutter was free. This is good news for you: you decide what stays in the history, and what you leave out is gone and costs nothing.

When the context gets too full 5 min

If the context grows with every step, and a window is finite, two problems appear: cost, which you have just seen, and quality. Anthropic's engineers describe context rot: as the number of tokens in the context grows, the model's ability to accurately recall information from it decreases. They treat context as a finite resource with diminishing returns, so the aim is "the smallest set of high-signal tokens" that makes the right behaviour likely (Anthropic, Effective context engineering for AI agents).

Think of a student desk. A desk with the one manual page you need is easier to work from than a desk with the whole shelf dumped on it, even if the shelf technically fits.

The same source lists techniques for keeping the context lean:

  • Clear old tool results. Once the model has used the calendar result, the raw result can be dropped from the history. This is the lightest-touch option.
  • Compaction: near the limit, ask the model to summarize the conversation so far, then start a new context from that summary. You lose detail, so decide first what the summary must keep, such as the student's decisions and unresolved questions.
  • Sub-agents: a separate helper works with its own clean context and hands back only a short summary. You will meet this in a later lesson on multi-agent systems; for a makerspace assistant it is usually not needed yet.
Compaction is lossy: a summary can drop a detail that matters later, such as "the student is not trained on the CNC router". That is one reason to write important facts to a file or database instead of relying on a summary.

What is kept between sessions: notes 5 min

A session here is one conversation, from the student's first message to the end. When the next session starts, the context starts empty again: the system prompt, the tools and the new question, and nothing from last week. The model has no way to know that Sam completed laser-cutter training on Tuesday.

So anything that must survive has to be saved outside the context, by your program, and loaded back when needed. Anthropic calls one version of this structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window and reads them back later (Anthropic, Effective context engineering for AI agents).

For the makerspace assistant, two kinds of saved information look alike but behave differently:

Training status"Sam prefers morning slots"
Must be exactly right?Yes: it gates safetyNo: it is a convenience
Best placeA database, read by a tool such as check_training_recordA short note the assistant writes and reads
Who writes itYour program or staff, not the model's guessThe model, via a save_note tool

The rule of thumb: facts that must be correct belong in a system of record that your code controls; soft context that merely helps belongs in notes. Either way the model gets it the same way, through a tool call whose result enters the context.

A common mix-up

"A large context window is memory." A large window lets one conversation hold more, but it is emptied when the session ends, and re-filling it costs tokens every time. Memory across sessions needs storage outside the window. Last week's chat does not exist for the model unless your program saves it and loads it back.

Retrieval: finding the right page 6 min

Notes cover what the assistant learns. The manuals are different: they are long, they already exist, and any one question needs only a page or two. Retrieval means fetching just the relevant pieces from a larger store into the context, at the moment they are needed. When the pieces come from a document collection and are placed in the prompt, the pattern is called retrieval-augmented generation, or RAG.

First, a question you should ask before building any of it: do you need it? Anthropic's advice is that if your knowledge base is under about 200,000 tokens (roughly 500 pages), you can simply put the whole thing in the prompt, and prompt caching makes that faster and cheaper; retrieval becomes the more scalable option as the base grows (Anthropic, Contextual Retrieval). Count your manuals before you build search. Remember, though, from earlier in this lesson that a full context is also re-sent on every call and is subject to context rot, so "fits" is not the same as "cheap".

If the manuals are too big, the usual pipeline is:

  1. Chunking: split each manual into pieces, typically a few hundred tokens each.
  2. Embeddings: an embedding model turns each chunk into a list of numbers that captures its meaning, and these are stored in a searchable database. A question is turned into numbers the same way, and the nearest chunks are the closest in meaning.
  3. BM25: an older keyword method that finds exact words and phrases. It helps with things such as error codes or a model number like "E-204", which meaning-based search can miss.
  4. Merge both lists of results, take the top few chunks, and put them in the context (Anthropic, Contextual Retrieval).

Retrieval fails in a typical way, and you can plan for it. Chunking can strip out what makes a chunk interpretable. Anthropic's example is a chunk reading "The company's revenue grew by 3% over the previous quarter", which names neither the company nor the quarter. A makerspace version: a chunk saying "Set the speed to 40% and power to 70%" does not say which machine or which material. Their fix, contextual retrieval, prepends a short note saying what the chunk is about to each chunk before indexing; they report that this, together with the keyword method, cut retrieval failures by 49% in their tests, and by 67% with reranking (Anthropic, Contextual Retrieval). Treat those figures as their results, not as a promise for your manuals.

Retrieval can also be done by the agent itself. Rather than loading everything up front, the agent keeps lightweight references, such as file names or saved queries, and loads data with tools when it needs it. The same source notes this "just-in-time" approach is slower than pre-loading and needs good guidance (Anthropic, Effective context engineering for AI agents). Your search_manuals tool is exactly this: the model asks, the program retrieves, and only the excerpt enters the context.

Worked example and practice 7 min

The skill for your design review is placing each piece of information in one of three places: context (this session, re-sent every call), stored notes or database (survives sessions, fetched by a tool) or retrieval (a big store searched for a small piece). Three questions decide it: Is it needed on every call? Must it outlive the session? Is the source too big to hold?

Worked example

Place these three items for the makerspace assistant: (a) "Never book a machine without confirming the time with the student"; (b) the laser cutter's 60-page manual; (c) whether Sam has completed laser-cutter training.

  1. (a), the booking rule. Needed on every call? Yes. Must outlive the session? It is fixed by you, so it is simply written into the system prompt each time. Place: context (system prompt). It is short, so re-sending it is cheap.
  2. (b), the manual. Needed on every call? No: most questions are not about the laser cutter. Too big to hold? Across all machines, probably. Place: retrieval, through search_manuals, so only the relevant excerpt enters the context. If all your manuals together are under about 200,000 tokens, you could instead send them whole, and weigh cost against simplicity.
  3. (c), Sam's training. Must outlive the session? Yes. Must be exactly right? Yes, it gates safety. Place: a database that check_training_record reads when a booking needs it, not a note the model wrote from memory.
Your turn

Place these three items, using the three questions: (d) Sam usually asks for afternoon slots; (e) the calendar result the assistant fetched five minutes ago, now that the booking is made; (f) the exact list of materials that are banned on the laser cutter. Start with (d): it must outlive the session, but it does not need to be exactly right. Decide where it belongs, then work out (e) and (f).

Show a solution

(d) Stored notes: a short preference note the assistant writes with a save_note tool and reads at the start of the next session. A wrong note costs little, so a note is fine.

(e) Context, then drop it. It was needed for this session, so it sits in the history for a few calls, but once the booking is done the raw result can be cleared, because it is stale tomorrow and it costs tokens on every later call.

(f) It depends on size and how often it is needed. A banned-materials list is short and safety-relevant, so a strong choice is the system prompt, where it is present on every call. If it grew to many pages, it would move to retrieval, with a rule in the system prompt that the assistant must search it before approving any material.

Cost check

Redo the table from earlier, but now search_manuals returns a 600-token excerpt instead of 2,000 tokens. The other numbers are unchanged. What is the total input over the four calls?

Show a solution

Call 1: 1,550. Call 2: 1,550 + 50 + 300 = 1,900. Call 3: 1,900 + 50 + 600 = 2,550. Call 4: 2,550 + 50 + 100 = 2,700. Total: 1,550 + 1,900 + 2,550 + 2,700 = 8,700 input tokens, against 11,500 before. A smaller tool result is saved on every call after it, not once.

Summary 3 min

  • The context is the text the model sees on one call; the context window is its maximum size. Nothing outside it can be used.
  • Between steps, the model keeps nothing. The program re-sends the full message history each call, so cost grows with the history, and too much context can also hurt recall.
  • Between sessions, nothing survives unless saved outside the context: a database for facts that must be right, notes for soft preferences.
  • Retrieval fetches only the relevant piece of a large store into the context. Skip it if the whole knowledge base is small enough to include.
