Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a searchable manual, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Every one of those choices is a context-and-memory choice, and you will have to defend them at your design review.

Warm-up 2 min

Two questions about the agent loop, from memory, before anything new.

Recall

A student asks, “Is the laser cutter free on Friday?” Name the steps of the loop, in order, until the student sees an answer. Who runs the tool: the model or the program around it?

Check your answer

The model is called and asks for check_calendar; the program runs it; the result goes back to the model; the model is called again and writes the answer. The program runs the tool, and every step is a separate model call. That second fact is the key to today: if every step is a separate call, what does the model know at each call?

The context window 5 min

Start with an example. You open a new chat and type: “My name is Riley and I'm training on the laser cutter.” The model answers. You type: “What was my name?” and it says “Riley.” It looks like it remembered. It did not. Your program sent both messages, plus its own earlier reply, in the second call.

The general idea: the context is the set of tokens given to the model when it writes a response (Anthropic, context engineering). A token is a small piece of text, a word or part of a word. The context window is the limit on how many tokens the model can work with in one call, including the response it writes. The docs call it the model's “working memory”, and say it is different from the large body of text the model was trained on (Claude docs, context windows).

What counts toward the window? Everything in the request: the system prompt, every message including tool results, and the tool definitions you wrote. The response counts too (Claude docs).

Check yourself

Your assistant's tool definitions take 800 tokens. Do they count toward the context window?

Show the answer

Yes: the system prompt, messages, tool results and tool definitions all count, so 800 tokens of definitions are used on every call.

What is kept between steps 5 min

Take the request: “Is the laser cutter free tomorrow at 3 pm, and do I need training?” The loop makes three calls. Here is what the model receives at each call (token counts are made up to show the pattern):

CallContext sentTokens
1system prompt, tool definitions, question1,500
2everything in call 1, plus the model's calendar request and the calendar result1,800
3everything in call 2, plus the model's manual search request and a manual page4,300

The pattern: the model keeps nothing between calls. Your program keeps the history and sends it again each time. Each turn's input is all earlier history plus the new message, and each output becomes part of the next input (Claude docs). In code, this history is the list of messages your Python program appends to after each step. Your while loop from the loop lesson is the memory.

A common mix-up

“The model remembers what happened earlier in the loop.” It is tempting because the answer in call 3 clearly uses the calendar result from call 2. But it can only do that because your program put the result in the context again. If your code forgot to append a tool result, the model would have no idea it ever asked.

Why more context costs more and works worse 4 min

Two reasons to be careful, and the second is the surprising one.

Cost. History is billed as input each time it is sent. The docs state that on models that keep earlier thinking, those kept blocks “are billed as input tokens, like the rest of the conversation history” (Claude docs). In Figure 2, call 1's 1,500 tokens are paid for three times. Add a ten-page manual excerpt at call 3 and every later call pays for it again. A small budget means small, deliberate contexts. (Prompt caching can lower the price of repeated tokens, but cached tokens still occupy the window.)

Quality. More context is not automatically better. As token count grows, accuracy and recall degrade, a phenomenon called context rot (Claude docs). Anthropic describes context as a finite resource with diminishing returns, like an “attention budget” that each new token draws down, and states the goal as the smallest set of high-signal tokens that gets the result (Anthropic, context engineering).

A common mix-up

“Pick a model with a huge window and paste in all the manuals.” Tempting, because it removes the need to design anything. But you pay for every token on every call, and recall gets worse as the context fills. A bigger window is room, not a reason to fill it.

Check yourself

Your agent works for 30 steps, and the manual excerpts from steps 2 to 20 are no longer needed. What is the best fix?

Show the answer

Drop or summarize the old results in your program. The model only sees what you send, so removing tokens is the only way to stop paying for them.

When a conversation nears the limit, the standard move is compaction: summarize the history and continue with the summary. Anthropic's example keeps decisions and unresolved problems and discards redundant tool output, and calls clearing old tool results a safe, light first step (Anthropic, context engineering).

Between sessions: nothing, unless you save it 4 min

A session here means one conversation, from the student's first message to the end. Suppose a student finishes laser-cutter training on Monday and returns on Thursday. The Thursday conversation starts with an empty history. The model has not been told about Monday, and it cannot look it up on its own.

So a session's context is gone when the session ends, and anything that must survive has to be saved outside the context by your program and loaded back in at the start of the next session. That saved store is what we call memory. For the makerspace assistant:

InformationLives whereWhy
This conversation's messagesContext (history list)Needed on every call, thrown away after
Student's training statusSaved record (a file or database row)Must survive between visits, and a fact must not be “remembered” wrongly
Laser cutter manualSearchable storeFar too long to send each time; only a page or two is needed
A common mix-up

“A chat app remembers me, so the model does.” Some chat products add saved memories or manage history for you, but that is software around the model doing what this table shows. Your assistant has none of it unless you build it.

Retrieval: finding the right page 5 min

A laser cutter manual might be 120 pages. Sending all of it on every call is costly and, because of context rot, can make answers worse. Instead, the program retrieves a few relevant pages and puts only those in the context. Retrieval means searching a store for the pieces most relevant to a question and adding them to the context.

The common setup: split each manual into chunks (a few paragraphs each), then search the chunks. Two ways to search, and they work well together:

  • Keyword search (such as BM25) finds chunks that share exact words with the question. It is good at exact names, like “Model X-200 lens”.
  • Embedding search turns each chunk into a list of numbers that captures its meaning, so “the cutter smells like smoke” can match a chunk about ventilation faults that never uses the word “smoke”.

Chunking has a known weakness: a chunk that says “Replace it every 200 hours” has lost what “it” is. Anthropic's contextual retrieval adds a short, chunk-specific explanation to each chunk before indexing, and reports that combining it with both search types cut failed retrievals, measured on top-20 results, by about half (Anthropic, contextual retrieval). You do not need that on day one; the lesson is that how you cut up the manual matters.

There are two ways to wire retrieval into an agent, and the difference matters for your design:

Retrieve up frontRetrieve when needed (just in time)
HowProgram searches before the model's first call and adds the resultsModel calls a search_manuals tool when it decides it needs a page
Good forPredictable questions, one fast callVaried questions; the model can search again with a better query
CostPages are added even if not neededExtra model calls, but only needed pages enter the context

Anthropic describes both and often recommends a hybrid: some information loaded up front, the rest fetched on demand (Anthropic, context engineering). Notice that search_manuals, from your quiz on the agent loop, is exactly this idea: retrieval as a tool.

Check yourself

A student writes: “The cutter smells like smoke.” The right manual chunk is titled “Exhaust fan and ventilation faults” and never says “smoke”. Which search is most likely to find it?

Show the answer

Embedding search, because it compares meaning rather than exact words. Keyword search would catch exact part names, which is why the two are often combined.

Notes as memory 4 min

Retrieval is for material that already exists, such as manuals. Notes are for what the agent learns while working: the agent writes short facts to storage outside the context and reads them back later. Anthropic calls this structured note-taking, or agentic memory, with examples such as a to-do list or a NOTES.md file. In its example, an agent resumed a long task after its context was reset by reading its own notes (Anthropic, context engineering). The docs also advise that agents spanning several sessions keep state artifacts designed so a new session can recover quickly (Claude docs).

For the makerspace assistant, a note might be: {"student": "riley", "laser_cutter_training": "done", "date": "2026-11-09"}. At the start of Thursday's session your program loads that record into the context, in a few tokens, instead of replaying all of Monday's conversation.

def start_session(student_id):
    record = load_record(student_id)      # saved outside the context
    system = BASE_PROMPT + "\nStudent record: " + json.dumps(record)
    return [{"role": "system", "content": system}]

def end_session(student_id, new_facts):
    save_record(student_id, new_facts)    # only facts worth keeping
This is a sketch of the idea, not a specific library's API: your team picks the storage and message format later.

Two design rules follow. First, save facts, not transcripts: a transcript of Monday costs tokens to reload and contains little you need. Second, decide who writes the note. If the model can write notes, it can write wrong ones; for something like training status, which gates access to machines, the trusted booking or training system should be the source of truth and the assistant should look it up with a tool.

A common mix-up

“Memory means keeping the whole conversation.” Keeping it all grows the cost and triggers context rot. Useful memory is selective: a few facts, saved on purpose, loaded when relevant.

Worked example and practice 5 min

Worked example

A student says: “I'm back. Can I book the 3D printer Saturday? Last time you told me the filament rule, but I forget it.” Decide what goes where.

  1. List what the answer needs: (a) is this student trained on the 3D printer, (b) is Saturday free, (c) the filament rule, (d) what was said last time.
  2. (a) Training status: a fact that survives between visits and gates access. Look it up from the saved record or training system at the start of the session. Not from the model's memory, which has none.
  3. (b) Saturday's calendar: changes constantly, so it is never saved. Fetch it with check_calendar and keep only the relevant rows in context for this session.
  4. (c) The filament rule: lives in the manual. Retrieve the matching chunk with search_manuals rather than loading the whole manual.
  5. (d) What was said last time: the old transcript is not needed. The student is asking for the rule again, and (c) provides it. Do not reload the transcript.
  6. Result: the context holds the system prompt, tool definitions, a one-line student record, calendar rows and one manual chunk, a small, focused context.
Your turn

A student says: “Can I use the soldering station without supervision? I think I did the safety quiz last month, and the station's hot-air tool settings are in the manual.” Sort each item into saved record, retrieved from manual, tool call for live data or not needed: (1) whether the student passed the safety quiz, (2) the hot-air tool settings, (3) whether the station is free right now, (4) the full text of last month's chat. Start with item 1: it must survive between visits and gates access.

Show a solution

(1) Saved record, looked up from the training system, because it must survive between sessions and the student's “I think” is not good enough. (2) Retrieved from the manual: stable text, too long to load whole. (3) Tool call for live data: it changes by the minute, so save nothing. (4) Not needed: if a fact from that chat mattered, it should already be a saved fact.

Summary 2 min

  • The context window holds everything the model sees in one call: prompt, tool definitions, history, tool results and its own response.
  • The model keeps nothing between calls: your program resends the history, so context grows each step, and cost and context rot grow with it.
  • Nothing survives between sessions unless your program saves it and loads it back.
  • Retrieval brings only the right chunks of a long document into context; notes save the few facts worth keeping.

Say it in your own words: without looking, explain to a teammate why the assistant can recall Monday's training on Thursday, and where that fact is stored.
