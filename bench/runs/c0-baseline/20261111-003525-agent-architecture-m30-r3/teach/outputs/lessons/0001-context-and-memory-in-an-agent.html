Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a searchable store, and say why.

Objective O3: context, memory and retrieval in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Every one of those three demands is a context-and-memory decision, and it is the kind of decision your design review will ask you to defend.

Warm-up 2 min

Before new material, pull something from memory. This is the loop you already know.

Recall

The model has just asked for check_calendar("laser cutter", "Friday"). Without looking back: who actually runs that tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. The program then sends the result back to the model and calls it again, so the model can pick its next step or write its answer. That last part matters today: "sends the result back" means the result becomes part of what the model reads next. What the model reads is its context.

The context window: what the model sees 6 min

Start with a concrete case. A student types: "Can I use the laser cutter on Friday afternoon?" Your program does not send just that sentence to the model. It sends a bundle: the assistant's instructions ("You help students at the university makerspace..."), descriptions of the three tools, and then the student's question.

Everything the model is given in one call, plus what it writes back, is the context window. The Claude docs describe it as all the text a language model can reference when generating a response, "including the response itself", and compare it to a working memory (Claude docs: Context windows). It is different from the model's training: training is what the model learned long ago and cannot be edited by you. The context window is what you put in front of it right now.

The window is measured in tokens: small pieces of text, often a short word or part of a word. A plain English word is usually one to two tokens. The window has a maximum size. For many current Claude models it is up to 1 million tokens, but the docs list others at 200 thousand, so check the model you pick (Claude docs).

Per the same docs, all of these count toward the window:

  • the system prompt (the standing instructions);
  • the tool definitions, meaning the descriptions you wrote;
  • every message so far, including tool results, documents and images;
  • the model's own output for this turn.

Two facts follow, and both matter for your budget. First, the model can only use what is inside the window; the machine manuals sitting on your server do not exist for it until you put some of their text in. Second, you pay for tokens, and the input to each call is the whole window, so a bigger window means a bigger bill for that call.

Prompt caching can lower the price of a prefix you send repeatedly, but the docs are clear that cached tokens "still occupy the context window": caching changes what you pay, not what is in the window.

The third option. The model works only from its window. A file on disk is invisible until your program (or a tool the model calls) reads it and puts the text into the window.

Between steps: everything is resent 6 min

Now the agent loop, seen through the window. Take the request "Is the laser cutter free Friday at 3 pm, and do I need training?" You traced this loop before. This time, count what the model reads each time it is called.

A model call does not remember the last one. Each call is a fresh request, and the program must send everything the model should know. So on every step the program resends the system prompt, the tool descriptions, the question, and all earlier tool requests and results, then adds the newest result at the end. The Claude docs describe this: each turn's input holds "all previous conversation history plus the current user message", and earlier turns are "preserved completely" (Claude docs).

Here are made-up but plausible sizes. The system prompt and tool descriptions together take 2,000 tokens, the question 50. The calendar tool returns 150 tokens. The manual search returns three passages of 1,500 tokens. The training lookup returns 100.

(For simplicity this ignores the model's own short tool requests, which add a few tokens each.)

Two consequences for your design. Cost: the manual passages are paid for again on call 4, and would be on every further call. Large tool results are the expensive part of an agent loop, so retrieve a few good passages, not many. Quality: Anthropic's engineers report that as the number of tokens in the window grows, the model's ability to recall information from it decreases, a problem they call context rot, and they describe context as a limited "attention budget" (Anthropic: Effective context engineering). More text is not automatically better, even when it fits.

A common mix-up

"With a window of a million tokens, I can paste in every manual and skip the clever parts." It is tempting because it removes work. But it fails twice. You would pay to process all of those tokens on every call of every request, and recall gets worse as the window fills. The docs say the same: "more context isn't automatically better", so curating what is in the window matters as much as how much space there is (Claude docs). Use a big window as headroom, not as a plan.

Check yourself

A request takes five model calls. The window holds 3,000 tokens before any tool runs, and each of the first four tool results adds 500 tokens. Roughly how many input tokens are processed across the five calls, ignoring the model's own text?

Show the answer

3,000 + 3,500 + 4,000 + 4,500 + 5,000 = 20,000. The loop's cost grows faster than the number of steps, which is why a step limit and small tool results both protect your budget.

Between sessions: nothing is kept unless you keep it 4 min

Suppose a student, Dana, finishes the laser cutter safety training on Monday and tells the assistant so. She returns on Thursday and asks to book the machine. A new conversation starts, with a new, nearly empty window. The model has no link to Monday's window. A session here means one conversation, from the first message until your program starts a fresh one. When it ends, its window is gone.

So the model does not know Dana trained on Monday. Nothing in the model changed: it learned nothing from that chat. If the assistant is to know, your program must save the fact somewhere outside the model and put it back into the new window. That saved fact is memory in the sense that matters for agents: information stored outside the context window, loaded in when needed.

A common mix-up

"The assistant remembers its past chats, because it is smart." It is tempting because chat apps do seem to remember you. When they do, it is because the app stores things and feeds them back into the window. The model itself starts every call blank, apart from what is sent. Your makerspace assistant remembers a student only if you build that.

Retrieval: finding the right page in a long manual 6 min

The manuals are too long to place in every window, and you now know why. The answer is retrieval: search the manuals for the few passages that fit the question, and put only those into the window. Systems that retrieve text and give it to the model are often called RAG, short for retrieval-augmented generation.

A concrete example. A student asks, "What speed should I use to cut 3 mm acrylic?" The program (or a search tool the model calls) does this:

  1. Prepare once: split each manual into chunks, short passages of a few hundred tokens, and build an index over them.
  2. Search: find the chunks that best match the question.
  3. Insert: put the top few chunks into the window as a tool result, so the model can answer from them and name its source.

Step 2 can work in two ways, and good systems use both. Keyword search (such as BM25) matches exact words, so it finds "3 mm" and a part number. Embedding search turns each chunk into a list of numbers that captures its meaning, so it finds the "acrylic speed table" even if the student wrote "plexiglass". Anthropic's tests found that combining the two beat either alone (Anthropic: Contextual Retrieval).

Retrieval can fail quietly. When you split a manual, a chunk can lose what it is about. A chunk reading "Set the speed to 40 and power to 60" does not say which machine or material it describes. Anthropic's fix, contextual retrieval, has a model add a short note to each chunk before indexing it, such as "From the laser cutter manual, acrylic section". They report that this, plus combining embeddings and keywords, cut failed retrievals by about 49%, and by about 67% with a further reranking step (Anthropic). Those are Anthropic's own measurements on their test sets, so treat them as an indication, not a promise for your manuals. You can get part of the same gain cheaply by storing the machine name and section title with each chunk.

Retrieve up front, or let the model fetch

There are two timings. Up-front retrieval searches before the model is called and hands over the chunks. Just-in-time retrieval gives the model a search tool and lets it decide when to look and what to search for. Anthropic describes agents that keep light references (file paths, saved queries, links) and load the actual data at runtime with tools. It notes the cost: runtime exploration is slower than having the data ready, and it needs well-designed tools (Anthropic: Effective context engineering).

For your assistant, a search tool the model calls fits well, because many questions (a booking) need no manual at all, and you do not want to pay for passages on those.

Notes: memory you write yourself 4 min

Retrieval brings in text that already exists. Notes are the other direction: the agent writes something down, outside the window, and reads it back later. Anthropic calls this structured note-taking, or agentic memory, and gives the example of Claude playing a game over thousands of steps, keeping notes on what it has explored and its strategies, and reading its own notes after a context reset to continue (Anthropic: Effective context engineering). The Claude platform even offers a memory tool for storing and reading files like this.

For the makerspace, a notes file per student could hold lines like "Prefers afternoon slots" and "Asked about acrylic settings twice". At the start of a session, the program loads that short file into the window. At the end, the model (or the program) adds anything worth keeping. Two rules make notes work:

  • Keep them short and curated. Notes are loaded into every future window, so a growing pile has the same cost and rot problems as the window itself.
  • Keep facts that must be right in a database. Training status gates safety, so it should come from the real record via a tool, never from a note the model wrote from memory.

When one session gets too long: compaction

A single long session can fill its own window. Compaction means summarising the conversation so far and starting a fresh window with that summary. Anthropic's advice is to keep decisions, open problems and key details, and to drop old raw tool outputs (Anthropic). The platform also has server-side compaction. A makerspace chat rarely gets that long, so for you it is a safety net, not a first priority.

Worked example and practice 5 min

Worked example

For the fact "the soldering station's tip must be cleaned before each use", decide where it lives.

  1. Ask how big and how often needed. It is one line in a long manual, and only needed when a student asks about soldering. Putting it in every window would cost tokens on every call for nothing.
  2. Ask whether it already exists as text. Yes, it is in the manual. So it is not a note; nobody has to write it down.
  3. Choose retrieval. Chunk the soldering manual, tag the chunks with the machine name, and let the search tool fetch it when a soldering question comes up.
  4. Check the exception. Is it safety-critical and must be exact? A cleaning rule is safe to quote with a source. If the manual said "never leave the iron on unattended," you would still cite the page, so the student can verify.

First step, given: for each, ask whether it must be exact and current, whether it already exists as text, and how often it is needed. Do the rest yourself, then check.

Show a solution

(a) A short note in Dana's notes file: it was learned in use, it is small, and it helps next time. (b) The booking database, read through check_calendar: it must be exact and current, so never a note, and never a number the model recalls. (c) Retrieval from the manual: it exists already, it is large, and it is needed only for some questions. (d) The context window, as part of this session's history: it is needed right now and nowhere else.

Summary 2 min

  • The context window is everything the model is given in one call, and the model can only use what is in it. The window is also the bill: you pay for it on every call.
  • Between steps, the program resends the whole window plus the newest result, so cost grows with every step and large tool results are expensive. Bigger windows are headroom, not a design.
  • Between sessions, nothing is kept unless your program saves it and loads it back. The model itself learns nothing from a chat.
  • Retrieval puts a few matching passages into the window; notes carry small facts across sessions; databases hold what must be exact.
