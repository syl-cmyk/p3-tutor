Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note between sessions, or behind a search tool.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status from one visit to the next. Both are memory problems. Your sponsor's budget also pays for every token the model reads, so what you keep in context is a design decision you will have to defend at the review.

Warm-up 2 min

Recall

From the agent loop: after the program runs a tool the model asked for, what does it do with the result, and how many times is the model called for a request that needs two tool calls and then a final answer? Answer in your head or on paper first.

Check your answer

The program sends the result back to the model as part of its next input, then calls the model again. Two tool calls plus the final answer is three model calls. Today's question is what, exactly, that "next input" contains.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free on Friday, and what settings do I use for 3 mm acrylic?" Your assistant answers in a few steps. At the very first step, what does the model actually receive?

Not just the question. It receives the assistant's instructions (the system prompt), the definitions of every tool, and the student's message. All of that is text, and the model reads all of it before it writes a single word.

The context window is all the text a model can reference when it generates a response, including the response itself. The Claude documentation calls it the model's "working memory", and distinguishes it from the large body of data the model was trained on (Claude docs: Context windows). It has a fixed size, measured in tokens, the small chunks of text the model reads and writes (a token is often a short word or part of a word).

The documentation lists what counts toward the window: the system prompt, every message including tool results, your tool definitions, and the output the model generates for the turn. If it is in the request, it takes space.

Sizes differ by model. Current Claude models listed in the docs have windows up to 1M tokens, and others 200k. Check the model you pick; the design lesson below holds either way.
Check yourself

The assistant's system prompt is 800 tokens and its three tool definitions are 600 tokens. The student's question is 40 tokens. How much of the context window is already used before the model writes anything?

Show the answer

1,440 tokens. The system prompt, the tool definitions and the question all count toward the window, as the docs list.

What is kept between steps 5 min

Here is the idea that surprises most people. The model itself keeps nothing between calls. When the loop goes around, your program builds the next input from scratch and sends it again. The "memory" inside a single request is the list of messages your program keeps and re-sends.

The Claude documentation describes this directly: each user message and model response accumulates in the context, previous turns are preserved completely, and each turn's input is all the previous history plus the new message (Context windows).

Follow the laser cutter question. The calendar tool returns a long list of bookings. The program appends that result to the messages. Next step, the model asks the manual-search tool for acrylic settings, which returns several long passages. The program appends those too. By the final answer, the model is re-reading the calendar dump, the passages, and its own earlier requests, on every single call.

Worked example: what a run costs

Invented numbers, to show the shape. Fixed part (system prompt and tools): 1,400 tokens. Question: 40. Calendar result: 1,500. Manual passages: 3,000. Model output at each step: about 100.

  1. Call 1 input: 1,400 + 40 = 1,440 tokens.
  2. Call 2 input: call 1's input + the model's request (100) + the calendar result (1,500) = 3,040 tokens.
  3. Call 3 input: call 2's input + the model's request (100) + the manual passages (3,000) = 6,140 tokens.
  4. Total read across the three calls: 1,440 + 3,040 + 6,140 = 10,620 tokens, though the conversation's final length is only about 6,200 tokens.

The step costs grow because each call re-reads everything before it. Prompt caching can change what you pay for repeated input, but the docs are clear that cached tokens still occupy the window.

That is why cost per request, in your mission, is a context question. Every large tool result is paid for again on every later step of that request.

There is a second cost besides money: quality. The Anthropic engineering team describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases. Their conclusion is that context is "a finite resource with diminishing marginal returns" (Effective context engineering for AI agents). A bigger window is room, not a reason to fill it.

A common mix-up

"If the window is huge, I can paste in every manual and skip the design work." It is tempting because the window size is a big number. It is wrong for two reasons shown above: you pay for those tokens on every step, and recall gets worse as the window fills. The target is the smallest set of useful information, not the largest that fits.

Keeping context small 4 min

Because the contents only grow, your program has to decide what to remove. The sources describe a few standard moves.

MoveWhat it doesMakerspace example
Clear old tool resultsRemoves bulky results the model has already used.Drop the 1,500-token calendar dump once the answer "Friday 2 pm is free" is written down.
CompactionSummarizes a conversation nearing the limit and continues in a fresh window.A long chat with one student about a project gets summarized.
Return lessDesign tools to return only what is needed.check_calendar returns the free slots for one day, not the whole month.

The engineering post calls clearing old tool results one of the safest forms of compaction, because a result that was already used rarely needs to be seen again (Anthropic engineering). The Claude docs offer tool result clearing as a context editing option, and server-side compaction as the main strategy for long conversations (Context windows).

Compaction is lossy: a summary can drop a detail that matters later. That is the reason to save what must survive somewhere else, which is the next section.

For a makerspace assistant, most conversations are short, so the cheapest win is usually the third move: make tools return small, relevant results.

Between sessions: notes 6 min

Now the second memory problem. Riley finishes a chat on Monday about the laser cutter. On Thursday Riley opens a new chat. What does the assistant know about Monday?

Nothing, by default. A session here means one conversation: one list of messages. When it ends, the list is gone, and a new session starts with an empty list. The model does not carry anything over. Memory across sessions is not automatic; you build it.

The pattern in the sources is structured note-taking: the agent regularly writes notes to storage outside the context window, and reads them back later. The engineering post describes it as persisting notes to memory outside the context window (Anthropic engineering).

Anthropic's memory tool is one concrete version. It lets the model create, read, update and delete files in a /memories directory that persist between sessions. The important detail for design: the tool is client-side. The model only requests a file operation, and your application runs it against storage you control, returning the result as a tool result (Claude docs: Memory tool). It is the same loop you already know: the model asks, the program acts.

Notes have a cost too: a note the model reads goes into the context, so it takes space like anything else. Keep them short and organized. The docs suggest that you cap file sizes and delete notes that have not been used in a long time, and that the model should keep its memory "up-to-date, coherent and organized".

For your assistant, the natural note is a student's training status: which machines they are signed off on, and when. Two design questions follow, and they are yours to answer for the review. Who is allowed to write that note (the model, or only a staff-controlled system)? And should a safety-critical fact like "certified on the laser cutter" live in free-form notes at all, or in a database that a fixed tool reads?

A staff-controlled record is the safer home for facts that must be right, such as certifications. Model-written notes suit softer facts, like a student's usual project type. This is my design suggestion, not a rule from the sources.
A common mix-up

"The assistant will remember a returning student automatically, because it is a smart model." It is tempting because chat products do seem to remember. But in your own program, a new session starts empty unless you saved something and load it. Whatever remembers is code and storage you design.

Retrieval: finding the right page 4 min

Third problem: the manuals. The laser cutter manual may run to hundreds of pages. Putting it all in context fails on both cost and recall, as you saw in section 2.

Retrieval means fetching only the relevant pieces from a larger store, at the moment they are needed. The engineering post calls this the "just in time" approach: the agent keeps lightweight references, such as file paths or stored queries, and loads data into context only when needed (Anthropic engineering). The memory tool doc uses the same idea for notes: record what is learned, and read it back on demand rather than loading everything up front.

In your assistant this is a tool. Say search_manuals(machine, query) returns the three best-matching passages, each with its page number. The model asks for "3 mm acrylic power speed", gets three short passages, and answers. The 300 pages stay on disk.

Worked example and practice 4 min

Worked example

Sort three facts for a different assistant, a library helper: (a) "Be polite and concise," (b) a patron's preferred language, (c) the 200-page lending policy.

  1. Ask: is it needed on every single call? "Be polite and concise" is, so it goes in the system prompt.
  2. Ask: does it need to survive past this conversation, and is it small? The preferred language does, and it is a few words, so it goes in saved notes, read at session start.
  3. Ask: is it large and only occasionally relevant? The lending policy is, so it goes behind a search tool and enters context only as passages.
Your turn

Sort these makerspace facts into system prompt, saved notes or database, or search tool: (a) "Never book a machine for a student who is not trained on it." (b) Which machines Dana is trained on. (c) The 3D printer troubleshooting guide, 80 pages. (d) The results of today's calendar lookup for the laser cutter. For (d), say what you would do with it once the booking is made. Step 1 is done for you: (a) is needed on every call, so it goes in the system prompt.

Show a solution

(a) System prompt, as given. (b) Saved notes or, better for a safety fact, a database the program reads at session start, since it must outlive the conversation. (c) Search tool: large and only sometimes relevant. (d) Neither: it is working data for this conversation only. Keep it while it is needed, then clear it from the context once the booking is made, so later steps do not pay for it again.

Summary 2 min

  • The context window is all the text the model sees in a call, including instructions, tool definitions, messages, tool results and its own output. It has a fixed size.
  • Between steps, your program re-sends the whole message list. It only grows unless you clear or summarize, and you pay for it again each step, while recall degrades as it fills.
  • Between sessions, nothing is kept by default. Notes saved outside the context, such as with a memory tool your program runs, are how an agent remembers.
  • Retrieval keeps large stores, like manuals, outside the context and brings in only the matching passages when needed.

Say it in your own words: without looking, explain to a teammate why the assistant should search the manuals instead of loading them, and where a student's training status should live.
