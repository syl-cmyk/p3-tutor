Lesson 1 · 30 minutes

Context management: what an agent sees, keeps and looks up

An agent's context is the text the model gets on each call, and its memory is whatever is saved outside that text so it can be loaded again. By the end of this lesson you can say, for any agent, what the model sees on each call, what is carried from step to step, and what must be saved outside the window (as notes or as a searchable store) to last between sessions.

Objective O3: what an agent keeps in context, saves and looks up About 30 minutes Builds on the agent loop (your earlier session)
Why this matters for you

The makerspace assistant answers from long machine manuals, and it has to remember each student's training status between visits. Both jobs come down to one decision: what the model sees right now, what it keeps, and what it looks up.

That decision is also your cost lever, because the small budget your sponsor gave you is spent per token sent. You'll be defending it at your design review.

Check your answer

The program. The model only writes a request like "run check_calendar for Friday", your code runs it, and the result goes back to the model as text. Hold on to that, because it decides where memory lives later in this lesson.

Recall 2

Why can a chatbot state an outdated fact with confidence?

Check your answer

All it has is what it learned in training, which stopped at some date, plus whatever text it is handed on this call. Today's lesson is about that second part: the text it is handed, and how you choose it.

Part 1: Context window: all the text the model can see on one call 5 min

The model knows only what is in the text you send it on this call, so you are the one choosing what it gets to see. That is why we start with what that text is and how it is measured.

Start with a real request. A student types: "Is the laser cutter free Friday?" These are round numbers I made up, so the arithmetic is easy. Here is everything your program sends to the model on call 1.

Worked example: the full text of call 1
  1. System prompt, 800 tokens. The assistant's standing instructions: "You are the makerspace assistant. Be brief. Never book a machine for a student who isn't trained."
  2. Tool definitions, 600 tokens. The list of tools it may use, each with a short description, such as check_calendar and search_manual.
  3. User message, 40 tokens. The student's question: "Is the laser cutter free Friday?"
  4. Total: 1,440 tokens in. That's the whole input. The model has nothing else to go on.

Now the words for what you just saw. A token is a small chunk of text, often a word or a piece of a word. It's the unit the model reads and writes in, and it's also the unit that the limit and the bill are counted in.

The context window is all the text the model can reference when it generates a reply, and that includes the reply it is writing (context windows doc). Everything counts: the system prompt, the messages, the tool results, the tool definitions and the output. Depending on the model, windows go up to 1M tokens (same doc).

Think of the window as the model's working memory. It's separate from training: training is fixed, and the window is whatever you put on the desk for this one call.

Here's call 1 as a trace, so you can see where each piece goes.

  1. The student sends "Is the laser cutter free Friday?".
  2. Your program glues together the system prompt (800), the tool list (600) and the question (40): 1,440 tokens.
  3. The model reads all 1,440 and starts writing a reply, say a request to run check_calendar.
  4. That reply counts toward the window too, so the room left shrinks as the model writes.
  5. When the call ends, the model keeps nothing. The next call starts from whatever text your program sends next.

One more way to see it. A second student asks the very same question a minute later. The model doesn't know the first student ever asked, because that text isn't in this call, and so it treats both questions as brand new.

A common mix-up

"The model remembers what it learned from earlier chats." It's tempting because chatbots feel like they know you. Test it: an hour ago a student told the assistant her name. If you send the same question in a fresh call with no history, the model has no idea who she is. Training is fixed; only the text you send changes.

A common mix-up

"The context window is how much the model knows." No, it's the size of the desk, not the library. A 1M-token window still holds nothing that this call doesn't contain, and if the laser cutter's limits aren't in the text you sent, the model can't read them.

Check yourself

Which statement about what counts toward the window on one call is right?

Show the answer

The second option. The system prompt, the tool definitions, any tool result and the reply all sit in the window, and all are counted in tokens.

Recap: the window is one call's worth of text. You build it, the model reads it, and then it's gone. Next, what happens when one request needs several calls.

Part 2: Message history: what carries from one step to the next 5 min

Every step of the loop is a fresh call, and the only thing that links the steps is the history your program sends again each time. So the window fills a little more with every step, and so does the bill.

Let's follow one longer question through three calls: "Is the laser cutter free Friday, and what is the thickest acrylic I can cut?" To keep the arithmetic easy, pretend the question still weighs 40 tokens, so call 1 is the same 1,440 tokens as before. (More round numbers I made up.)

Worked example: three calls, with the running total
  1. Call 1 sends 1,440 tokens. The model replies with a request to run check_calendar, 60 tokens.
  2. The program, not the model, runs the calendar check. The result is 160 tokens of text.
  3. Call 2 sends 1,440 + 60 + 160 = 1,660 tokens. The model replies with a request to run search_manual, 50 tokens.
  4. The program runs the search and gets back a manual page: 1,500 tokens.
  5. Call 3 sends 1,660 + 50 + 1,500 = 3,210 tokens. The model writes its final reply, 120 tokens, and the loop stops.
  6. Total input sent across the three calls: 1,440 + 1,660 + 3,210 = 6,310 tokens. Beyond the first call's 1,440, only about 1,800 tokens of new content were added along the way, but the big manual page is sent again at every later step.

Here's why. Each model call is separate: the model doesn't wait around between steps with the conversation in its head. The history is just a list your program keeps, and it resends the whole list on each call. Previous turns are preserved completely, and each output becomes input of the next turn (context windows doc).

In Python you've already seen the shape of it. The list is the memory of the conversation, and your code is the only thing that grows it.

history = [student_question]
while True:
    reply = call_model(history)        # a separate call every time
    history.append(reply)              # what the model just said
    if reply_is_final_answer(reply):
        break
    result = run_tool(reply)           # your program runs the tool
    history.append(result)             # forget this line and the model never sees it

This is the bill link. Cost per request follows the tokens sent, so a long history costs more with every step. One side note: caching can change what you pay for repeated text, but it doesn't change whether that text counts toward the window (context windows doc).

A common mix-up

"The model keeps the conversation going on its own between steps." It doesn't. Say your program forgets to append the calendar result in call 2: the model sees no answer, so it asks for the calendar again. The loop repeats, until it hits a step limit.

A common mix-up

"A tool result is only used once." It feels that way because the model used it for one decision. But the 1,500-token manual page is paid for in call 3, and again in every later call of the same conversation.

Your turn: a numeric check

A different student asks a question that weighs 55 tokens, so call 1 sends 800 + 600 + 55 = 1,455 tokens. The model replies with a 90-token request, the program gets back a 210-token result, and call 2 goes out. The model then replies with a 45-token request, the result is 400 tokens, and call 3 goes out. How many tokens does call 3 send?

Hint

Call 2 is call 1 plus the request plus its result. Call 3 is call 2 plus the next request plus its result. Add each call on top of the one before, not on top of 1,455.

Show the solution

Call 2 = 1,455 + 90 + 210 = 1,755. Call 3 = 1,755 + 45 + 400 = 2,200 tokens. If you also add all three calls, 1,455 + 1,755 + 2,200 = 5,410 tokens sent in total.

Recap: every step resends everything before it, so the window only grows. What do you do when it grows too far?

Part 3: Context rot and compaction: keeping the window small and useful 4 min

Fuller is not better: the more the window holds, the worse the model gets at using any one piece of it. So an agent has to trim as it goes, and what it trims, it loses.

Picture the same assistant 40 steps into a long booking chat for a group of students. The history has grown to 62,000 tokens (made up), and most of it is old manual pages it already used. Here are the three things you can do about it.

Worked example: a 62,000-token history
  1. Option 1, clear old tool results. Drop the old manual pages, and keep a short note in their place that says the call happened and can be run again. Nothing is lost for good, because the page can be re-fetched.
  2. Option 2, compaction. Have the model write a summary of the conversation so far, then start a new window from that summary.
  3. Option 3, do nothing. Pay for all 62,000 tokens on every later call, and watch the model get worse at finding the one fact it needs.

A good summary must keep the booking just made and the students' constraints (for example, "needs the laser cutter Friday, group of four"). A weak summary says "checked the manual for acrylic limits" and drops the actual page number and the limit. That is the cost of compaction: whatever the summary leaves out is gone.

Now the terms. Context rot means accuracy and recall degrade as the token count grows, so choosing what goes in matters as much as how much fits (context windows doc). The aim is the smallest set of high-signal tokens, because context is a finite resource with diminishing returns (Effective context engineering).

Compaction means summarizing a conversation that's nearing the limit and starting a new window from the summary (same article). Tool result clearing means dropping old results that can be fetched again, and leaving a short placeholder where each one was (context editing doc).

One more concrete case of clearing. At step 12 the assistant read a 3D printer page of 1,500 tokens. At step 40 that page is replaced by a one-line placeholder (my own wording here; the API sets the exact placeholder text): "[result of search_manual for 3D printer settings cleared; call it again to re-read]". The line costs maybe 30 tokens, and if a student asks about printers again, the assistant just looks it up.

So which option wins? Clearing is the safe one, because what it drops can be fetched again. Compaction is stronger but riskier, because the summary is all that's left. Doing nothing is the only one that's wrong every time.

A common mix-up

"A bigger window solves it: just paste everything in." It's tempting because 1M tokens sounds like room for anything. But accuracy and recall degrade as the count grows, and every call re-sends all of it, so a 62,000-token history costs about 62,000 input tokens on every later call.

A common mix-up

"Compaction keeps everything, just shorter." It keeps what the summary says, and nothing else. A summary of "checked manual for acrylic limits" has lost the actual limit. Anything you can't afford to lose goes in a note instead, which is Part 5.

Part 4: Retrieval: loading only the page you need 4 min

A manual is far too long to keep in the window, so the assistant keeps a way to find the right page and loads only that. This is how it answers from long manuals without paying for the whole manual on every call.

Say the makerspace has 120 manual pages at about 1,500 tokens each. That's 180,000 tokens (made up), and it lives in a store outside the window. A student asks: "What's the max acrylic thickness on the laser cutter?"

Worked example: search, then read
  1. The model calls search_manual("laser cutter acrylic maximum thickness").
  2. The program searches the manual's index and returns 3 short snippets. Each has a page number and about 100 tokens, so 300 tokens in all.
  3. The model sees that the page 42 snippet says "Acrylic up to 12 mm", and calls read_page(42) to get the whole page.
  4. The program returns page 42: 1,500 tokens.
  5. The model replies: "Up to 12 mm (manual p. 42)."
  6. Content loaded from the manual: 300 + 1,500 = 1,800 tokens instead of 180,000, which is 1 percent.

Now compare the bill. Take a three-call run shaped like Part 2's, with a base of 1,500 tokens (system, tools and question, rounded). Retrieval sends 1,500 on call 1, then 1,500 + 50 + 300 = 1,850 on call 2, then 1,850 + 30 + 1,500 = 3,380 on call 3. That's 1,500 + 1,850 + 3,380 = 6,730 tokens in total.

Pasting the whole manual in would send the 180,000 tokens on every one of those calls: 180,000 × 3 = 540,000 tokens from the manual alone, about 546,700 once you add the 6,730 from above. Retrieval is roughly 1 percent of that.

Retrieval means finding the relevant pieces in a store outside the window and loading only those. The idea behind it is just-in-time loading: keep light pointers, like file paths, page numbers or stored queries, and load the real content on demand. Mixing in some upfront context is common, and looking things up at run time is slower than a precomputed lookup (Effective context engineering).

Notice that a retrieval tool is just a tool in the loop you already know: the model asks, the program runs the search, the result comes back. The search itself can be plain keywords or something fancier, and later lessons can look at that.

A common mix-up

"Retrieval means the model has read the whole manual." It has seen 3 snippets and 1 page. If the real answer is on page 57 and the search missed it, the model can't know that, and it may answer wrongly with confidence.

A common mix-up

"Retrieval is the same as memory." The manual is the same for every student, and nobody changes it while they chat. A student's training status is different: it changes, so it has to be written down. That's next.

Part 5: Notes as memory: what survives between sessions 4 min

When a session ends, the window is gone, so anything the assistant must know next time has to be written somewhere outside it and read back. That is all "memory" means for an agent.

Take Dana, a student. On 4 March she tells the assistant she finished laser cutter safety training. Watch what happens, and then what happens two weeks later in a brand new window.

Worked example: two sessions

Session 1, 4 March.

  1. Dana: "I finished the laser cutter safety training today."
  2. The model calls the memory tool: create /memories/students/dana.md with the text "laser cutter: trained 2026-03-04; 3D printer: no training on record".
  3. The program writes that file to its own store and returns a success message.
  4. The model replies: "Great, noted." The session ends and the window is gone.

Session 2, 19 March, a new window with no history.

  1. The model is told to check its memory first (the API adds that instruction for you when the memory tool is on).
  2. The model calls view /memories, and the program returns a list of files.
  3. The model calls view /memories/students/dana.md and gets the line from March.
  4. Dana asks to book the laser cutter. The assistant books it, and tells her the 3D printer needs training first.

The memory tool works just like the other tools you've met. It's client-side: the model asks for a file operation, and your application runs it on storage you control (memory tool doc). The general idea is notes outside the window, like a NOTES.md or a to-do list that the agent reads back after a reset (Effective context engineering).

Notes also get updated, not just created. Say that on 2 April Dana finishes the 3D printer training: the model asks the tool to change that one line in the file, the program edits it, and the next session reads the new line. The window from 19 March is long gone, but the folder holds the latest truth.

Here's the whole picture so far, in one table. It's the same table you'll use to decide things in Part 6.

WhatLives whereLasts how longCosts tokens when
System prompt and tool definitionsIn the windowEvery call, resentOn every call
Message historyIn the windowThis session, resent each stepOn every later step
Retrieved manual pagesManual store, then historyLoaded on demand, then stay in historyWhen loaded, and on each call after
Notes or memory filesMemory folder, outside the windowBetween sessionsOnly when read

A few cautions. A note can go stale: training can expire, so write the date next to it. Store only what you need, and remember that saving student data is a privacy decision for your team.

One more: the application must keep memory operations inside the memory folder. Otherwise a sneaky path using "../" could reach other files, which is called path traversal (memory tool doc).

A common mix-up

"The model remembers Dana because it talked to her before." Session 2's window starts empty. If the program hadn't saved and reloaded the note, the assistant would ask her about training again, or worse, assume she's trained.

A common mix-up

"Memory is a built-in feature that stores itself." With the memory tool, the model only requests operations. If your app's handler doesn't write the file, nothing is saved.

Part 6: Choosing what to keep: a worked example, then practice 6 min

Now put the pieces together: for each thing the assistant needs, decide whether it lives in the window, in a search over the manuals, or in a saved note. This is the decision you'll defend at your design review.

Ask these questions, in order, about any item.

  1. Is it needed on every step? Keep it in the window, and keep it short.
  2. Is it big and only sometimes needed? Retrieve it.
  3. Does it change between sessions, and is it ours to record? Save a note, with a date.
  4. Does someone else's system own it and keep changing it? Don't copy it; ask for it with a tool each time.
Worked example: sort six items
  1. The assistant's rules and tone: window. They're needed on every call, so keep them short.
  2. The machine manuals: retrieval. They're big and only one page is needed at a time.
  3. Dana's training status: note, with the date. It changes between visits and nothing else records it.
  4. The booking Dana just made in this chat: history. It's already there. Write a note only if it must be known next visit, and even then the calendar is the real record.
  5. The calendar: a tool call each time. It changes constantly and belongs to the booking system, so a copy would go stale.
  6. The list of tool descriptions: window, kept short. They're needed on every call, and every word costs tokens each time.

Notice the booking and the calendar are the same rule seen twice: when another system holds the truth, point to it instead of copying it. Also notice that one item can be in two places for different reasons. The booking sits in the history for this chat, and in the calendar for good.

Your turn: four new items, steps fading

Sort each item into window, retrieval, note or tool call, with a one-line reason. Item (a) is done for you. Item (b) has its answer and needs a reason. Items (c) and (d) are yours to do in full.

  1. The safety rules for the 3D printer, 40 pages. Answer: retrieval. Reason: it's big, and only needed when someone asks about it.
  2. Which students have had the soldering training. Answer: note. Reason: ______
  3. What the student asked two steps ago in this chat. Answer: ______ Reason: ______
  4. The bandsaw's maintenance schedule, which changes weekly. Answer: ______ Reason: ______
Hint 1

For each item ask: does it change? If it does, who owns the record?

Hint 2

Ask: is it needed on every step? If it's already in this chat, it's already in the history.

Show the solutions

(b) Note, because the list changes as students train and nothing else records it; write the date, since training can expire. (c) History: it's already in the window because the program resends the chat. (d) A tool call each time, because someone else maintains it and it changes weekly, so a saved copy would go stale by next week.

A common mix-up

"Put everything in the system prompt, it's simplest." With 180,000 tokens of manuals sent on every call, three calls per request means 540,000 input tokens for one question (Part 4). Simple to build, ruinous for a small budget.

That's the real point for your sponsor: what you keep, retrieve or save is your cost lever, because tokens sent on each call decide the bill.

Summary 2 min

  • The model sees only the window on each call, and tokens measure both that window and the cost.
  • Each step is a new call that resends the history, so the window and the bill grow.
  • Trim with clearing and compaction, and look up long material with retrieval instead of pasting it in.
  • Between sessions, only what was written outside the window survives, as notes you read back.
